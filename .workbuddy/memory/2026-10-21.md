## §84 传输层：不做 HTTP 中转（2026-10-21）

用户第二次提"以前玩的客户端都是 http 连 php 再转后端"，问 ws 直连会不会出别的问题。

**结论**：不做应用层中转（③）；要 TLS/端口/穿透做**反代**（②）。
- 关键分辨：② **不懂**业务协议（只搬字节 + 透传 `Upgrade`）；③ **懂**（每次 POST 一条指令）⇒ 要会话粘性、要自己实现推送。
- 用户见到的 PHP 是 ③，根因是 **2011 年前浏览器没有 WebSocket**（XHR + `flush()` 是唯一推法）+ 便宜主机只能跑 PHP。
- ③ 的代价：会话粘性 / 协议第二份真相（§82 刚收敛完）/ 客户端与中转各写一遍长轮询 / 多一段会挂的链路 / 保活零收益。
- ws 直连的真实问题（已列成表）：Android 9+ 明文、运营商 NAT 撕空闲 TCP、WiFi↔4G 半开、只放 443、只给 CONNECT 的代理环境、服务端无 TLS。
- **代码里已经留好口子**：`mud.core.Transport`（connect/send/close）是唯一替换点，HTTP 中转也塞得进这个形状；服务端 `WS_PATH='/ws'` 不依赖反代特性。

### 补：`normalizeWsUrl`（同日）

## 手机联调启动器 `npm run start:phone`（26 册 §88｜31 册 §9.8）

新增 `tools/serve-phone.mjs` + npm script `start:phone`。起因：`npm run start:lan` 印的是
**http** 局域网地址，而服务端那行 `WebSocket ws://0.0.0.0:8123/ws` 里的 `0.0.0.0` 是通配地址、
**不是能拨的地址** —— 安卓端要填 `ws://192.168.1.2:8123/ws`，照抄任一行都连不上，
而失败表现是"点了没反应/一直转圈"，报错里不会出现地址长得对不对。

做法：不复制逻辑（复用 `cli.DEFAULT_PORT` / `cli.lanAddresses()` / `cli.main()` /
`server/paths.ts#PROJECT_ROOT`），**不用子进程**跑服务（Windows `kill('SIGTERM')` 不投真信号），
进程内 `cli.main()` 挂着即可。

三条判据与理由：
1. 端口预检用 **TCP 连一下**而不是 bind —— Windows `SO_REUSEADDR` 宽松，两进程能绑同端口；
   连得上才证明有人在听。
2. 自检**真拨一次 WS 握手**（`ws` 包，1.5s 超时），回环 + 每块网卡各一次；
   三结局分开报：全不通=没起来 / 只通回环=防火墙或跨网段 / 网卡通=可装机。
3. ★★ 边界写进输出：Windows 防火墙不拦本机到本机 ⇒ 自检绿**证不到**手机能连；
   真正能证的是**手机浏览器**打开 `http://IP:8123/`。所以脚本让人先开浏览器再装 APK。

实测（本机 192.168.1.2）：回环 ✅ / 局域网 ✅，输出"手机上填 ws://192.168.1.2:8123/ws"。
自证会红：服务开着时再跑同端口 → 预检拦下 exit 1。停服务后 `netstat` 只剩 TIME_WAIT、
无 LISTENING（"进程退了端口还占"是这类脚本最容易留下的假象，专查了）。

闸门 12/12、vitest 52/1178 全绿。`tools/` 三约束都满足：R6.7 用 `EXIT_*`、G17 不 export、
R6.8 非空。★ 顺带确认 R6.5（禁硬编码 `ws://`）扫的是 `shared|server|world|src`，`tools/` 不在内 ——
但脚本仍按 `cli.ts` 的纪律用常量拼前缀。
