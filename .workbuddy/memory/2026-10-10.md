### ★ 本次抓到的真缺陷：`isPropKey()` 与 `PropKey` 类型不等价

`shared/constants.ts` 的运行时守卫原实现是「**一次性**剥掉 `diff_`/`add_` 前缀 + `_per` 后缀再查核心键」。
但核心表里本身就有以 `_per` 结尾（`bj_per`、`diff_sh_per`）、以 `add_`/`diff_` 开头（`add_sh`、`diff_fy_per2`）的键
→ 单次剥离**多剥一层** → **22 个类型合法键被误拒**：
`add_bj_per`(=add_+bj_per)、`diff_sh_per_per`、`add_add_bjsh_per`、`diff_fy_per2_per` …

- **手工枚举时我只看出 6 个**，机械全量展开后报出 **22 个** —— 这就是"不靠人工枚举"的直接证据。
- 反向也有坑：`per`（容貌）**是合法核心键**，同时是派生后缀词，极易被误伤（我第一版噪声样本就自己写错了）。
- 修法：按 **6 个族各自独立**判定（族1 `c` / 族2 `c_per` / 族3-4 `diff_c[_per]` / 族5-6 `add_c[_per]`），任一命中即合法。
- 守护方式：`tests/g3-constants.test.ts` 用「**类型全量展开 vs 运行时守卫**」双向对账（先跑红再修），
  并纳入元闸门变异样本（把 isPropKey 退回旧实现 → 测试立刻变红）。

### 设计改动：EXT 层从"闸门报红"升级为"编译期写不进去"

- 新增品牌类型 `ExtProp = string & { readonly [EXT_PROP_BRAND]: true }`，**唯一来源**是 `registerExtProp()` 的返回值
  （返回类型 `void` → `ExtProp`）。
- `server/world/defs.ts` 新增 `PropMap`：`prop`（闭集 `PropKey`，参与核心公式）
  + `extProp: ReadonlyArray<readonly [ExtProp, number]>`（已登记扩展键，不参与核心公式）。
- **刻意不写 `Partial<Record<PropKey | ExtProp, number>>`**：`Record<ExtProp, ...>` 会退化成
  `{ [x:string]: number }` 索引签名，`prop: { attack: 1 }` 又能编译通过，闭集护栏当场失效。

## 最小属性访问器落地（同日续 2）

### 先取证：wushen 的 `add_prop` 有两处**静默污染**

`os/char/chara_prop.js:3-19` 的真实实现：

```js
CHARACTER.prototype.add_prop = function (p, v) {
    if (!p) return;                 // ★ 只挡空键
    var v1 = this.prop[p] || 0;
    this.prop[p] = v1 + v;          // ★ 对 v 零校验
}
CHARACTER.prototype.query_prop = function (name) {
    if (this.prop) return this.prop[name] || 0;   // 未设置读作 0（不是 undefined）
}
```

- `add_prop('gj', undefined)` → `0 + undefined` = **NaN**，攻击变 NaN，后续所有公式**静默**失效
- `add_prop('gj', '5')` → `0 + '5'` = **`'05'`**（字符串拼接），数值变字符串
- 另有 `clear_prop`（无 remove_prop）；`change_prop(prop, isadd)` 遍历加/减并特判 `'skill'`

### 交付物 `server/engine/props.ts`

**核心/扩展两套入口 + 两个 Map**（存储层不变量，不只是类型约定）：`props` / `extProps`。

| 入口 | 键类型 |
|---|---|
| `getProp` `setProp` `addProp` `hasProp` `removeProp` `clearProps` | `PropKey` |
| `getExtProp` `setExtProp` `addExtProp` `hasExtProp` `removeExtProp` `clearExtProps` | `ExtProp`（运行时再用 `isExtProp` 兜强转） |
| `snapshotProps` `loadProps` | 存档边界；`loadProps` 逐键校验，未登记键记账 `rejected` **不写进表** |

- `createPropHolder()` / `PropHolder` 接口：与 `defs.ts` 的 `Actor` 同取向——**不要求继承任何引擎基类**。
- `PropValueError`：非有限数值 / 未登记扩展键一律抛错。
- props.ts **只 import `@shared/constants.js`**，不碰 `server/world/**`（保持引擎与内容框架解耦）。
- ⚠️ 除 props.ts 外任何地方不得直接操作 `.props`/`.extProps`（G3.E 闸门守）。

### 测试 `tests/props.test.ts`（19 tests）——每条防护都配"没有它会怎样"的对照

- ★ **对照实验**：复刻 wushen 旧实现，断言它确实产出 `NaN` 与 `'05'`，再断言新访问器抛错且 `h.props.size === 0`（不写脏表）。

### 讨论：jQuery 是否繁琐 → 改掉我们自己同类写法（`docs/26` §15.8）

用户问"wushen 全程 jQuery 是否繁琐 / JS 发展这么久没优化过吗"。结论三层：
① **jQuery 的活原生全干了**（`querySelector` / `classList` / `closest` 事件委托 / `fetch` / `dataset`），
   所以"优化"不是出现更好的库，而是**不需要那个库了**；
② **wushen 真正的繁琐不在 jQuery**：字符串拼 HTML（XSS 面）、`Process`↔`Dialog` 循环引用、
   `Process.itemsElement` 与 `Dialog.pack.items` **同一事实存两份**、无类型 —— 换掉 jQuery 也照样存在；
③ **我们自己也有三处同类写法，已改**：
   - `need()` 每次 `getElementById` → **缓存**（+ `resetNodeCache()` 供测试）
   - `fill()` 逐个 `removeChild`/`appendChild` → **`replaceChildren(...)`**
   - 每个 `.ritem`/`.vb`/`.room-exit`/`.dtab` 各绑监听器 → **`delegate()` 事件委托**
     （监听器从"每次渲染 N 个"降到整页固定 13 个；**渲染函数变成纯的**，只产节点、`data-*` 记动作）
   ★ 委托的关键收益是"**重建 DOM 不用重新绑**"，测试专门钉住这条 + 一条防越界（点容器自身不触发）。

**明确不做**（避免为"现代"而折腾）：虚拟 DOM / keyed diff（一屏几十个，收益为负）、
引入框架（多一个要跟协议对账的地方）、Web Components（没有复用边界）。

内环：tsc 双 config 0 错 / **420 测试**（+6）/ 闸门全 PASS 无 SKIP。
