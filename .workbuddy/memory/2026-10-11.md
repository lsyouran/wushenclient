**实测取证（不是查文档推断）**：

| 事实 | 后果 |

**三个设计决策**：

- **D1 静态 + WS 必须同端口** —— 前端 `defaultUrl()` = `ws://${location.host}/ws`（同源）。
  分两个端口会"页面正常但连不上"（最难查的形态）。契约：传入的 http 服务器**必须尚未 listen**。
- **D2 `GET /` 返 302**（不是直接把 index.html 吐在 `/`）—— 否则相对引用以 `/` 为基址 →
  去请求 `/style.css` 而不是 `/src/style.css` → 404。与 §16.12 F5 同类：**把"内容来源"当成"内容基址"**。
- **D3 `--web-root` 语义 = 服务根**（默认 `dist/web`，`src/` 与 `shared/` 是它的同级子目录）；
  测试用 `PROJECT_ROOT` 做对照组，证明两种布局都成立。

**五个坑（每个都有测试钉住）**：

- **P1 `node_modules` 里 `.js` 旁边躺 `.d.ts`** —— 我的 `.js`→`.ts` 候选一路生效到依赖里，
  把 zod `v3/external.d.ts`（类型声明）当模块加载 → 启动链当场炸。修：候选表**永不含 `.d.ts`** +
  依赖内一律放行。**并写对照组**（只断言"返回 null"没区分力，FG-11 形态）。

- **P4 `fetch` 会把 `%2e%2e` 归一化成 `..` 并弹掉一段** ⇒ 路径穿越**到不了服务器**，测是**假绿**。

  会在到达被测代码之前改变输入，此时失败的测试是**正确的**。**

### 附：Vite 选型评估（**已实测取证**，未落地任何改动）

起因：用户问"如果前端采用 Vite 会怎么样"。**Vite 8.3.4 已随 vitest 躺在 `node_modules` 里**，所以直接读实现取证。

**两条原本以为要改、实测不用改的**：

- **`.js` 说明符 → `.ts`：Vite 原生支持。** 源码里有 `knownTsOutputRE = /\.(?:js|mjs|cjs|jsx)$/` + `isPossibleTsOutput()` → `tryCleanFsResolve` 的 `possibleJsToTs` 分支。本项目的 TS ESM 写法不用改。
- **tsconfig `paths`：Vite 8 能读，但 `@default false`。** `dist/node/index.d.ts` 里
  `interface ResolveOptions extends EnvironmentResolveOptions` 内有 `tsconfigPaths?: boolean`（JSDoc: "Enable tsconfig paths resolution / @default false"），
  `UserConfig.resolve?: AllResolveOptions`。开 `resolve.tsconfigPaths: true` 即可沿用同一份 tsconfig，
  **不必手写第四份别名表**（前提是记得开）。

**真正的代价（若上了）**：

1. **同端口消失**（最硬）。dev server 默认 5173，前端 `defaultUrl()` = `${location.host}/ws` → 连到 5173 → 连不上后端；
   必须 `server.proxy` 转 `/ws`（`ws: true`）。代价：多一份**只存在于开发期**的解析规则（正对 FG-18「构建成功 + 白屏」那类）；
   且**中间多一层可能掐断空闲连接的代理** → **F1"浏览器自动 pong 活过 90s"的结论必须重验**（现有验证方法：真浏览器挂机 95s）。
2. **G14 判据失效**：`g14-webgraph.mjs` 的判据是"可达图里无裸包名"，而 Vite 会预打包依赖 ⇒ 裸包名合法。
   即 **Vite 会直接消掉 FG-18 那条硬约束**（好处：前端可复用 `shared/protocol.ts` 的 zod 做前置校验；代价：产物变大 + `import type` 那套纪律失去必要性）。
3. **产物布局与一批测试作废**：`tsc` 现在是"保留目录结构到 `dist/web/src|shared/**`、服务根 `dist/web/`"，
   `DEFAULT_INDEX_PATH='src/index.html'`、`GET /` 的 302、`tests/static-web.test.ts` 的"与真实产物对账"全建立在此；
   Vite build 产出扁平 + hash（`dist/index.html` + `dist/assets/index-[hash].js`）。
4. devDeps 从 7 个变两百多个（esbuild 原生二进制 / rollup / postcss…）。**运行期依赖不变**（`ws`+`zod` 不动，vite 进 devDependencies）。
5. **后端的 `tools/dev/ts-loader.ts` 与 Vite 完全无关** —— 上了 Vite 也**不能删**（Vite 只管前端）。

**闸门冲突核对**：`g6-redline.mjs` 的 `PRODUCT_DIRS = ['shared','server','world','src']`，
根目录的 `vite.config.ts` **不在扫描范围** ⇒ 在里面写 proxy 目标不会撞 G6 R6.5。

**结论**：现在不该上（需求只是"递文件"；会撞三条已用闸门钉住的纪律 + 破坏 F1 结论）。
值得重估的触发条件：引入 React/Vue、需要 npm 生态库、前端文件数上几百、`tsc` 全量编译 >~5s、需要代码分割。
若只嫌 `tsc` 慢 → `tsc -p tsconfig.web.json --watch`，**零新依赖零纪律改动**。
若一定要上 → **要么全上要么不上**；"只 dev 用 Vite、生产走 tsc"是最糟组合（开发/生产解析规则不一致）。

**启服务器实测时的一个"假 404"（环境，非代码）**：`curl -L http://127.0.0.1:8123/` 报 404，
但 `curl --noproxy '*' -L` 与直接取 `/src/index.html` 都是 200 text/html；同一条 keep-alive 连接上用
node `http` 顺序发 `/` → `/src/index.html` 也是 302 → 200。**根因是本机代理环境变量**
（`http_proxy=http://127.0.0.1:11327`）在复用连接转发重定向目标时弄坏了请求 ——
与 §16.12 的"本机代理造出假 502"同族。**复核本机服务一律加 `--noproxy '*'`**，
否则会去改一段没坏的代码（已记进 26 册 §17.11 与 MEMORY.md 环境坑）。
