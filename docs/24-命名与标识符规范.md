## 0. 为什么需要这份文档

21 册已确认的缺陷里，**将近一半属于"标识符漂移"**——不是逻辑错，而是同一件事被写成了两个名字。本次对 wushen 源码独立复核，又拿到三条硬证据：

| 证据 | 实测 | 来源 |
|---|---|---|
| 同一索引两种拼写并存 | `OBJ_STROE`/`NPC_STROE`（错）**7+7 处**，`OBJ_STORE`/`NPC_STORE`（对）**4+2 处** | `os/world.js:15/16`、`os/util/hotload.js:184/185/306/307` |
| 属性键定义与使用严重脱节 | `query_prop/add_prop` 实际用 **121** 个键，`PROPERTIES` 只定义 **70** 个，**69 个未登记**（几乎全是技能专属键如 `ylxf_gj`、`whd_sh_max`） | `os/const.js:35-115` + 全库扫描 |
| 常量缺项导致静默降级 | `EQUIP_TYPE.PANTS` 不存在，但 `equipment.js:103/140`、`go.js:95` 在用 | 21 册 #17 |

**结论：不先把"名字"钉死，TS 的编译期护栏也救不了。** 本文件就是那根钉子。

## 1. world 对象标识符 —— 方案 C（路径 + 显式 kind）

### 1.1 语法

```
id  := <area> ( '/' <segment> )+ [ '#' <variant> ]
```

| 规则 | 值 |
|---|---|
| `segment` | `/^[a-z][a-z0-9_]*$/`（小写字母开头；只允许小写字母、数字、下划线） |
| 段数 | **1 ~ 5 段**。非 `area` 的 kind **至少 2 段**；`area` 允许单段（如 `yz`，沿用 wushen 语义） |
| `variant` | `/^[A-Za-z0-9_]{1,32}$/`（允许大小写，仅作后缀） |
| 总长 | ≤ 128 |
| 大小写 | **严格小写**，不做静默归一化（大写 = 直接拒绝） |

### 1.2 三段含义

| 段 | 含义 | 例 |
|---|---|---|
| `area` | 一级分组。房间/NPC/物品按**地理区域**，指令/技能按**功能分类** | `yz` / `pub` / `action` |
| `path` | area 之后的全部层级 | `guangchang` / `bj/guanwai/xiong` |
| `variant` | 可选，同文件派生的第 N 个对象（`#` 语法沿用 wushen） | `drug/yao#2` |

### 1.3 关键取舍：`kind` 不写进 id

这是方案 C 与方案 B（`area:kind:localname`）唯一的功能性差异。理由见下：

| | 方案 A 纯路径 | 方案 B 分段 ID | **方案 C（采纳）** |
|---|---|---|---|
| id 示例 | `yz/guangchang` | `yz:room:guangchang` | `yz/guangchang` |
| id 自解释 | ✗ 看不出类型 | ✓ | ✗（但由 `kind` 字段补足） |
| 类型判别 | 靠目录约定 | id 内建 | **kind 字段 + 注册表桶** |
| 文件名 = id | ✓ | ✗ **`:` 是 Windows 文件名非法字符**，必须额外维护 `id→文件` 映射表 | ✓ |
| 迁移成本 | 零 | 需全量转换 | 零 |

**决策记录**：方案 B 唯一优势是"id 自解释"，代价是凭空多出一张映射表——而映射表本身就是漂移温床（参考本文件开头那三条证据）。方案 C 用**一个必填字段 `kind`** 换掉整张映射表，同时保留类型判别能力。

### 1.4 kind 清单（闭集）

| kind | 注册表桶 | `world/` 目录 |
|---|---|---|
| `room` | `registry.rooms` | `world/room/` |
| `area` | `registry.areas` | `world/area/` |
| `npc` | `registry.npcs` | `world/npc/` |
| `item` | `registry.items` | `world/item/` |
| `skill` | `registry.skills` | `world/skill/` |
| `family` | `registry.families` | `world/family/` |
| `command` | `registry.commands` | `world/command/` |
| `task` | `registry.tasks` | `world/task/` |

> **目录名恒等于 kind 名**。这是方案 C 的核心约定，也是与 wushen 最大的结构差异（wushen 用 `map/` 装房间、`cmd/` 装指令，类型与目录名不一致，必须靠一张翻译表——删掉它）。

### 1.5 subtype（不参与 id）

wushen 靠继承区分 `NPC`/`MONSTER`、`OBJ`/`EQUIPMENT`；新项目在 `kind` 之上再加一个 `subtype` 字段：

| kind | 允许的 subtype |
|---|---|
| `npc` | `monster` |
| `item` | `obj` · `equipment` · `container` · `corpse` · `money` |
| 其余 | 无 |

`subtype` 只作为对象字段，**不进 id**——避免 id 越来越长。

### 1.6 area 规则

- **area 的 id 是单段的**（`yz` / `bj` / `pub`），这是 id 语法里唯一允许 1 段的 kind。
  其余 kind 必须写成 `<area>/<...>`。该约束由 `MIN_SEGMENTS_BY_KIND` 承载，
  在注册时（`asWorldIdForKind`）而非正则里校验 —— 这样 `parseWorldId` 保持与 kind 无关，
  可被闸门通用复用。
- 保留字：**不得与任何 kind 同名**（否则 `item/gj` 这类 id 会歧义），也不得占用工程目录名（`shared`/`server`/`src`/`tools`/`index`/`test`）。
- `pub`：跨区域公共内容区（对应 wushen `npc/pub/`），**正式保留**。
- 新区域先在此登记再做内容，避免"同一个地方两个名字"。

### 1.7 变体 `#`

- 一个文件可派生 N 个对象：`world/item/drug/yao.ts` → `drug/yao`、`drug/yao#0`…`#3`。
- 变体**不改变文件位置**；引用时必须写全（`book/bc#taijijian`）。
- 禁止用变体表达"同一对象的不同状态"（那是运行时字段的事）。

### 1.8 唯一性

- **同一 kind 内 `path` 唯一**（跨 kind 允许重名，因为注册表已分桶）。
- 加载期断言：重复注册 → **直接抛错终止**（wushen 是 `console.error` 后照旧覆盖，见 13 册 13.1）。

### 1.9 文件映射（零翻译表）

```
world/<kind>/<area>/<...path>.ts      ←→      id = <area>/<...path>
```

| id | kind | 文件 |
|---|---|---|
| `yz/guangchang` | room | `world/room/yz/guangchang.ts` |
| `pub/xiaoer` | npc | `world/npc/pub/xiaoer.ts` |
| `bj/guanwai/xiong`（**示意**，见下） | npc | `world/npc/bj/guanwai/xiong.ts` |
| `drug/yao`（+`#0`~`#3`） | item | `world/item/drug/yao.ts` |
| `move/go` | command | `world/command/move/go.ts` |

> ★ **本表是"映射规则"的示例，不是内容清单**（2026-10-13 订正，26 册 §29.5）。
> 表里只有 `yz/guangchang` / `pub/xiaoer` / `drug/yao` / `move/go` 四行是**当前真实内容**；
> `bj/guanwai/xiong` 是**多段路径（`<area>/<...path>`）的示意**，`bj` 区域尚无内容。
> 另：命令的 id 曾是 `action/go`，`go` 指令迁到 `world/command/move/` 后 id 变成 **`move/go`**
> —— 描述形状的规则（`world/command/` 下的相对路径 = id）**一个字没变**，变的只是目录名。
> 全量真实 id 见 **26 册 §29.7** 那张清点表（**2026-10-13 人工清点**）。
> ⚠️ **别指望闸门**：`G5` 兜的是"**代码里的** id ↔ 路径 ↔ 登记清单"三方一致，
> 它**读不到本表** —— 也就是说 **文档里的示例写错了，G5 不会红**（这正是 §29 要人来做的那一层）。

## 2. 代码层命名法

### 2.1 文件与目录

| 项 | 规则 | 例 |
|---|---|---|
| 代码文件 | `kebab-case.ts` | `ws-server.ts`、`damage.ts` |
| 内容文件 | **全小写下划线**，= id 的 path | `beidajie1.ts`、`cui_sz.ts` |
| 目录 | `kebab-case`（内容目录除外，内容目录 = id 段） | `world/room/yz/` |

### 2.2 类型与接口

| 项 | 规则 | 例 |
|---|---|---|
| 类型 / 接口 / 枚举对象 | `PascalCase`，**不加 `I` 前缀** | `RoomPacket`、`ServerPacket`、`WorldId` |
| 判别联合的成员 | `<语义>Packet` | `ScPacket`、`CmdsPacket` |
| 泛型参数 | 单大写字母或 `TPascal` | `T`、`TData` |

### 2.3 变量 / 函数 / 常量

| 项 | 规则 | 例 |
|---|---|---|
| 变量、函数、方法、参数 | `camelCase` | `parseWorldId`、`allowLevel` |
| 模块级真常量（数字/字符串） | `SCREAMING_SNAKE_CASE` | `TICK_MS`、`MAX_GRADE` |
| 常量**表**（枚举语义的 `as const` 对象） | `SCREAMING_SNAKE_CASE` | `PROPERTIES`、`EQUIP_TYPE` |
| 布尔 | `is` / `has` / `can` / `allow` 开头 | `isFighting`、`allowBusy` |
| 私有字段 | `#` 前缀（原生私有），不用 `_` 前缀 | `#cache` |

### 2.4 协议字段：wire 用 `snake_case`

| 层 | 风格 | 例 |
|---|---|---|
| **协议包字段（wire）** | `snake_case` | `max_hp`、`role_id`、`order_id` |
| 引擎内部对象字段 | `camelCase` | `maxHp`、`roleId` |
| 数据库列 | `snake_case` | `max_hp` |

**理由**：① 与 24 册协议字典、wushen 语义 1:1 对照；② 与 SQLite 列名一致，少一层映射；③ 两端都是 TS，字段名不影响 IDE 提示。

> 例外中的例外：wushen 的 `items` 数组**末尾 `0` 哨兵**（`room.js:139`）**取消**，不再保留。

### 2.5 布尔字段

统一 `is_` / `has_` / `can_` / `allow_` 前缀 + `_` 后缀语义：

- `is_equipment`、`is_container`、`is_player`（对象特征）
- `has_use`、`has_study`（能力）
- `allow_fight`、`allow_busy`（闸门）

**禁止**：`no_fy`（否定式，读起来双重否定）→ 新代码用 `blockDefense`；仅因 wushen 常量表兼容才保留 `no_fy`/`no_pfm` 作为**属性键**。

### 2.6 常量必须收成联合类型

**任何字符串枚举只允许定义一次**，并导出对应联合类型。写法见 `shared/constants.ts`：

```ts
export const EQUIP_TYPE = { WEAPON: 0, /* ... */ PANTS: 11 } as const;
export type EquipSlotName = keyof typeof EQUIP_TYPE;
```

这样 `EQUIP_TYPE.PANT` 这种拼错会在编译期失败，而不是像 wushen 那样落到 default 分支静默降级。

### 2.7 路径规范（★ 可重命名安全）

> **需求**：项目目录名会变（现在叫 `newmud`，将来可能改名）。改名后**不允许**出现
> 「一堆路径导入报错」。因此本项目对"路径"立三条硬规则。

| # | 规则 | 说明 |
|---:|---|---|
| R1 | **代码内禁止出现绝对路径字面量** | 不得写 `D:\...`、`C:/...`、`/Users/...`；一律由根派生 |
| R2 | **禁止硬编码项目目录名** | 代码里不得出现 `newmud` 这个字面量（改名即失效） |
| R3 | **禁止用 `process.cwd()` 拼资源路径** | 启动目录 ≠ 项目目录；一律用 `PROJECT_ROOT` |

**项目根的求法（唯一允许的方式）** —— 从**文件自身位置**向上查找**特征文件**，
与目录名、CWD、层级深度都无关：

```ts
// server/paths.ts
import { existsSync } from 'node:fs';
import { dirname, join, resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

const ROOT_MARKERS = ['package.json', 'tsconfig.json'];   // 特征文件 = 判据
const THIS_DIR = dirname(fileURLToPath(import.meta.url));

export function findProjectRoot(startDir = THIS_DIR): string {
  let dir = resolve(startDir);
  for (let i = 0; i < 6; i++) {                            // 向上最多 6 层
    if (ROOT_MARKERS.every((m) => existsSync(join(dir, m)))) return dir;
    const parent = dirname(dir);
    if (parent === dir) break;
    dir = parent;
  }
  throw new Error('项目根定位失败');
}

export const PROJECT_ROOT = findProjectRoot();
```

> ⚠️ **为什么不能只 `resolve(THIS_DIR, '..')`**：源码布局下 `server/paths.ts`
> 上溯一层确实是根，但一旦编译/打包到 `dist/server/paths.js`，上溯一层得到的是
> `dist/` 而不是项目根 —— 路径全错。**向上查找特征文件**才能同时兼容两种布局。
> （此问题在实测中被 `assertProjectRoot()` 捕获，见 §5 G12 实验记录。）

配套约定：

- **模块导入一律用相对路径**（`./ids.js`）或 tsconfig 别名（`@shared/*`）。
  `tsconfig.json` 的 `baseUrl: "."` 与 `paths` 均为**相对值**，因此整个工程目录
  可以随意改名 / 移动，编译不受影响。
- **`shared/` 保持零 Node 依赖**（不 import `node:*`、不使用 `process`），
  这样它既能被服务端也能被浏览器端引用；Node 专属的路径解析放 `server/paths.ts`。
- **纯逻辑用相对路径（id / `world/<kind>/...`），磁盘绝对路径只在 `server/paths.ts` 落地一次。**

**验证方式（可复现）**：把工程目录改名后重跑 `npm run check`，必须仍然通过。
本项目已实测通过（见 §5 闸门 G12 的实验记录）。

## 3. 属性键：双层结构（★ 本次复核的最重要产出）

### 3.1 证据

对全库 `query_prop` / `add_prop` / `set_prop` 扫描：

```
实际使用 key 数: 121
PROPERTIES 定义数: 70
使用了但未定义: 69   ← 几乎全是技能专属键（ylxf_gj / whd_sh_max / mgqq_cc ...）
```

**单张表不可能覆盖**：技能/物品/门派会不断自造 buff 键。所以分成两层：

| 层 | 范围 | 类型 | 未登记时 |
|---|---|---|---|
| **CORE** | 引擎明确理解的键（属性、战斗、气血、绝招、活动效率…共 76 个） | **闭集联合类型** `CoreProp`（+ 规则派生的 `ModProp`） | 编译期直接报错 |
| **EXT** | 内容层自造（技能/物品/门派） | **品牌类型** `ExtProp`，唯一来源是 `registerExtProp()` 的**返回值** | **编译期就写不进去**（强转由 G3 闸门兜底） |

### 3.2 派生规则（不逐一枚举）

| 后缀 / 前缀 | 语义 | 例 |
|---|---|---|
| `<X>_per` | 百分比加成 | `gj_per`、`study_per` |
| `diff_<X>` | 减免 / 抵抗 | `diff_sh`、`diff_busy` |
| `diff_<X>_per` | 减免百分比 | `diff_fy_per` |
| `add_<X>` | 追加 | `add_sh` |
| `add_<X>_per` | 追加百分比 | `add_bjsh_per` |

`PropKey = CoreProp | ModProp`，全部由 `shared/constants.ts` 导出。

### 3.3 引擎 vs 内容的边界

> **引擎层（`server/engine/**`）只允许读写 `CoreProp`/`ModProp`。**
> 内容层（`world/**`）可以用扩展键，但必须登记，且**扩展键永远不参与引擎核心公式**
> （`recount()`、伤害公式只认 CORE —— 这正是 wushen 21 册 #20「两处各覆盖一份
> recount，`ds` 公式 `/5` vs `/10` 不一致」的根治办法）。

### 3.4 落点：为什么属性映射要拆成两个字段

| 字段 | 类型 | 语义 |
|---|---|---|
| `prop` | `Partial<Record<PropKey, number>>` | 引擎核心键（CORE + MOD），参与核心公式 |
| `extProp` | `ReadonlyArray<readonly [ExtProp, number]>` | 已登记的扩展键，**不参与核心公式** |

**为什么不是 `Partial<Record<PropKey | ExtProp, number>>`（一个字段更简单，但会漏）**：
`Record<ExtProp, number>` 里 `ExtProp` 是「字符串 + 品牌」的交集类型，映射类型无法对它
建索引签名，会退化成 `{ [x: string]: number }` —— 于是 `prop: { attack: 1 }` 这种错键
**又能编译通过**，闭集护栏当场失效。拆成两个字段还顺带把 §3.3 的边界结构化了。

**为什么 EXT 用「品牌类型」而不是「闸门报红」**：
把「必须登记」做成**编译期约束**（拿不到 `registerExtProp()` 的返回值就写不进 `extProp`），
比等闸门报红更早、更难绕过。残留缺口只有 `'x' as ExtProp` 这类强转，由 G3.B 兜底。

#### ★ 本次实测：`isPropKey()` 与 `PropKey` 类型**不等价**（22 个键漏判）

原实现是「一次性剥掉 `diff_`/`add_` 前缀 + `_per` 后缀，再查核心键」。但核心表里
**本身就有**以 `_per` 结尾（`bj_per`、`diff_sh_per`）、以 `add_`/`diff_` 开头
（`add_sh`、`diff_fy_per2`）的键 —— 单次剥离会**多剥一层**：

```
add_bj_per        = add_ + bj_per          → 误剥成 bj       → 误判非法
diff_sh_per_per   = diff_sh_per + _per     → 误剥成 sh       → 误判非法
add_add_bjsh_per  = add_ + add_bjsh_per    → 误剥成 add_bjsh → 误判非法
…共 22 个类型合法键被拒
```

反向也有坑：`per`（容貌）**是合法核心键**，同时又是派生后缀词，极易被误伤。

**修法**：按 6 个族**各自独立**判定，任一命中即合法（与类型定义一一对应）。
**这条不靠人工枚举守住**——由 `tests/g3-constants.test.ts` 拿「类型全量展开 vs 运行时守卫」
双向对账（先把断言跑红，再修代码），并纳入元闸门变异样本。

> 这与 §3.1 那组「121 vs 70」是同一个病：**类型与运行时两套规则各自演化**。
> 只要两套规则不焊死，换一种拼写方式它就再犯一次。
> 附带证据：手工枚举时我只看出 6 个漏判键，测试机械展开后报出 **22** 个——
> 这正是"不靠人工枚举"的理由。

### 3.5 属性访问器（`server/engine/props.ts`）

唯一读写入口，取代 wushen `CHARACTER.prototype.query_prop / add_prop`
（`os/char/chara_prop.js:3-19`）。核心与扩展**两套入口、两个 Map**：

| 入口 | 键类型 | 语义 |
|---|---|---|
| `getProp` `setProp` `addProp` `hasProp` `removeProp` `clearProps` | `PropKey` | 核心属性。未设置读作 **0**（与 `query_prop` 一致，不是 `undefined`） |
| `getExtProp` `setExtProp` `addExtProp` `hasExtProp` `removeExtProp` `clearExtProps` | `ExtProp` | 扩展属性。运行时再用 `isExtProp()` 校验一次，兜住 `'x' as ExtProp` 这类强转 |
| `snapshotProps` `loadProps` | — | 存档边界。`loadProps` 逐键校验，未登记键**记账到 `rejected` 而不写进表** |

四道防护，每道都配了「没有它会怎样」的对照：

| # | 防护 | wushen 的实际行为 |
|---|---|---|
| 1 | 键有类型：CORE/MOD 一套入口、EXT 另一套 | 任意 `string` 通吃 —— 121 个键里 69 个没定义也照样跑 |
| 2 | **值必须是有限数值**，否则抛 `PropValueError` | `add_prop` 只做 `if (!p) return`，**对值零校验**：<br>`add_prop('gj', undefined)` → `NaN`；`add_prop('gj','5')` → `'05'`（字符串） |
| 3 | 核心 / 扩展存在**两个 Map** | 一个大对象，扩展键与核心键同池，边界只靠约定 |
| 4 | 不可信数据一律过 `loadProps` 校验 | 没有校验层 —— 这正是 §3.2 那 69 个未登记键得以长期存在的条件 |

> **G3.E 闸门**保证除 `props.ts` 外没有任何地方直接操作 `.props` / `.extProps`
> （即"访问器是唯一入口"不是口号，而是可机检的不变量）。

#### ★ 本次实测：`add_prop` 的静默污染

第 2 条不是防御性编程，是**实测出来的**。`tests/props.test.ts` 里先复刻 wushen 旧实现
作为对照，断言它确实会产出 `NaN` 与 `'05'`，再断言新访问器会直接抛错且**不写脏表**：

```
wushen:  add_prop('gj', undefined) → Number.isNaN(prop.gj) === true   // 攻击变 NaN，后续公式全废
wushen:  add_prop('gj', '5')       → prop.gj === '05'                 // 数值变字符串
本访问器: addProp(h, 'gj', undefined) → throw PropValueError，h.props.size 仍为 0
```

这类错误在 wushen 里**不报错、不日志、不可察觉**，只有等战斗数值明显不对才会被追查，
而那时已经跨了几十个调用栈。故必须在使用点拦下。

> **FG-19 / FG-20 的教训**：**"注释说有人管"最容易骗过所有人** —— 因为它不需要任何代码，
> 而那件事恰好是"别的机制在做"，于是你 grep 代码看不到任何异常。FG-20 尤其危险：
> 被宣称的核对**当时确实"成立"**（四个表碰巧一致），所以不写反例、不故意改坏一处，
> **这条假绿永远不会现形**。识别方法只有一条：读到一个"X 会核对 Y"的宣称时，
> **去把 X 打开看有没有读 Y**；没有就是 FG-20。
> 这与 FG-18（"前端不许依赖 zod"只有一句话在守）的区别是：FG-18 有**真实的失败形态**
> （白屏），FG-20 连失败形态都要先构造出来（改坏一处别名）才存在。
>
> **FG-23 的教训**：**判据的取值域也是断言的一部分**。FG-11 说的是"别停在 `ok` / `kind`，
> 要落到 `via` 这种区分性字段上"；FG-23 说明它前面还有一层 —— **若那个字段本身只有两个值
> 而现实有三种情况，那么无论怎么读它都会丢信息**，读得再仔细也没用。
> 识别方法：把**判据字段的值域**与**要让判据为真的情况数**并排写出来，对不上就是 FG-23 的形态。
> 顺带一条坏味道：旧版只在 `!ok` 时打印子进程输出 ⇒ **崩溃的堆栈恰好在最需要它的时候被丢掉**
> （判据判它"绿"，于是不打印）。**"只在失败时打印证据"会让判据自我封闭**。
>
> **A 批（§28）的教训 —— 三条，都是"写断言时被自己的断言骗了一次"**：
> ① **同一族缺陷有两条腿，别只修看得见的那条**：FG-14 的现象是"判据不可达"，
>    但它还有另一半 —— `session.#send` **把 `enqueue` 的返回值丢了**。只补上可达的判据、
>    不管消费者，等于"把警报装好了却没人听"。**一个新判据落地时必须同时回答两个问题：
>    它在运行时够得着吗？谁在照它做？**
> ② **判据的区分性要**实证**，不能靠推理**：第一版 FG-14 断言测的是"缓冲超限那档"，
>    而那一档 `enqueue` 会**顺手关掉连接** ⇒ `drain` 拿到空数组 ⇒ **看不看返回值都一样**。
>    改坏实现后测试照样绿（`--only=FG-1` 跑出 `❌ 假绿`），**这才发现断言测错了档**。
>    同样地，T18 的第一版断言用 `toContain('无性')`，而技能名就叫「**无性**功」——
>    篡改 `GENDER_LABELS[0]` 它照样绿。**两条都是 FG-11 的老形态，只是这次是自己写的。**
>    教训：**判据必须锚定到不可能被"别的原因"满足的位置**（这里是"队列条数那一档"与"句首"）。
> ③ **类型比实现窄，也是假绿**（T18）：三档性别的**文案早就是三档**（`skill.ts` 与
>    wushen `skill.js:239` 一致），只有类型是两档 —— 于是"只有女性可学"**表达不出来**。
>    这类缺陷**不会让任何测试变红**（`tsc` 只在你真去写第三档时才报），
>    所以它只能靠"把口径并排对一遍"发现：**类型声明 / 文案 / 原作**三者互相对照。
>    ★ 顺带记住取值的**顺序**本身就是口径：wushen 是 `1 男 / 2 女 / 0 无性`，
>    「0」不是"第一个"，按序号猜必错。
> ④ **（收尾追加，G15）"记录缺陷的地方"不能被"守那条缺陷的闸门"判红** —— **自指问题**。
>    G15 写完第一次跑，就报出 **3 处违规，全部在它自己的文档块里**（那个块必须**逐字**写出幽灵册号才说得清）。
>    两种解都是**结构性**的，都不引入行内豁免标记：**位置判据**（剥掉注释后同一行**仍含**该文本 ⇒
>    它在字符串字面量里、是数据 ⇒ 于是 `mutation-test.mjs` 里的样本注入文本**天然不计**）
>    与**角色豁免**（`docs/` 必须能**讨论**一个不存在的册号；**规则文件不判自己** ——
>    后者用 `import.meta.url` **自指**推出路径，不写死文件名，且表头打印供审计）。
>    反例是 **G12**：它扫**裸文本**、且规则显示名**自身**含被禁模式，没有可退的结构位置，
>    只能发明 `// g12-allow R1` 行内标记。⇒ **能在结构上让开，就别发明标记**；
>    真要发明标记，至少要求"必须紧跟规则号"，不留裸后门。
> ⑤ **（§29 批追加）"窄口写进文档"≠"窄口被解决"** —— 而且**窄口迟早会掉进东西**。
>    G15 的文档块明文写着"只判**册号**、不判 `§节号`"，当时读起来像一句**免责声明**；
>    直到 §29.3 复核，实测 **8 处**注释把 `24 册 §5.3` 写成 `26 册 §5.3`：`26` 是**真册**
>    ⇒ 闸门 100% 放行。**判据的覆盖边界必须与"已知会漏什么"一起读**，
>    否则"闸门全绿"会被当成"引用都对了"。写法上的配套要求：凡声明窄口，**必须同时给出"漏掉时会怎样"**
>    （G15 这次恰好给对了 —— 而正因为给了，事后能立刻断定"是窄口内的漏网，不是闸门坏了"）。
> ⑥ **（§29 批追加）机检的"召回率"本身也要自检**：§29 那支行号审计要求**写出文件名**
>    （`xxx.js:NN`），于是**回指式的裸行号**（`` `:20` `` —— 前面引过一次就不再重复文件名）
>    它**一条都看不见**：25 处行号错里它只报了 12 处。
>    ⇒ 与"零命中结论必须自检"同族：**"机检报 N 条、我改 N 条"不是收工，是抽样**。
>    做法：机检只负责**穷举它看得见的那部分**，人工必须再问一句"**这个形状有没有它看不见的写法**"。
> ⑦ **（28 册批追加）"靠某个号不存在"的判据是脆的** —— 而**建一册这种纯增益的动作，也会打穿既有判据**。
