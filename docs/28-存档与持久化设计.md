# 28 · 存档与持久化设计

> **状态（2026-10-13）：本册是「设计 + 实测」，不是落地记录** —— 存档批次（**T12**）**尚未实现**，
> 代码里已有的只是**预留接缝**（见 §28.5）。本册把「200 人 + NPC 该选哪种存档策略」用**实测数据**钉下来，
> 等 T12 开工时照着做，不再重新拍脑袋。
>
> 起因是 2026-10-13 的一个提问：
> 「如何确保数据实时更新？比如一个玩家，如何确保属性一直正确，是存储到数据库吗？
> 那么大量玩家每秒都在存储数据库压力是不是特别大」
> —— 规模基线由用户当场给定：**最多 200 人同时在线**（玩家；NPC 另算）。
>
> 范围：`wushen/{config.js, os/world.js, os/char/user.js, os/util/data.js, data/sql.js}` ↔
> `newmud/{shared/constants.ts, server/paths.ts, server/session.ts, server/engine/*}`。
> 证据归档在 `D:/ts-mud/_bench-存档基准-2026-10-13/`（脚本 + 两轮结果，可复现）。

## 28.0 一页结论

1. **「属性一直正确」不是靠读写数据库保证的**，靠的是**唯一副本 + 单一重算入口**：
   同一玩家在内存里只有一个对象，`hp`/`mz`/`ds` 这类**派生值**由 `Character.recount()` 从
   **输入量**（先天属性 / 经验 / 技能账 / 装备）算出来，没有"多个副本要对齐"这件事。
2. **存档存的是输入量，不是每跳一变的运行值** ⇒ **写库频率与战斗频率无关**。
   打一分钟架 `hp` 变上千次，**一次库都不写**。
3. wushen 的真实写库时机只有 **4 个**（§28.3），主力是「**心跳 5 s × 720 次 ≈ 1 小时的全量存档**」
   + 「**登出时单角色写**」—— **不是每秒写库**。用户担心的那个模式，在这个设计下**不存在**。
4. **200 人规模的实测结论（§28.4）**：wushen 那种最差的写法（逐条 `run`、默认 pragma）
   全量存档 **44.1 ms** —— 对 5 s 的心跳而言占 **0.9%**，**完全不是压力**。
5. **但有一个真陷阱**：SQLite 的 `cache_size` 默认只有 **2 MB**，且**与数据量无关**。
   库内热数据一旦越过这条线，耗时从 66 ms **跳到 2830 ms（43×）**，而且**与事务边界、WAL 全都无关**
   （实测：500 人时五种写法全部卡在 3.3 s，唯独显式调大缓存降到 78 ms）。
   200 人 × 8 KB = **1.56 MB**，**离这条线只剩 22% 余量** ⇒ **必须显式设 pragma**（§28.7.2）。
6. **NPC 与房间不进数据库**（§28.1.3）—— 所以「NPC 数据多些」**不增加任何写库压力**，只影响内存。
7. **推荐策略：候选 B（§28.6.4）** —— 登出写 + 每小时全量 + **脏标记** + **单事务批量** + **显式 pragma** + 备份轮转。
   理由不是性能（200 人下三种候选都跑得动），而是**崩溃窗口 / 实现复杂度 / 可测试性**的三角。

### 28.1.3 ★★ NPC / 房间**不进数据库** —— 这是本册最重要的结构事实

「NPC 数据可能多些，会不会压力大」——不会，因为**它们根本不落库**。

| 对象 | 落库吗 | 判据（可逐行回查） |
|---|---|---|
| **玩家角色** | ✅ 是 | `WORLD.save()` 只遍历 `WORLD.USERS`（`wushen/os/world.js:234-238`）→ `players` 表一人一行 |
| **NPC** | ❌ 否 | `os/char/npc.js` 里**没有** `save` / `save_db`（grep 零命中）；NPC 是**模板 + 运行时实例**，重启即按初始值重建 |
| **房间** | ❌ 否 | `os/room/*.js` 里**没有** `save` / `save_db`（grep 零命中）；房间状态（含地上的掉落物）随重启重置 |
| 世界全局 | ⚠️ 少量 | `WORLD.DATA`（`os/data.js`，123 行）只存 `parties`(帮派) / `PAIMAI`(拍卖行) / `temp`(带过期的全局 KV) + `on_save` 追加的榜单与广播（见 wushen 册 20 §20.4） |

**所以写库的规模与「世界上有多少 NPC / 多少房间 / 多少物件模板」无关**，
只与「此刻有多少玩家在线」有关。上表的 grep 判据：
`grep -rn "save_db\|prototype.save" wushen/os/room/*.js wushen/os/char/npc.js` → **零命中**。

★★ **但"零命中"必须自检**（本项目的老教训：`grep` 写错会**静默**归零 —— 见 24 册 §5.3 与 26 册 §29）。

`wushen/os/room/` 下有房间实现文件 ⇒ 这次"零命中"是**真的没有**，不是"扫了个空目录"。
（同理，`os/world.js:234-238` 的 `WORLD.save()` 只遍历 `WORLD.USERS` 是**读到代码**、不是靠 grep 推断。）

## 28.2 「属性一直正确」靠什么

### 28.2.1 没有副本，就没有一致性问题

同一玩家在 newmud 内存里**只有一个** `Player` 对象；掉线即从 `#players` 注销
（`server/session.ts:365` 明写「掉线即注销」）。所以不存在"两份数据要对齐"。

### 28.2.2 数值分两类：**输入量**（存） vs **派生值**（算）

```
                    ┌─ 输入量 ──────────────────────────────┐
                    │ 先天属性 con/dex/str、经验、技能等级    │  ← 改一下才变一次
                    │ 背包与装备、所在房间、未过期的临时状态   │  ← 存档存这些
                    └───────────────┬───────────────────────┘
                                    │ Character.recount()
                                    ▼
                    ┌─ 派生值 ──────────────────────────────┐
                    │ hp / max_hp、mz（命中）、ds（防御）      │  ← 每次都算，不存
                    │ 攻防与各类加成                          │
                    └───────────────────────────────────────┘
```

**单一重算入口**这条纪律在代码里已经钉死：

| 位置 | 内容 |
|---|---|
| `server/engine/character.ts:492` | `recount()` —— 派生值的**唯一写入口** |
| `server/engine/character.ts:461` | `maxHp` 是**只读 getter**，读 `#derived` |
| `server/engine/character.ts:433-451` | `setInnate()` 改完先天属性**自动** `recount()`，注释明写「不提供"只改不重算"的入口」 |
| `server/engine/character.ts:541-543` | `loadProps()` 之后**也**必须 `recount()`（读档边界） |
| `server/engine/skill.ts:348` | 技能改完属性后必须 `recount()`（等价 wushen 每次改技能尾部的 `me.recount()`） |
| `server/engine/formula.ts:6-24` | 公式只有一份，`recount()` 只负责调用 |

⇒ **「属性一直正确」与"有没有写库"完全无关**，它靠的是这条**单行道**。

### 28.2.3 ⚠️ 但要说准：wushen 其实**存了 `hp` / `mp`**

上一轮口头回答时我说过"派生值不落盘"，**这句话对 wushen 是要打个折的** ——
`SAVE_NUMPROP`（`wushen/os/char/user.js:271-273`）**19 项里含 `hp` 与 `mp`**：

```js
var SAVE_NUMPROP = ["str", "con", "dex", "int", "gender", "max_mp", "limit_mp", "exp", "pot", "kar", "per"
    , "hp", "mp", "max_item_count", "money", "reg_time",
    "max_store_count", "cash_money", 'eq_group'];
```

准确的说法是：**存的是"上一次落盘那一刻的快照"，不是"每跳一变的运行值"**
—— 存档只发生在 §28.3 那 4 个时机，两次存档之间的所有变化（含战斗掉血）**都只活在内存里**。
**关键结论不受影响**：写库频率与战斗频率**无关**。newmud 侧可以选择更彻底的"只存输入量、读档后满血"
（wushen 其实是"存半血就回半血"，两种都合法，**要在 T12 明确选一种并写成断言**）。

## 28.3 wushen 原作的落盘时机（逐行核对）

| # | 触发 | 代码 | 范围 |
|---|---|---|---|
| 1 | **心跳累计 720 次（≈60 分钟）** | `config.js:18` `HEARTBEAT: 5000` → `os/world.js:122` `setInterval(WORLD.heart_beat, 5000)` → `:182-187` `if (WORLD.HEARTBEATCOUNT > 720) { … WORLD.save(); }` | **全量**（所有在线角色） |
| 2 | **玩家退出** | `os/world.js:194-198` `login_out` → `user.save()` | **单角色** |
| 3 | 服务器关闭 | `world/extends/world.js:56` `if (await WORLD.save())`；`main.js:597` | 全量 |
| 4 | GM 命令 / 接口 | `os/world.js:508` `saveAllPlayers()`；`api/gm.js saveAll` | 全量 |

★ 心跳每 5 s 只做 `heart_beat(dt)`（回血 / 战斗推进 / 房间心跳），**不碰数据库**
（`os/world.js:170-187`）。这就是"不是每秒写库"的**代码证据**。

### 28.3.1 序列化：手工拼 JS 字面量

`USER.prototype.getData()`（`os/char/user.js:275-330`）**不是** `JSON.stringify`，而是
`str.push(...)` 手工拼字符串：`{prop:[19 个裸数字],quit_room:"…",items:[…],stores:[…],books:[…],skills:{…},temp:{…},settings:{…}}`。
`prop` 用**位置数组**省 key（19 个数字占 ~100 B），代价是**永远不知道第 7 个数是什么**。

### 28.3.2 双写备份：存档与备份是**同一件事**

`WORLD.save()`（`os/world.js:232-254`）→ `db.saveRoles(roles)`（`os/util/data.js:23-41`），
后者一边 `await DB.saveRole(role)` 一边往 `data/<SERVERID>/bak/data<年-月-日-时>.js` **流式追加**。
所以 `data/100/bak/` 里**每小时一个文件**，`os/world.js:186` 那句日志「数据已备份」是名副其实的。
★ wushen 册 20 §20.7 第 4 条已经把它评为「✅ 值得抄，成本极低但能救命」——本册沿用这个判断。

### 28.3.3 ⚠️ 它踩的三个坑（实测支撑见 §28.4）

| # | 坑 | 位置 | 后果 |
|---|---|---|---|
| 1 | `saveRoles` **逐条 `await`**，**没有包在一个事务里** | `os/util/data.js:29-33` | N 个在线玩家 = N 次独立刷盘。200 人时 44.1 ms vs 单事务 19.4 ms |
| 2 | **没有设任何 pragma** ⇒ 用 SQLite 默认 `cache_size`（2 MB） | `data/db.js:32` / `:37` 的 `new Database(this.db_path)` —— ★ 该文件里 `pragma` / `PRAGMA` **零命中**（grep 判据） | 库内热数据一过 2 MB，**耗时跳到 3.3 s**（43×）。**wushen 自称支持 5100 用户，在它自己的容量下这一条必然踩中** |
| 3 | 备份文件**追加写进同一个小时文件**、无上限、无轮转 | `os/util/data.js:25-26` | 长期运行单调增长 |

★ 第 2 条是本轮**新发现**，wushen 册 20 与 21 册都没有记 —— 建议回填到 wushen 册 20 §20.3（属"审查待办"，编号顺延）。

## 28.4 ★★ 200 人规模的实测：写库压力到底多大

### 28.4.1 方法（可复现）

- 脚本与两轮结果：`D:/ts-mud/_bench-存档基准-2026-10-13/`（`README.md` 有一页摘要）
- 建 `players` 表（**照抄 wushen 的 DDL**：`data TEXT` 存整块存档），灌 N 行，然后整表 UPDATE 一轮
- 运行时：Node `22.22.2` + 内置 `node:sqlite`（`DatabaseSync`，**同步** API）
- ⚠️ **没有用 wushen 自带的 `better-sqlite3`**：它的原生模块与当前 Node ABI 不匹配（`ERR_DLOPEN_FAILED`）。
  两者同为同步 C 绑定、阻塞特征相同，**"逐条 vs 单事务"与"缓存悬崖"这两条量级结论可迁移**；
  **绝对毫秒数不要在别处引用**（换机器、换版本都会变）。
- 每角色按 **8 KB** 造存档（§28.4.4 说明这是**悲观值**），内容形状模仿 `getData()`（`prop:[…]` + 长 `items:[…]`）

### 28.4.2 实测 A：六种写法对照

**200 人 / 每角色 8 KB / 库内 1.56 MB**

| 写法 | 中位 | 最小 | 最大 |
|---|---|---|---|
| `delete`/`FULL` **逐条**（= wushen 现状） | **44.1 ms** | 42.0 ms | 68.3 ms |
| `delete`/`FULL` 单事务 | 19.4 ms | 17.8 ms | 30.1 ms |
| `wal`/`NORMAL` 逐条 | 18.8 ms | 17.1 ms | 22.4 ms |
| `wal`/`NORMAL` 单事务 | 17.2 ms | 15.3 ms | 18.3 ms |
| `wal`/`NORMAL` 单事务 + `cache_size` 32 MB | 18.5 ms | 14.6 ms | 20.4 ms |
| `delete`/`FULL` 单事务 + `cache_size` 32 MB | 20.2 ms | 18.4 ms | 22.8 ms |

**500 人 / 每角色 8 KB / 库内 3.91 MB**

| 写法 | 中位 |
|---|---|
| `delete`/`FULL` 逐条 | **3478.0 ms** |
| `delete`/`FULL` 单事务 | 3286.4 ms |
| `wal`/`NORMAL` 逐条 | 3328.3 ms |
| `wal`/`NORMAL` 单事务 | 3294.2 ms |
| **`wal`/`NORMAL` 单事务 + `cache_size` 32 MB** | **78.6 ms** |

★★ **500 人那组的读法是"五种写法全都一样慢"** —— 这说明**事务边界与 journal 模式都不是瓶颈**。
如果不测 500 人这一组，很容易得出一个**错的因果**：
"500 人慢是因为没包事务"（把 43× 的劣化归给一个只值 2× 的因素）。
**这就是为什么本册要跑第二组对照**。

### 28.4.3 ★★ 实测 B：**页缓存悬崖**

固定 500 人、只变每角色存档大小（`wal`/`NORMAL`/单事务，排除其它变量）：

| 每角色 | 库内总量 | 默认 2 MB 缓存 | 显式 32 MB 缓存 |
|---|---|---|---|
| 512 B | 0.24 MB | 76.9 ms | 46.1 ms |
| 1 KB | 0.49 MB | 53.2 ms | 53.6 ms |
| 2 KB | 0.98 MB | 61.2 ms | 63.4 ms |
| **4 KB** | **1.95 MB** | **3015.7 ms** ⚠️ | 71.4 ms |
| 8 KB | 3.91 MB | 3342.0 ms | 79.2 ms |
| 16 KB | 7.81 MB | 5147.4 ms | 155.8 ms |

★ 本表跑了两轮，**断崖位置与量级完全复现**（两轮的 4 KB 行分别是 2829.6 / 3015.7 ms）；
两端的 512 B 与 16 KB 行在两轮间有 1.5–2 倍抖动（那两档要么太小、要么单轮要写近 8 MB，
受磁盘抖动影响），**它们不是本结论的承重点**，承重点是"0.98 MB 仍快 / 1.95 MB 断崖"这条界线。

**判据**：断崖**精确落在库内热数据 ≈ `cache_size` 处**（1.95 MB 越过了 2 MB 线；
0.98 MB 还没越，仍是 61 ms）。显式调大缓存后断崖**消失**，耗时随数据量**线性**（46 → 156 ms）。

⇒ **容量规划不能对人数做线性外推**，必须先答一句"库内热数据有多少字节"。
`cache_size` 是一个**隐式配置陷阱**：不写就是 2 MB，**与你的数据量毫无关系**。

### 28.4.4 实测 C：真实存档有多大

| 来源 | 样本 | 结果 |
|---|---|---|
| `wushen/data/100/bak/*.js` | 35 条 | 中位 **364 B** / 最大 375 B / 平均 358 B |
| `wushen/data/database.db` → `players.data` | 2 条 | 235 B / 292 B |

⚠️ **这些全是开发期的空角色**（`skills:{}`、`stores:[]`、背包 3 件）。
同一个序列化形状下，真实活跃角色要多出：满背包（~30 件）、仓库（可达 100 件）、
数十个技能（`"skill":120` 每条约 25 B）、`titles` / `eq_groups` / `sk_groups`。
**乐观 1–2 KB、悲观 5–10 KB** ⇒ 本册所有推演**一律按 8 KB/角色**（悲观值）算。

### 28.4.5 结论：200 人**不在**压力区，但余量只有 ~20%

| 场景 | 库内总热数据 | 对 2 MB 线 |
|---|---|---|
| 200 人 × 364 B（实测中位） | **0.07 MB** | 3.5% — 极其安全 |
| 200 人 × 1 KB | 0.20 MB | 10% |
| 200 人 × 4 KB | 0.78 MB | 39% |
| 200 人 × 8 KB（悲观规划值） | **1.56 MB** | **78%** ⚠️ 只剩 22% 余量 |
| 200 人 × 12 KB | 2.34 MB | **越线 ⇒ 断崖** |

★★ **所以「200 人」是一个"舒服但薄"的区间**：
按实测中位数它只用掉 3.5%，按悲观值用掉 78% —— **同一句"200 人没问题"，两种参数下差 20 倍**。
这正是**必须显式设 `cache_size`** 的理由：它把这条悬崖**直接搬走**，
以后的余量问题从"预算"变成"没有的事"。

**什么情况下才会真的痛？**（按实测反推）

| 条件 | 会不会痛 |
|---|---|
| 200 人在线、每角色 ≤10 KB | ❌ 不痛（≤45 ms） |
| 200 人 × 每角色 >12 KB | ⚠️ 只在**不设 pragma** 时痛（断崖）；设了就 ≤90 ms |
| ⚠️ 要支持 500+ 人 | ✅ **必修 pragma**，否则每次全量存档卡 3.3 s |
| 「每人每秒各写 1 次」= 200 条/秒 | ⚠️ 单条 183 µs ⇒ 约 **37 ms/秒**（3.7%）。**技术上可行**，但见 §28.6.3 的成本 |

### 28.4.6 一条方法论备注

A 组的 200 人与 500 人**各自独立复现了两轮**，数字一致（44.6/44.1 ms；3.3 s / 3.3 s）
⇒ 结论稳定，不是一次抖动。
另：**同一份脚本在 `node | grep` 下会被 SIGPIPE 掐断**（本项目已记过的坑）——一律**重定向到文件再读**。

### 28.5.5 读档契约：**分级**（E3 裁定，2026-10-15）

**取证**：`tests/engine-skill.test.ts` 的 E3 组（7 条）· `tests/engine-temp.test.ts` ·
`gate:mutation` 的 **SKL.11 / SKL.12** · 完整实现见 `server/engine/load-report.ts` 头注释。

**为什么要有"统一契约"**：props / temp / skill 三处各有一对「取快照 / 装回去」，
而"读档要不要拒绝、拒到哪一档"**只有一种答案** —— 三处各写一份必然分家
（E3 的成因正是三处口径各写各的）。于是把**报告形状 + 两条判定原语**抽到一处。

三条规则：

1. **结构性损坏 ⇒ 抛异常**。判据是**容器种类**：该给对象的给了 `null` / 数组 / 标量，
   该给数组的给了非数组。为什么必须抛而不是"静默装 0 条"：`typeof [] === 'object'`，
   空数组会"成功地装进 0 条且不报错"，调用方**永远发现不了自己传错了形状**。
2. **条目级异常 ⇒ 丢该条 + 记账**：不认识的键 / 非法值 / 非法装配槽。
   **为什么不在这里整包抛**：存档里多出一个"新版本才认识的键"是**版本回滚的正常场景** ——
   整包抛会让回滚后的**全体**角色打不开（不可逆，且玩家只会认为"服务器坏了"）；
   丢一条只是少一个值（可逆、可补）。
   ★ 顶层"不认识的字段"同样属**条目级**，理由同上（回滚安全的那一种读法）。
3. **调用方义务（T12 落实）**：`rejected` **非空即视为读档失败** —— 至少记审计日志 +
   拒绝登录。缺了这一条，规则 2 就退化成"静默放行"，那正是 wushen 的形态
   （`os/char/user.js:188` 把存档字段**直接赋给实例**，类型与范围一概不问）。

#### E3 具体修的是什么

26 册 §35 记的是「**改过的存档可把基本技能装进武功槽**」：`enable()` 有三道准入
（槽名合法 / `type === SKILL` 才可装配 / 槽在 `can_enables` 里），而 `load()` 此前
**一道都不判** —— 只做 `isEnableSlot` 兜底，把不合法一律降级成 `null`。

★ **关键认识**：`load` **就是绕过 `learn()` / `enable()` 的那条路**，
所以"校验写在 `enable()` 里"并不覆盖它 —— **校验必须与数据入口同处**。

现在 `load()` 逐条走同一套判据，不过的那条**只丢槽**（技能保留、`enabled = null`）+ 记账：
- 非法的是**装配**这件事，技能本身可能是真学会的 ⇒ 角色不会因一行脏数据失忆；
- 丢槽 ⇒ 篡改者拿不到任何东西（槽没被占、属性账也没它）；
- 少装的一个槽**必定进 `rejected`**，所以漏不掉（这正是规则 3 的作用）。

★ 两处**刻意宽松**、不记账（都要能说出理由）：
- `enabled` 缺字段 / 为 `null` ⇒ 当"未装配"，**不记账**。与 `loadProps()` 对
  "字段缺失 = 该字段没有内容"的取向一致；且缺 `enabled` 取的是**最保守**的值，
  不构成任何越权路径。
- `temp` **不做键白名单**（它就是自由键值袋：BUFF / 冷却 / 任务进度），
  只判"键名非空"与"数值有限"。

### 28.5.5 依赖现状（影响选型）

`newmud/package.json` 的运行依赖**只有 `ws` + `zod`**；全仓 grep `sqlite|better-sqlite|DatabaseSync`
在源码里**零命中** ⇒ **存档层还没有任何数据库依赖**。

| 候选 | 优点 | 代价 |
|---|---|---|
| **`node:sqlite`（内置）** | **零依赖**；`engines` 已经是 `>=22.15.0`（本机 22.22.2 可用）；无原生编译、**无 ABI 问题** | 标记为 **experimental**（API 可能变）；需要在本项目里钉住版本 |
| `better-sqlite3`（wushen 同款） | 成熟、wushen 已用 | **原生模块 + ABI 敏感**（本轮实测就踩到 `ERR_DLOPEN_FAILED`）；需要编译工具链 |

★ 本轮的踩坑经历本身就是一条选型论据：**原生模块会随 Node 版本失效**，
而这个项目的 `engines` 允许 `>=22.15.0`（即允许漂移）—— 对这种"小项目、要长期跑"的场景，
**零依赖的内置模块风险更低**。⚠️ 但 `experimental` 是新风险，**要在 T12 用一条闸门/断言把用法钉住**
（例如"只允许 `DatabaseSync` + 白名单 pragma"）。

## 28.6 方案对比：哪个更安全稳定

### 28.6.1 候选 A · 登出写 + 每小时全量（= wushen 同款）

| 维度 | 评估 |
|---|---|
| 崩溃窗口 | 最长 **1 小时**（心跳存档之间崩） |
| 写放大 | 全量 = **所有在线角色**都写，哪怕只动过一个人 |
| 实现复杂度 | **最低**（已有一小时常量与备份目录） |
| 200 人实测 | 44.1 ms（逐条）/ 19.4 ms（单事务） |
| 风险 | ★ 若照抄 wushen 而**不设 pragma**，规模一涨就是 3.3 s 的**同步阻塞**（§28.4.3） |

### 28.6.2 候选 B · A + 脏标记 + 单事务 + 显式 pragma + 备份轮转（★ 推荐）

| 维度 | 评估 |
|---|---|
| 崩溃窗口 | 同 A（1 小时），**但窗口的代价可评估** |
| 写放大 | **只写脏角色**；`SAVE_NUMPROP` 那类"只改了一个人"的场景从 N 条降到 1 条 |
| 实现复杂度 | 低：一个 `Set<roleId>` 标脏 + 一个事务 + 三条 pragma |
| 200 人实测 | **全量 17–20 ms**；真实常态（多数人没动）**远低于此** |
| 风险 | 脏标记漏标 ⇒ **静默丢数据**。**必须配一条断言**（§28.8 第 3 条） |

### 28.6.3 候选 C · 关键事件即写 + 周期兜底

| 维度 | 评估 |
|---|---|
| 崩溃窗口 | **几秒**（最好的） |
| 写放大 | 每次升级/交易/拾取都写 ⇒ **业务路径上到处是 IO** |
| 200 人实测推演 | 单条 183 µs；200 人每秒各 1 次 ≈ **37 ms/秒**（3.7%）—— 数字上**不贵** |
| 实现复杂度 | **高**：事务与业务逻辑交缠；"哪些事件算关键"要逐个定；每条路径都要单测 |
| 真风险 | ★ 不是性能，是**正确性**：写点分散 ⇒ 必然有几条路径**漏了写**，而漏写是**静默**的 |

### 28.6.4 ★ 推荐：候选 B。理由与配套

**为什么不是 A**：A 的实测耗时（44 ms）其实也没问题，**但 A 有三个已知坑（§28.3.3），B 就是 A 的针对性修正**——
脏标记（省写放大）、单事务（省刷盘）、显式 pragma（**搬走悬崖**）、备份轮转（防单调增长）。
**A 与 B 的实现量差得很少，但 B 把三条已知缺陷都关掉了。**

**为什么不是 C**：C 的收益是把崩溃窗口从 1 小时降到几秒，代价是**在每条业务路径上撒写点**。
对 MUD 来说，1 小时窗口丢的是**慢变量**（经验、等级、背包），
而不是"刚才那一刀"—— 损失量级与实现风险**不成比例**。
★ 而且用户担心的正是"高频写库"，**C 恰好是唯一会撞上那个担心的方案**：
它把"每分钟 0 次写"变成"每分钟几百次写"，而换来的东西很有限。

**推荐的完整组合（T12 照此实现）**：

```
登出写（单角色）
  + 心跳周期全量写（AUTOSAVE_INTERVAL_MS = 1 h，脏角色优先）
  + 脏标记：谁被改过写谁（含"只改了一格属性"）
  + 单事务批量：一轮的 N 条 UPDATE 包在一个 BEGIN/COMMIT 里
  + 显式 pragma：journal_mode=WAL、synchronous=NORMAL、
                 cache_size = 热数据上限 × 2（★ 见 §28.7.2，这条最关键）
  + 备份：写前备份（像 wushen 那样"存档与备份同一件事"）+ 按小时文件轮转上限
```

**如果将来真要"秒级窗口"**：升级路径是 **B → B+C 的增量**，
即**只对少数关键事件**（升级 / 交易 / 拾取稀有物）即写，其余仍走周期 —— 而不是全量改 C。

## 28.7 落地设计（T12 照着做）

### 28.7.1 表结构

**不要照抄 wushen 的整块字符串**（wushen 册 20 §20.7 第 1 条已判「❌ 必须改」）：

| 层级 | 建议 | 理由 |
|---|---|---|
| `players` | `id / userid / name / title / level / create_time / update_time` | 与 wushen 一致，便于对账 |
| 存档体 | **拆成功能性 JSON 列**：`props`(prop+ext) / `items` / `skills` / `temp` / `settings` / `eq` / `misc` | 一个块坏掉不至于整个角色报废；也便于只写变了的块 |
| `players_bak` | 同构 + 归档时间 | 删号归档（wushen 已有此设计） |
| `world_kv` | `key TEXT PRIMARY KEY, value TEXT, expire_at` | 对应 `WORLD.DATA`（榜单 / 广播 / 帮派 / 拍卖行） |

★ 但**不要一上来就上关系化拆表**（背包一行一件）：200 人规模下**收益为负** ——
它把"一次 UPDATE"变成"一次删+插 N 行"，写放大反而更大。
**先按"列"拆到 JSON 粒度，够用。**

### 28.7.2 ★★ pragma 清单（本册最可操作的一条）

```sql
PRAGMA journal_mode = WAL;       -- 读写不互相阻塞（逐条时 44.1 → 18.8 ms）
PRAGMA synchronous  = NORMAL;    -- WAL 下的推荐档；FULL 会让每条都刷盘
PRAGMA cache_size   = -32768;    -- ★ 单位 KiB ⇒ 32 MB。默认 -2000(2MB) 是断崖的成因
PRAGMA busy_timeout = 5000;      -- 多进程/多连接时的等待，而不是直接 SQLITE_BUSY
```

★★ `cache_size` 必须是**显式、且由数据量反推**的：`ceil(预计热数据量 × 2)`。
按 §28.4.5 的悲观值（200 × 8 KB = 1.56 MB）算，32 MB 有 20 倍余量，**成本可忽略**。
**不写这一行，就是继承了那个 43× 的悬崖** —— 这条要写进 T12 的验收标准。

### 28.7.3 保存流水线

```
① 业务改动 → 只改内存 + 往 dirty 集合里记一个 roleId（★ 不碰 IO）
② 心跳每 5 s：若 dirty 非空 → 取本轮要写的角色（可分批错峰，见下）
③    BEGIN
④      for each 角色：snapshotProps / snapshotTemp / skill.snapshot … → UPDATE
⑤    COMMIT                      ← 一轮一条事务
⑥  写前备份：先把旧值/整块落到 backup/<年-月-日-时>.js（追加），再落库
```

- **错峰**（可选，200 人下不必）：把 dirty 摊到 K 个心跳周期里，每跳写 `dirty.size / K` 个。
  实测 200 人全量只要 20 ms，**这个优化在当前规模下是过度设计** —— 记在这里是为了"规模变了有预案"。
- **失败处理**：事务失败 ⇒ 该轮不 `clear` dirty（下一轮重试），并把异常**打到日志**，
  **绝不** `catch(e){}` 静默吞掉（wushen `os/world.js:372` 的 `logGM` 就是这么废掉的 —— wushen 册 20 §20.5 记为缺陷）。

### 28.7.4 崩溃窗口与恢复

| 崩溃点 | 丢什么 | 恢复 |
|---|---|---|
| 两次存档之间 | 自上轮存档以来的**慢变量**变化（经验/等级/背包） | 读上一份备份或库里的旧值 |
| 存档**进行中** | 无（单事务 ⇒ 要么整轮生效、要么整轮回滚） | 直接读库 |
| 备份文件写到一半 | 无（追加流 + 下次覆盖） | 忽略残缺尾行 |

★ **"单事务"在这里的收益不只是快，而是"一轮存档是原子的"** ——
逐条写时崩在中间会得到"一半人新、一半人旧"的**混合态**，而单事务不会。**这条比 20 ms 更值钱。**

### 28.7.5 与现有接缝的接线点

| 现有成员 | T12 里怎么用 |
|---|---|
| `propHolder` → `snapshotProps` / `loadProps` | 存档体 `props` 列的两端 |
| `Character.loadProps()` 后自动 `recount()` | **不要绕过** —— 读档后必须重算派生值 |
| `temp.snapshotTemp(now)` | 存档体 `temp` 列；**过期项天然不写** |
| `temp.loadTemp(raw, now)` | 读档；语义是"合并"，需要整体替换时先清 |
| `skill.snapshot()` / `load()` | 存档体 `skills` 列 |
| `oidSpace.restore()` | 读档后把实体 id 空间对齐（⚠️ 现状：`logout()` **没有** `release()`，见 `docs/26` §14.6 第 3 条） |
| `AUTOSAVE_INTERVAL_MS` | ②的周期（当前**零消费者**，T12 接上） |
| `backupDir()` | ⑥的目录（当前**零消费者**，T12 接上） |

## 28.8 验收标准（写成可跑的断言）

| # | 断言 | 为什么必须有 |
|---|---|---|
| 1 | **pragma 生效且完整**：连上后读回 `journal_mode` / `synchronous` / `cache_size`，逐个等于期望值 | ★ `cache_size` 不设 = 继承 43× 悬崖；这条**必须是断言**，不能靠代码评审 |
| 2 | **一轮存档是原子的**：事务中途抛错 ⇒ 库里**一行都没变**（不是"变了一半"） | §28.7.4；"单事务"的真正价值 |
| 3 | **脏标记不漏**：改一条属性 / 加一件物品 / 升一级，各自都让角色进 dirty | ★ 漏标 = **静默丢数据**；这是候选 B 的唯一新风险 |
| 4 | **读档后派生值正确**：`loadProps` 之后 `maxHp` 等于按 `formula.ts` 重算的值（不是存档里的数） | `session.ts:92` 已定的口径；防止有人把 `max_hp` 从存档直接装回去 |
| 5 | **过期临时状态不复活**：写档时已过期的 temp 项，读档后**查不到** | `temp.ts:165` 的契约 |
| 6 | **脏数据不进屋**：`loadProps` / `loadTemp` 收到数组 / 非数值 ⇒ 按现状**拒收并记 `rejected`**，不抛到调用栈外 | `props.ts:250-256` 的既有取向 |
| 7 | **崩在两次存档之间可恢复**：模拟"库是旧的、备份是新的"，恢复后角色可登录且属性自洽 | §28.7.4 |
| 8 | **备份文件有上限**：连续 N 小时后备份目录不单调增长（轮转策略生效） | wushen 的坑 3 |
