## 1. 项目总览与目录结构

### 1.1 定位与技术栈

这是一个**服务端权威 + Web 前端**的武侠文字 MUD（Multi-User Dungeon）。

| 维度 | 技术 |
| --- | --- |
| 运行环境 | Node.js（CommonJS，服务端大量使用 `vm.compileFunction`） |
| 数据库 | SQLite（`better-sqlite3`，见 `data/db.js`） |
| Web 服务 | Express（`web.js`），静态目录 `www/`，JSON API `/api/:class/:method` |
| 游戏通信 | **自研 WebSocket 服务器**（`os/net-ws.js`，三种协议变体） |
| 前端 | 原生 JS + jQuery + Vite 构建（`src/` → `www/`） |
| 配置 | `config.js` 读取 `.env`（`MD5_PREFIX` 等） |

### 1.2 双进程结构

```text
┌────────────────────────┐        ┌─────────────────────────────┐
│  main.js  游戏主服      │        │  web.js  站点/登录/GM 入口   │
│  - 装载世界(world/)     │        │  - Express 静态页 + /api    │
│  - 监听 WS 端口(31300)  │◀──────▶│  - 代理 /api/gm → 8090       │
│  - 角色/战斗/心跳       │        │  - 用户注册/登录/改密        │
│  - 读写 SQLite          │        │  - 读写同一 SQLite           │
└────────────────────────┘        └─────────────────────────────┘
        ▲                                       ▲
        │ WebSocket (自研协议)                    │ HTTP JSON
        └───────────────────┬───────────────────┘
                            ▼
                    src/ 前端（浏览器）
```

- **游戏服务器**入口：`main.js`（加载 `os/`，装载 `world/`，启动 WS 监听）。
- **站点服务器**入口：`web.js`（Express，端口由 `WEB_PORT` 决定，默认 8088）。
- 两个进程共用同一个 SQLite 数据库文件。

## 2. 核心框架层：自定义对象系统

**文件：[os/base.js](os/base.js)**

这是理解全项目的钥匙。它没有用 ES6 `class`，而是自定义了一套"文件即对象"的机制。

### 2.1 关键成员

| 成员 | 位置 | 作用 |
| --- | --- | --- |
| `BASE.prototype.set(obj)` | `os/base.js:12` | 批量把属性复制到 `this` |
| `BASE.prototype.inherits(ctor)` | `os/base.js:26` | **核心继承**：让子类原型指向父类实例，并调用父构造函数 |
| `BASE.prototype.select(func,...)` | `os/base.js:104` | `setTimeout` 包装（带 `this` 绑定） |
| `BASE.prototype.setInterval(fn,time)` | `os/base.js:113` | 定时器包装，句柄存在实例上便于清理 |
| `BASE.ITEMS` / `vm.compileFunction` | `os/base.js:124` | 读取 `.js` 文件文本 → 编译成函数（"文件即对象模板"） |
| `BASE.CREATE` | `os/base.js:124+` | 从路径创建对象（读文件 + 编译 + 缓存） |
| `BASE.NEW` | `os/base.js:124+` | 实例化对象并调用其 `create` |
| `BASE.UPDATE` | `os/base.js:124+` | 热更新对象定义 |

### 2.2 继承机制怎么工作

```js
BASE.prototype.inherits = function (ctor, ...args) {
    // 伪代码：把父类实例作为子类原型，并执行父类构造
    this.__proto__ = new ctor();      // 关键点：原型链挂接
    ctor.apply(this, args);           // 执行父构造函数初始化
    ...
};
```

- 子类写法：`CHARACTER.inherits(ITEM)`、`USER.inherits(CHARACTER)`、`EQUIPMENT.inherits(OBJ)`。
- **含义**：`os/` 下的每个 `.js` 文件（`character.js`、`equipment.js`…）以及 `world/` 下的每个内容文件，本质都是"**一段会被编译并 `apply` 到某个基类上的配置脚本**"。
- 内容文件（如 `world/family/wudang.js`）开头 `this.inherits(FAMILY);`，随后 `this.id = "WUDANG"` 等，就是在向对象实例挂属性/方法。

> 因为"文件即对象模板"，`world/` 内容层与 `os/` 引擎层使用**完全相同的语法**：`this.xxx = ...`、`this.func = function(){}`。这也是热更新能统一处理它们的基础。

### 2.3 全局命名空间

引擎通过全局变量把各类注入到内容脚本的运行环境（内容脚本可直接用 `WORLD`/`CHARACTER`/`ROOM`/`SKILL`/`FAMILY`/`COMMAND` 等，无需 `require`）。热更新沙盒即显式列举了这些全局对象（`os/util/hotload.js:37-55`）。

## 4. 网络通信层

### 4.1 自研 WebSocket 服务器

**文件：[os/net-ws.js](os/net-ws.js)**

这不是 `ws` 库，而是**手写的 WebSocket 协议实现**，支持三种变体：

| 变体 | 触发条件 | 位置 |
| --- | --- | --- |
| `var1` | 报文头含 `Sec-WebSocket-Key`（RFC6455） | `os/net-ws.js:73` |
| `var2` | 报文头含 `Sec-WebSocket-Key1`（旧 hixie-76） | `os/net-ws.js:164` |
| `tcp` | 两者都没有（裸 TCP 长度前缀协议） | `os/net-ws.js:231` |

要点：
- 连接建立：`listen()` → `net/tls.createServer` → `onClientConnect`（`os/net-ws.js:40`）。
- 首个 `data` 事件若未握手，则解析 HTTP 头并 `handShake`。
- `var1` 的帧解析在 `readData`（`os/net-ws.js:95`）：解析 FIN/opcode/mask/length，按 4 字节掩码 XOR 解码，`Text` 帧交给 `server.onReceive`。
- 发送：`sendData` 支持 3 种长度编码（126 / 65536 边界）。

### 4.2 登录态与角色加载

**文件：[os/login.js](os/login.js)（`USERLOGIN`）**

- `check_session(user, str)`（`world/extends/login.js` 覆写）：解析首包 `"user token [pid] [sid]"`，`encryptUser` 校验后写出 `user.userid/password/user_level`，随后走 `load_roles` 或 `wait_login`。
- `load_roles`：查库得到角色列表并下发 `{type:'roles',roles:[...]}`。
- `wait_login`：登录后进入 `wait_input` 状态，等待"选角/进入游戏"指令。

### 4.3 前端 WebSocket 客户端

**文件：[src/client.js](src/client.js)**

- `connectServer(server, pid)`：构造 `WSClient`，绑定 `OnConnect/OnClose/OnError/OnData/OnMessage`。
- `OnReceived`：**收到以 `{`/`[` 开头的报文用 `new Function("return "+data)` 解析为对象**，否则当文本消息。
- `SendCommand(cmd)`：未连接时记录 `LastCommand` 并触发重连，连接后重放。

> 客户端 `WSClient.Connect` 里计算了 `var pol = location.protocol == "http:" ? "ws" : "wss";`，但实际使用的是**硬编码 `'ws://'`**（见问题清单）。

## 16. 问题与风险清单（分级）

> 级别：**P0 严重**（安全/可被利用或导致崩溃）、**P1 重要**（功能正确性/稳定性）、**P2 一般**（可维护性/健壮性）。

### P0（严重）

#### P0-1. 开发环境下的 GM 接口鉴权绕过
`api/gm.js:529` 中 `getPlayerFullAttrs` 在 `process.env.NODE_ENV === 'development'` 时**完全跳过 `checkGM()`**，任何人可请求 `/api/gm/player-local/:id/full` 获取在线玩家全量属性（含 prop 明细）。
- 风险：只要线上误配 `NODE_ENV=development`，即泄露数据。建议移除该分支，或用独立的内网开关 + 来源校验。

#### P0-2. 热更新 = 任意代码执行（含路径穿越）
- `api/gm.js:501` `const fullPath = basePath + name;` 中 `name` 来自请求体，未做规范化 → 可用 `..\..\` 逃逸到任意目录。
- `os/util/hotload.js:58-60` 用 `vm.Script` 执行任意 JS，沙盒中**注入了 `require`**（`hotload.js:38`），等同于 RCE。
- `os/char/character.js:895` 游戏内 GM 指令 `hotload` 同样 `basePath + name`。
- `world/cmd/admin/call.js:11` 使用 `new Function(arg)` 执行任意代码。
- 风险：若 GM 账号或 cookie 泄露，攻击者可上传/执行任意脚本。建议：白名单目录 + 路径规范化校验 + 去掉沙盒中的 `require`。

#### P0-3. CORS 通配 + 允许携带凭证
`web.js:32-35` 同时设置 `Access-Control-Allow-Origin: *` 与 `Access-Control-Allow-Credentials: true`。该组合本身是无效/不安全的（浏览器会拒绝 `*` 配 credentials），且若后续改为回显 Origin，则等于允许任意站点带 Cookie 调接口。建议改为**固定白名单 Origin**。

#### P0-4. 弱口令哈希与默认管理员
- 密码用 **MD5 + 固定前缀**（`api/base.js:83`、`data/db.js:194`），无逐用户盐，易被彩虹表/撞库。
- 默认管理员硬编码口令 `123456`（`data/db.js:191`）。
- 建议改用 `bcrypt/scrypt/argon2`，并强制首次改密。

### P1（重要）

#### P1-1. 热更新 `reloadSkill` 变量作用域错误（必然抛异常）
`os/util/hotload.js:151` 在 `if (global.WORLD && WORLD.USERS) { ... }` **块内**声明 `let updatedCount = 0;`，但在块**外**的 `return { updatedPlayers: updatedCount || 0 }`（`hotload.js:171`）引用它 → `ReferenceError`。即**只要热更新技能就会报错**。修复：把 `let updatedCount = 0;` 提到 `if` 之前。

#### P1-2. 本地 GM 降级路由被代理中间件屏蔽（实际不可用）
`web.js:145` 注册的 `app.use('/api/gm', proxy)` 会拦截**所有** `/api/gm/*` 请求并转发到 8090；而"降级"路由 `web.js:192-213`（`/api/gm/status-local` 等）注册在其**之后**，因此永远无法被命中。注释宣称的"8090 不可用时使用"不成立。修复：调整注册顺序，或用更精确的路径前缀区分。

#### P1-3. 前端解析服务端报文使用 `new Function`（客户端 RCE 面）
`src/client.js:169`：`new Function("return " + data + ";")()`（另有 `src/utils/util.js:126/130`）。若服务端被入侵或遭中间人篡改，报文可注入任意 JS 在**玩家浏览器**执行。建议改为 `JSON.parse`（或严格白名单解析）。

#### P1-4. 前端硬编码 `ws://`（HTTPS 页面下必然失败）
`src/client.js:154-155` 计算了 `pol = (http? ws : wss)` **却未使用**，实际 `new WebSocket('ws://' + this.IP + ':' + this.Port)`。当页面为 HTTPS 时会出现混合内容被拦截 / 明文传输。修复：`new WebSocket(pol + '://' + ...)`。

#### P1-5. 自研 WebSocket 帧处理不完整
`os/net-ws.js:95` 的 `readData`：
- **不处理分片/续帧**（`FrameTypes.Continuation = 0` 在 switch 中落入 `default` 被丢弃，`net-ws.js:117-134`）→ 大消息或分片帧会丢失。
- `length == 127` 时直接 `return`（`net-ws.js:107-110`）→ 超长帧被静默丢弃。
- 未校验客户端必须使用 mask、未限制单帧/累积长度 → 潜在 DoS。
- 建议：改用成熟的 `ws` 库，或在自研实现中补齐续帧、长度上限与控制帧处理。

#### P1-6. 玩家名/房间描述等直接拼进 HTML（前端 XSS）
`src/process.js:265-296` `create_roomitem` 用字符串拼接 `item.name` 等；`src/process.js:300` `$(".room_desc").html(room.desc)`；`ReceiveMessage` 把服务端文本直接 `push` 进 DOM。若玩家名/自定义文本含 HTML/脚本，可能造成 XSS。建议对非颜色标签内容做转义（保留 `<>` 颜色标签白名单）。

#### P1-7. 跨服跳转标志位读写对象不一致
`src/process.js:103` 设置的是实例属性 `GameClient.ChangeServer = true;`，而 `src/client.js:41` 的 `OnClose` 读取的是**模块级变量** `ChangeServer`（未导出）。跨服时该"抑制断线处理"的意图不会生效，可能导致跨服后错误触发 `Process.clear()` 与"连接中断"提示。

### P2（一般）

#### P2-1. 大量可维护性问题
- **命名**：`NPC_STROE/OBJ_STROE` 拼写错误（应为 `STORE`），全项目沿用。
- **重复/死代码**：`world/extends/world.js:37-38` 声明了 `illegalUARegex`、`Origins` 却从未使用；`check_connect`（`world/extends/world.js:39`）恒返回 `true`，与其存在的意义（UA/来源过滤）不符。
- `os/data.js` 的 `temp_replacer`（`os/data.js:14`）为空实现且未被使用；`save_temp` 拼接 `'temp:'` 不带逗号，依赖 `on_save` 自行补逗号，格式脆弱。

#### P2-2. 潜在 SQL 注入面（当前被白名单掩盖）
`data/sql.js:18-32` 的 `getUser/getUsers` 采用 `sql += " where " + cond` 的**字符串拼接**。当前调用方（如 `api/game.js:18-30` 的 `search_role`）都以 `ALLOW_TYPES` 白名单约束 `cond`，暂时安全；但该模式一旦被新调用方传入不可信字符串即成注入。建议统一改为**结构化条件对象**或用固定参数化模板。

#### P2-3. 异常处理薄弱
全项目 `catch` 多为空实现或只 `console.error`（如 `api/gm.js:545` 的 `catch(e){}`），异步失败容易被吞掉；`data/util/data.js` 的备份流缺少完整错误兜底。建议关键路径补日志与降级。

#### P2-4. 定时器/监听清理
- `src/process.js:495` 的 `setInterval(Process.updatestate)` 依赖状态切换清理，若状态异常可能泄漏。
- `process.js:38-61` 的 `mousemove/mouseup` 在 `window` 上挂/解绑，注意确保成对。
- 倒计时/动作按钮的 `clearInterval` 需保证在切界面时全部清理（`Process.itemremove` 有清理，但列表重建路径需复核）。

#### P2-5. 自研继承机制的可维护性
基于 `__proto__` + `apply` 的继承（`os/base.js:26`）OK 但非标准，调试/工具链不友好；`vm.compileFunction` 动态编译使静态分析困难（本项目的"文件即对象"能力正依赖它，属于**设计取舍**，非 bug）。建议至少在文档/注释中固化加载顺序与全局对象清单。

## 17. 优化建议与优先级

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| 1 | 移除 `getPlayerFullAttrs` 的开发态鉴权绕过 | 直接数据泄露（P0-1） |
| 2 | 热更新路径规范化白名单 + 沙盒去掉 `require` | 直接 RCE（P0-2） |
| 3 | CORS 改固定 Origin 白名单 | 横向伪造请求（P0-3） |
| 4 | 密码改强哈希 + 去默认口令 | 账号安全（P0-4） |
| 5 | 修 `reloadSkill` 作用域 bug | 热更新技能必报错（P1-1） |
| 6 | 修 GM 降级路由注册顺序 | 降级方案失效（P1-2） |
| 7 | 前端报文改 `JSON.parse`、WS 协议改 `pol` | 客户端 RCE / HTTPS 失败（P1-3、P1-4） |
| 8 | 补齐 WS 续帧/长度限制（或换 `ws` 库） | 稳定性/DoS（P1-5） |
| 9 | 前端 HTML 转义 | XSS（P1-6） |
| 10 | 命名/死代码/异常处理清理 | 长期可维护性（P2） |
