## 1. 一句话拓扑

**单进程**：一个 Node 进程同时提供**静态资源**与 **WebSocket**，**同一个端口**。

```
浏览器 ──(http, 同端口)──> 静态资源(dist/web/)
       ──(ws,  同端口 /ws)> WebSocket 升级 ──> hub ──> session ──> 引擎
```

★ **为什么必须同端口**：前端默认连接地址是**同源**的（`ws://${location.host}/ws`）。
拆成两个端口的表现是"**页面能开、点了进不去**"（`tools/start.mjs` 与 `launcher.test.ts` 都把这条钉住）。
★ **WebSocket 端点是 `/ws`**（不是根路径）：服务端单点定义在 `server/net/ws-server.ts` 的 `WS_PATH`；
  前端与 `cli.ts` 各持一份字面量（不共享模块），**改动时三处一起看**。
★ **对外发布的标准拓扑**：本进程**只监听 loopback**，前面加**反向代理做 TLS 终止**
  （见 §3）—— 因为本进程**不实现 TLS**。

## 2. 运行参数全表

启动：`npm start`（`prestart` 自动先 `npm run build:web`）。给 npm script 传参必须用 `--` 隔开：

```bash
npm start -- --port 9000 --host 0.0.0.0
npm start -- --help          # 打印下表
```

| 参数 | 作用 | 缺省 | 校验范围 |
|---|---|---|---|
| `--port <n>` | 监听端口（静态 + WS 同端口） | `8123` | `0`–`65535`（`0` = 系统分配） |
| `--host <addr>` | **监听地址** | `127.0.0.1` | 要对外**必须显式**给（如 `0.0.0.0`） |
| `--no-web` | 只提供 WebSocket，不发前端 | 关 | —— |
| `--web-root <dir>` | 前端产物目录 | `<项目根>/dist/web` | —— |
| `--max-connections <n>` | **全局**同时在线连接上限 | `MAX_CONNECTIONS`(200) | `1`–`100000` |
| `--max-connections-per-ip <n>` | **同一地址**连接上限 | `MAX_CONNECTIONS_PER_IP`(8) | `1`–`100000` |
| `-h`, `--help` | 打印 usage 退出 | —— | —— |

★ 缺省值来自 `server/cli.ts`（`DEFAULT_PORT` 等）与 `shared/constants.ts`（`MAX_CONNECTIONS*`）——
  **单源真相**，本表只是搬运，改常量这里跟着改（没有闸门守这张表，属人工纪律）。
★ `--host` 缺省 **`127.0.0.1`** 是**有意的安全缺省**：默认只本机可访问。
  要对外才显式改 —— 而"显式改"的那一刻，就是**必须走一遍 §4 安全清单**的时刻。

`npm start` 只在启动时构建一次前端；**边改边看**要用 `npm run dev`

## 3. 对外发布（反向代理 + TLS）

本进程**不做 TLS** ⇒ WebSocket 明文（`ws://`）= **token 与全部对话明文**。
对外部署**必须**在反向代理处终止 TLS，把 `wss://` 转成 loopback 上的 `ws://`。

**最小 Nginx 骨架**（要点：升级头 + 读超时 ≥ 空闲心跳间隔 + 只代理到 loopback）：

```nginx
server {
    listen 443 ssl;
    server_name mud.example.com;

    ssl_certificate     /etc/letsencrypt/live/mud.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mud.example.com/privkey.pem;

    # 静态资源与页面
    location / {
        proxy_pass http://127.0.0.1:8123;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket（端点是 /ws，不是根）
    location /ws {
        proxy_pass http://127.0.0.1:8123;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 3600s;   # ★ 必须 ≥ 服务的空闲心跳间隔，否则长挂机会被代理掐断
    }
}
```

★ **WebSocket 的两个必备头**（`Upgrade` / `Connection: upgrade`）漏一个 = 升级失败 =
  浏览器那句"页面能开、点了进不去"；`proxy_read_timeout` 漏了 = 玩家挂机一会儿就被断开。
★ **前端走相对地址**（`ws://${location.host}/ws`），所以 TLS 之后**前端零改动**就变成 `wss://`。

### 3.1 ★★ 反向代理会压平 `remoteAddress`（**per-IP 限流的已知退化**）

服务端按 `req.socket.remoteAddress` 取客户端地址做 **per-IP 连接上限**。
**一旦加了反向代理，所有连接对服务端都来自代理的地址** ⇒ `--max-connections-per-ip`
**退化成"对所有客户端合计生效"**（8 个连接就把所有人挡在门外）。

- 当前**未读取** `X-Forwarded-For`（代理头可被伪造，信任它要配套"可信代理层数"逻辑）。
- ⇒ **现状**：上代理后要么把 `--max-connections-per-ip` 调大，要么等**账号/暴露批次（T12）**
  落地"可信代理 + 真实 IP 解析"。**这是有意的未做项，不是 bug**，记在此处免得部署时踩。
- ★ 同理，`--host` 后**本进程自己的 Origin 校验**（`isSameOriginRequest`）仍按 Host 判定 ——
  代理要**透传 `Host`**（上面的骨架里已带），否则合法请求会被判成跨源。

## 4. 对外发布前的**安全清单**（逐条勾）

| # | 项 | 现状 | 依据 |
|---|---|---|---|
| 1 | **TLS 终止**（`wss://`） | ⛔ **未做**（本进程无 TLS；靠代理，见 §3） | 26 册 §4（安全前置） |
| 2 | **安全响应头** | ✅ **已发**（L1，静态服务四段响应统一带） | `server/static.ts#SECURITY_HEADERS`、测试 `static-web.test.ts` |
| 3 | 监听地址**不裸奔** | ✅ 缺省 loopback；对外才显式 `--host` | `cli.ts` / `ws-server.ts` |
| 4 | WS 只认 **`/ws`** | ✅ 非该路径不升级 | `ws-server.ts#WS_PATH` |
| 5 | **同源校验**（防跨站 WS 连接） | ✅ `isSameOriginRequest` | 26 册 §30.2（N2） |
| 6 | **限流**（连接数 / 每 IP / 每 5s 帧） | ✅ 全局 + per-IP + 速率三档 | `shared/constants.ts`、§3.1 的代理退化说明 |
| 7 | **账号 + token 验签 + 角色存档** | ⛔ **未做**（T12） | 28 册（存档设计）、26 册 §14 |
| 8 | 出站**背压**不静默丢弃 | ✅ 超限关连接 + 记账 | `MAX_BUFFERED_BYTES`、26 册 §16.4 |

### 4.1 安全响应头（已发，值如下）

由 `commonHeaders()` 统一附加到 **200 / 404 / 204 / 302** 四段响应：

| 头 | 值 |
|---|---|
| `x-content-type-options` | `nosniff` |
| `referrer-policy` | `no-referrer` |
| `x-frame-options` | `DENY`（点击劫持 · 旧语法） |
| `content-security-policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` |
| `cache-control` | `no-store`（开发期"改完刷新就看到"；上生产可按资源类型再议） |

★ **这套 CSP 不需要 `unsafe-inline` / `unsafe-eval`**，因为前端**逐条对齐**过：
  无 `<style>` 块 / 无 `style="…"` / 无内联事件 / 无 `eval`；血量条走 **CSSOM**（`element.style.width`，
  CSP 不拦）。这条由 `static-web.test.ts` 的**通扫**钉住 —— 谁哪天加了内联写法，那里红。
★ `x-frame-options` 与 `frame-ancestors` 是**同一策略的新旧两版**，刻意都发（老/新浏览器各认一个）。
  **不是两份真相**，值必须一致（都表示"不许任何页面嵌我"）。

## 6. 启动链与运行环境

```
npm start
  └─ prestart: npm run build:web   （node tools/build-web.mjs → dist/web/）
  └─ node tools/start.mjs          （注册 TS 解析钩子 → server/cli.ts）
       └─ server/cli.ts → main()   （解析参数、装配、listen）

npm run dev
  └─ node tools/run.mjs --watch    （同一套：build-web → start → 开浏览器 → 监听 src/）
```

| 项 | 值 |
|---|---|
| **Node 门槛** | **≥ 22.15.0**（用到 `module.registerHooks`）—— 由 `package.json#engines` 与测试共同钉住 |
| 构建步骤 | **无**。服务端直跑 `.ts`（自研零依赖类型剥离加载器，`tools/dev/ts-loader.ts`） |
| 服务根 | `dist/web/`（**不是** `dist/web/src/` —— 弄错就是白屏 + 404）；`GET /` → **302** → `/src/index.html` |
| 页面地址 | `http://127.0.0.1:8123/`（默认端口） |
| WS 地址 | `ws://127.0.0.1:8123/ws`（**同一端口**） |

★ 原理与踩过的坑见 **26 册 §17**；`server/main.ts` 是**纯工厂，不能直跑**，入口链是 `cli.ts → main()`。
★ **同端口**这件事对反代是友好的：一个上游地址同时覆盖页面与 WS。

2. 解压得 `app-debug.apk` → 传到手机 → 点开装。
   手机要允许"安装未知应用"（各 ROM 叫法不同）。
3. 免费账户的 artifact 有保留期（当前 90 天），过期就重新跑一次 `Run workflow`。

★ **不需要配任何 secret**：`assemble` 出的是 **debug** APK，签名由 AGP 用自动生成的
debug keystore 完成，所以能直接装。真要出 release 版才需要 keystore（且**绝不能**入库，
`.gitignore` 已挡）——那是另一批事，现在没做。

### 9.5 公开还是私有：先说额度

- **公开仓库**：Actions 免费、不限分钟。
- **私有仓库**：免费额度按账户给（个人账户 2000 分钟/月，Linux 机器按 1 倍计）。
  本 workflow 每次跑三个作业，`assemble` 是最贵的一个（要下 SDK 35 + 全部依赖），
  **第一次**跑没缓存、最慢；之后 cache 命中会快不少。想省就只在需要装机时
  用 `Run workflow` 手动跑，别每次 push 都跑。

### 9.6 装上之后连不上：按这个顺序查

这三条按"实际踩到的概率"排，**都不是 App 的 bug**：

1. **地址还留着模拟器默认值**。`MudViewModel.DEFAULT_URL = ws://10.0.2.2:8123/ws`，
   `10.0.2.2` 只在**安卓模拟器**里代表宿主机。真机要填电脑的局域网 IP，
   形如 `ws://192.168.1.5:8123/ws`（登录屏的地址框可以直接填，`http://…` 也会被自动换成 `ws://`）。
2. **服务端只听 127.0.0.1**。默认 `127.0.0.1` 只接受本机连接，手机连不上。
   用现成的一条：`npm run start:lan`（= 构建 + `--host 0.0.0.0` + 启动后打印局域网地址），
   或 `npm run dev -- --lan`（dev 的其余参数会原样转给 `server/cli.ts`）。
3. **路径少了 `/ws`**：`ws://IP:8123` ≠ `ws://IP:8123/ws`，少了它服务端握手直接 400。
   ★ 电脑上防火墙弹窗要放行 Node。

明文 `ws://` 能连，是因为清单里 `android:usesCleartextTraffic="true"`（开发包专用）——
上线换 `wss://` 时这条要改回去，否则应用商店会拒审。

### 9.7 红了怎么看：只有**注解**这一条路（★ 实战结论）

三条路里只有一条能匿名读到正文，别走错：

| 通道 | 匿名可读？ | 说明 |
|---|---|---|
| 原始日志 `/actions/runs/{id}/logs` | ❌ **403** | 只有仓库 owner 能下 |
| **step summary** | ❌ | 无条数限制、页面上人能看，但 run 页面是 **JS 渲染**的 ⇒ `curl` 抓 HTML **拿不到正文** |
| **注解 annotation** | ✅ | `GET /repos/{o}/{r}/commits/{sha}/check-runs` → 每个 check run 的 `annotations_url` |

所以"失败诊断"那一步**只发注解**，由 `.github/ci-diagnose.py` 按值钱程度挑（单步 ≤9 条，
每步上限是 10）：失败用例（含断言消息与前 3 行栈）> 编译错 > `What went wrong` > 过滤后的日志尾。

取证的完整命令（`sha` 换成出问题的那次提交）：

```bash
curl -s "https://api.github.com/repos/lsyouran/wushenclient/commits/<sha>/check-runs" \
  | grep -o '"annotations_url": "[^"]*"'      # → 拿到每个作业的注解地址（含 check run id）
curl -s "https://api.github.com/repos/lsyouran/wushenclient/check-runs/<id>/annotations"
```

★ 匿名 API 限 **60 次/小时**（`X-RateLimit-Remaining` 会到 0）。两条绕法：
① 换出口（不同机器/不同网络走的是不同配额）；② 直接读 `check-runs` 里的
`conclusion` 判断红绿，只在确实红时才花配额去读注解。

★★ 诊断步骤**必须自己永远 exit 0**。第一版是在 YAML 里拼 `grep`，而 GitHub 的默认 shell 是
`bash -eo pipefail` —— `grep` 没匹配返回 1 就把整步打断，于是"最需要看原因的时候，
诊断什么都没输出"（run `39618705876` 的 step 6，0 秒退出）。这也是逻辑要放进脚本的原因。

### 9.8 一条命令起后端给手机连：`npm run start:phone`

```bash
npm run start:phone                    # 构建 + 以 0.0.0.0:8123 起服务 + 打印手机该填的地址 + 自检
npm run start:phone -- --port 8124     # 换端口（8123 被 npm run dev 占着时）
npm run start:phone -- --no-build      # 跳过前端构建
```

它和 `npm run start:lan` 的区别**只有一处**，但那一处正是手机连不上的常见原因：

| | `start:lan` | `start:phone` |
|---|---|---|
| 局域网地址 | 打 **http**：`http://192.168.1.2:8123/` | 打 **ws**：`ws://192.168.1.2:8123/ws`（安卓端要的是这个） |
| `WebSocket` 行 | `ws://0.0.0.0:8123/ws` —— **`0.0.0.0` 是通配地址，不是能拨的地址** | 只打能拨的真实网卡地址 |
| 起完自检 | 无 | 真拨一次握手，分开报「服务没起 / 只通回环 / 这块网卡通」 |
| 端口被占 | 直接撞 | 先预检，说明是谁在占、给出换端口命令 |

典型输出（本机实测）：

```
─── 自检（真的拨了一次 WebSocket 握手）────────────────────────
  ✅ 127.0.0.1:8123/ws  通
  ✅ 192.168.1.2:8123/ws  通

─── 手机上填这个 ───────────────────────────────────────────────
  WebSocket 地址：ws://192.168.1.2:8123/ws
  先拿手机浏览器开一下：http://192.168.1.2:8123/
```

★★ **自检的边界，别读过头**：它证明的是"**这台机器**能通过这块网卡的地址完成 WebSocket 握手"。
Windows 防火墙通常**不拦本机到本机**，所以自检全绿、手机仍然连不上是可能的 ——
那种情况的判据是**手机浏览器的** `http://192.168.1.2:8123/` 打不打得开（而不是这个自检）。
打不开就是防火墙或不同网段，按 §9.6 那三条查。

★ 为什么点名叫"先开浏览器"而不是"先装 APK"：浏览器能打开就是纯网络问题的**最强分隔**——
装 APK 要多花几分钟，而它连不上的原因通常跟网络完全无关（地址框里还是 `10.0.2.2`）。
