# 01 · 总览与架构

---

## 1.1 双进程模型

wushen 由**两个完全独立的 Node 进程**组成，它们通过 **SQLite 数据库 + Cookie 会话票据**间接协作，进程间**没有任何直接通信**（无 IPC、无消息队列）。

```
┌─────────────────────────────────────────────────────────────────┐
│                     浏览器（前端 src/ 构建到 www/）                │
│   jQuery 4 + 原生 ES Module，单一 index.html，DOM 全 JS 生成        │
└───────────┬─────────────────────────────────┬───────────────────┘
            │ HTTP (同域 :8088)                │ WebSocket (直连 :31300)
            │ 登录/注册/验证码/改密/服务器列表   │ 游戏内一切交互
            ▼                                 ▼
┌───────────────────────────┐   ┌──────────────────────────────────┐
│  Web 服务器  web.js        │   │  游戏服务器  main.js               │
│  Express 5                │   │  自研 WS 服务器（net 模块）         │
│  ├─ 静态托管 www/          │   │  ├─ os/   引擎内核（全局裸变量）     │
│  ├─ /api/:class/:method   │   │  ├─ world/ 世界内容（脚本体）       │
│  │    → api/user.js       │   │  ├─ WORLD 单例（房间/玩家/索引）    │
│  │    → api/game.js       │   │  └─ 5 秒全局心跳                   │
│  ├─ /gm 代理 → :8090       │   │  （GM HTTP 服务在 :8090）          │
│  └─ Set-Cookie: u / p     │   │                                  │
└───────────┬───────────────┘   └───────────────┬──────────────────┘
            │                                   │
            └──────────► SQLite ◄───────────────┘
                     data/<SID>/database.db
                     users / players / servers
```

启动方式（`package.json:15`）：`npm start` = `concurrently "npm run web" "npm run os"`。

> ⚠️ 注意：两台服务器**共享同一个 SQLite 文件**，readme 明确"不支持分开部署"。这意味着横向扩展只能靠"多服（servers 表）+ 跨服登录"实现，而不是多实例负载。

## 1.2 分层架构

| 层 | 目录 | 角色 | 关键特征 |
|---|---|---|---|
| **传输层** | `os/net-ws.js`、`os/ws.js` | 手写 WebSocket/TCP 服务器 | 三种协议并存（RFC6455 / 旧 draft / 裸 TCP 长度前缀） |
| **会话层** | `api/base.js`、`os/login.js` | 会话票据签发与校验 | AES-128-CBC，明文 `id%name%pwd%time%level` |
| **分发层** | `os/world.js`、`os/char/character.js` | 消息路由到指令 | `WORLD.COMMANDS[cmd]` 查表 + 六道闸门 |
| **引擎层** | `os/*` | 类定义与机制骨架 | **全局裸变量**，`BASE` 为唯一根类 |
| **补丁层** | `world/extends/*` | 覆盖引擎 prototype | 加载顺序第一，是真正的"机制实现所在" |
| **内容层** | `world/{map,npc,obj,skill,family,task,cmd}/*` | 游戏数据 + 指令 | 926 个"脚本体"文件，非模块 |
| **协议序列化** | `world/extends/item/obj.js` 等 | 对象 → 客户端 JSON | 手工拼字符串，**不是 JSON.stringify** |
| **前端** | `src/*` | 渲染与输入 | `Process[data.type]` 动态分发 |

## 1.3 一次"移动"的完整数据流（端到端）

这是理解全系统最有价值的单条链路：

```
① 用户点击方向按钮
   src/game/main.js:222 ContainerCommand
     → 读取元素 attr("cmd") = "go north"
     → src/client.js:68 SendCommand("go north")
     → WebSocket.send("go north")            【纯文本，非 JSON】

② 服务端收帧
   os/net-ws.js:95 protocols.var1.readData
     → 解 mask → frameType=Text → server.onReceive(msg, socket)
   os/ws.js:23  → WORLD.request(msg, socket)
   os/world.js:75 → 防刷计数 → user.command("go north")

③ 指令分发
   os/char/character.js:136 command()
     → 切分 cmd="go", pars="north"
   os/char/character.js:156 do_command()
     → ① 先试房间/物品自定义动作 do_item_action
     → ② WORLD.COMMANDS["go"] → check_command 六道闸门
     → ③ cmd.enter(me, "north")

④ 业务执行（world/cmd/action/go.js）
     → 归一化方向 → 查 room.exits["north"] → ROOM.Get(path)
     → me.moveto(next_room, 出房文案, 进房文案, dir)

⑤ 房间变更枢纽
   os/room/room.js:29 item_changed(obj, false)  （原房间广播离开）
   os/room/room.js:20 do_enter(obj, true, msg)  （新房间）
     → user.send(room.to_json())       {"type":"room",...}
     → room.send_exits(user)           {"type":"exits",items:{...}}
     → user.send(room.items_to_json()) {"type":"items",items:[...]}
     → item_changed(obj,true) → 广播给房内其他人 {"type":"itemadd",...}

⑥ 前端渲染
   src/client.js:165 OnReceived
     → 首字符 '{' → new Function("return "+data)()  ⚠️ eval 级风险
     → src/client.js:93 ReceiveData → Process[data.type](data)
     → src/process.js:297 Process.room / :330 Process.exits / :224 Process.items
     → 更新 .room-name / .room_desc / .room_items / .map-panel
```

**关键设计启示**：服务端向客户端推的是**语义化的 UI 指令包**（`room`/`items`/`exits`/`sc`/`dialog`），而不是"事件流"。客户端几乎不做业务判断，只做渲染。这让客户端很薄，但也意味着**协议与 UI 结构强耦合**——服务端改一个字段，前端必须同步改。

## 1.4 五个核心设计取舍

| # | 取舍 | 选择 | 代价 | 复刻建议 |
|---|---|---|---|---|
| 1 | 模块系统 | **全局裸变量**（`BASE`/`CHARACTER`/`WORLD`/`FAMILIES` 全在 globalThis） | 无法单元测试隔离、加载顺序敏感 | **必须改**：改用 ESM + 显式依赖注入 |
| 2 | 内容脚本 | 文件体即构造器（`vm.compileFunction` + `func.apply(obj)`），**零 `module.exports`** | 无法静态分析、IDE 无提示、无法 tree-shaking | 可保留范式（写内容的人很爽），但建议封装成 `define({...})` |
| 3 | 协议序列化 | **手工拼 JS 字面量字符串**（`"{type:\"sc\",id:\"" + id + ...}"`） | XSS/注入风险、无法 schema 校验、字段错配静默失效 | **必须改**：统一 `JSON.stringify` + 类型定义 |
| 4 | 前端框架 | 无框架，jQuery + 模板字符串 | 23 个 dialog 无统一范式、样式靠运行时注入 | 可保留（MUD UI 简单），但 dialog 基类要统一 |
| 5 | 战斗驱动 | 每场战斗一条 `setTimeout` 自递归链（周期 = `gjsd`） | 千场战斗 = 千个定时器；无法统一调度 | 建议改为"全局 tick + 战斗对象注册" |

## 1.5 与"新 MUD"相关的三个判断

1. **协议设计值得抄**。把"服务端推 UI 语义包、客户端只渲染"这套思路保留，它让客户端代码量极小（11k 行就能覆盖 23 个面板）。但**必须把字符串拼接换成 JSON + 类型定义**，这是本项目最大的可维护性黑洞。

2. **脚本化内容层值得抄**。`world/` 下 926 个文件、3.9 万行，靠"目录即类型 + `this.inherits()`"组织，配 `#变体参数` 和 `BASE.UPDATE` 热更新，内容生产效率很高。这是 MUD 这类内容密集型项目的正确解。

3. **`os/` 内核不建议抄**。它是"年代久远、大量方法只声明不实现、真实逻辑散落在 `world/extends/`"的状态（readme 自己承认）。复刻时应**按本套文档第 7~12 册描述的机制重新实现**，而不是照搬代码。
