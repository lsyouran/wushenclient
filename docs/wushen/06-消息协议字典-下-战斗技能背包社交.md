## 6.1 战斗

### 6.1.1 `combat` — 战斗开始/结束

- **发送**：`os/char/combat.js:22`（开始）/`os/char/combat.js:114`（结束）
- **前端**：`src/process.js:454`

```js
{type:"combat", start:1}      // 开战
{type:"combat", end:1}        // 停战
```

前端行为（`src/process.js:456-463`）：
- `Setting.auto_showcombat` → 自动展开 `.combat-panel`
- `Setting.auto_hideroom` → 自动隐藏 `.content-room`，结束时恢复

### 6.1.2 `sc` — 血蓝变化（★ 高频包）

- **发送**：`os/char/combat.js:45-75 notify_hp(type, val)`
- **前端**：`src/process.js:425`
- **广播范围**：当前房间内**所有玩家**

```js
// 完整包（不带参数调用时）
{type:"sc", id:"a1b2", hp:3200, max_hp:4000, mp:800, max_mp:900}
// 单值包（add_hp / add_mp 调用时）
{type:"sc", id:"a1b2", hp:3200}
{type:"sc", id:"a1b2", mp:800}
// 带伤害统计（接收方开启 show_damage 设置）
{type:"sc", id:"a1b2", hp:3200, damage:1250}
```

| 字段 | 说明 |
|---|---|
| `id` | 角色/怪物 id |
| `hp` / `max_hp` / `mp` / `max_mp` | 数值 |
| `damage` | 该玩家累计造成的伤害（`this.damages[player.id]`），仅 `type==="hp"` 且 `query_setting('show_damage')` 时附加 |

> 用于更新房间物件列表里的 `.progress-bar`（`src/process.js:265-296`）。

### 6.1.3 `status` — BUFF/DEBUFF 变更

## 6.3 背包与物品（`dialog:"pack"`）

物品序列化由 `world/extends/item/obj.js` 的 `format_to_pack()` 产出，**是一个数组而非对象**：

```js
// 单个物品 = 13 元素数组
[color_name, id, count, grade, unit, value, is_equipment, has_use, has_study, has_open, combine_count, is_locked, otype]
// 例：
["<hig>武当长剑</hig>", "a1b2", 1, 4, "把", 20000, 1, 0, 0, 0, 0, 0, 0]
```

| 下标 | 含义 |
|---:|---|
| 0 | `color_name`（含品阶颜色标签） |
| 1 | `id` |
| 2 | `count` |
| 3 | `grade`（品阶 0-6） |
| 4 | `unit`（量词） |
| 5 | `value`（价值；不可交易时为 0） |
| 6 | `is_equipment` 0/1 |
| 7 | 有 `on_use` 0/1 |
| 8 | 有 `on_study` 0/1 |
| 9 | 有 `on_open` 0/1 |
| 10 | `combine_count`（合成所需数量，无则 0） |
| 11 | `is_locked` 0/1 |
| 12 | `otype`（客户端分类） |

**背包增量更新包**（前端 `src/dialog/packet.js:25-138 updateitem` 按分支就地更新，不整表重绘）：

| 载荷 | 发送位置 | 含义 |
|---|---|---|

| `{type:"dialog",dialog:"pack",id:"a1b2",uneq:0}` | `os/item/equipment.js:158` | 卸下 |

前端行为（`src/process.js:521`）：写入 `.channel` 浮层或主消息流，取决于设置。

> ★★ **勘误（2026-10-13）**：本表原写有 **`say`（说话）** 与 **`es` / `emote`（表情动作）**
> 两行，**两行都不成立**，已删除。复核命令：
> `grep -rEn 'ch *: *["'"'"']' os/ world/`（在 wushen 根目录跑；注意别用 `ch:\s*"` ——
> BRE 里 `\s` 不是空白符，那样会得到"零命中"的**假结果**）。
>
> - **`say` 不是 `msg` 的 `ch`**：`world/cmd/channel/say.js:18` 收尾是
>   `return me.send_room("$N说：" + UTIL.htmlEncode(msg));` —— **房间广播**（三视角），
>   进主消息流，根本不发 `msg` 包。前端频道浮层也没有「房间」这一档：
>   `src/dialog/channel.js` 的页签是 全部/世界/队伍/门派/全区/帮派/系统，
>   它的 `switch (data.ch)` 更没有 `say` 分支（`ch:'say'` 落进去会被显示成【闲聊】）。
> - **`emote` 不是 `ch`**：它是**包类型** —— `world/cmd/channel/emote.js:79` 发的是
>   `{type:'emote',items:[…]}`（表情**清单**，给前端开面板用）。
>   而表情**动作**的文本（`emote.enter(me, str)` 的返回值）是被
>   `chat/tm/fam/es/pty` 拼进**各自** `content` 里的（见 `chat.js:31`）。
>
> 这条勘误是在 newmud 侧对账 `say` 的渲染归属时被翻出来的（26 册 §24）：
> 正是它让 T16 那边一度把 `say` 当成"频道消息"实现。
> 教训与 00 册 §4 纪律 6 完全一致 —— **文档写错的事，只看文档看不出来**。

## 6.5 `dialog` 通用容器（★ 最重要的协议抽象）

**这是本项目协议设计的精髓**：一个包类型承载 23 个面板的所有数据。

```js
{type:"dialog", dialog:"<面板名>", ...其余字段由该面板自定义}
```

前端统一处理（`src/process.js:423`）：

```js
dialog: function (data) { Dialog.show(data.dialog, data); }
// → src/dialog/base.js:73  dialog.onData(data)
```

**服务端也可以主动弹面板**——这是服务端驱动 UI 的关键手段。

## 6.7 协议设计评价与复刻建议

### 值得抄的

1. **`dialog` 通用容器**：一个包类型打通所有面板，新增面板只需在服务端发 `{type:"dialog",dialog:"xxx"}` + 前端加一个同名对象，**协议层零改动**。
2. **`cmds` 命令条**：服务端下发"按钮 + 命令"，避免在协议里定义无数种表单交互。MUD 这类文本驱动游戏非常适用。
3. **三视角文案替换**（`$N/$n/$P/$w/$l`）：服务端写一次文案，自动适配当事人/目标/旁观者。
4. **增量优先**：`itemadd/itemremove` 而非每次全量 `items`；背包按 `eq/uneq/remove` 分支更新。

### 必须改的

1. **字符串拼接 → JSON 序列化**。当前 `{type:"sc",id:"` + id + `"...}` 的写法无法做 schema 校验，字段缺失会静默产生 `undefined`。
2. **统一引号风格**。现存 `type:"room"`（无引号 key）与 `type:'roles'`（单引号）混用，前端靠 `new Function` 才都能解析；一旦改 `JSON.parse` 就会全崩。
3. **`items` 数组的 `0` 哨兵**（`room.js:139`）：是拼接时图省事留下的，应去掉。
4. **补一个协议版本号字段**，配合客户端版本协商。
5. **`setting` 包没有对应的服务端强制同步机制**，全靠登录时下发一次。
