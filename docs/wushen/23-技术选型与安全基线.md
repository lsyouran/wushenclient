# 23 · 技术选型与安全基线

> 输入变量（用户确认）：**AI 辅助开发** · **安全性最重要** · **在线规模 ≤ 200 人**
> 本文是后续所有 AI 生成代码的**约束契约**：任何新代码都不得违反第 4 节的红线清单。

---

## 1. 结论

**TypeScript（Node 22+）+ 内容层 JS 脚本体（vm 沙箱隔离）+ zod 运行时校验。**

| 层 | 技术 | 理由 |
|---|---|---|
| 共享协议 | TypeScript 类型 + zod schema | AI 开发的类型护栏；运行时校验防外部输入 |
| 服务端引擎 | TypeScript（strict） | 类型收益最高的区域 |
| 内容层 | JS 脚本体（**跑在 vm 沙箱**） | 保留 wushen 的内容生产效率，但隔离执行 |
| 前端 | Vite + TypeScript | 与服务端共享 `shared/protocol.ts` |
| 数据库 | SQLite（better-sqlite3） | 200 人规模，同步 API 更简单 |
| 传输 | `ws` 库 + wss + 限流 + 心跳 | 不手写 RFC6455 |

## 2. 三个输入变量的推理链

### 2.1 「AI 开发」→ TypeScript（权重最高）

AI 生成代码最典型的失败模式不是语法错，而是**接口对不上**：

- 在 A 处写 `room.name`，在 B 处读 `room.title`，两边各自生成，跑起来才发现
- 协议包字段少一个、名字拼错，运行时静默 `undefined`

TypeScript 把这个失败模式**从运行时提前到编译期**：

| 环节 | 纯 JS | TypeScript |
|---|---|---|
| AI 生成序列化代码 | 靠猜字段名，需人工核对 | 对着 `ServerPacket` 类型生成，大概率一次就对 |
| 错误反馈闭环 | 无（只能跑起来看） | `tsc --noEmit` 报错可直接喂回 AI 自我修正 |
| 跨会话一致性 | AI 第二次来可能发明新字段名 | 类型定义是持久契约，约束后续所有 AI 会话 |
| 重构安全性 | 改字段名需全库 grep | 编译器列出所有引用点 |

> **这一点对个人 + AI 的项目尤其关键**：类型定义文件就是"给未来 AI 的说明书"。没有它，每次新会话的 AI 都在重新发明接口。

### 2.2 「安全性最重要」→ 架构优先，语言次之

诚实评估：**语言本身对安全的影响远小于架构决策**。Python（pydantic）同样能做运行时校验。但 TypeScript 有两个额外优势：

1. 类型定义 + zod 可以**从同一份 schema 生成**（`z.infer<typeof Schema>`），避免"类型和校验两处维护、容易漂移"
2. 类型能拦住 wushen 那批低级缺陷（`OBJ_STROE` 拼写、参数丢弃、字段错配）

**但真正的安全来自第 4 节的四层闸门，不是语言本身。**

### 2.3 「≤ 200 人」→ 性能出局，架构可大幅简化

200 并发长连接对 Node 单进程是**极轻量**负载。带来三个简化：

| 简化 | 说明 |
|---|---|
| 单机单进程足够 | 不需要多进程分片、不需要 Redis 共享状态 |
| 全内存对象模型可行 | 保留 wushen 的"对象常驻内存 + 定期落盘"，不需要每次操作走数据库 |
| SQLite 足够 | better-sqlite3 同步 API，比异步简单且更快（无连接池开销） |

> ⚠️ 但**不能因此放松架构**：wushen 的 `WORLD.USERS` 线性扫描、`find_obj_byid` 线性扫描在 200 人时不会爆，但仍是坏设计。索引一律用 `Map`。

## 4. ★ 安全基线（红线清单）

### 4.1 四道闸门

| # | 闸门 | 措施 | 挡什么 |
|---:|---|---|---|
| 1 | **传输层** | wss（TLS）、连接限流、心跳 + 踢死连接、单连接请求频率限制 | 嗅探、慢连接攻击、资源耗尽 |
| 2 | **协议边界** | 所有入站数据过 **zod schema**，失败即断连；`JSON.parse` + try-catch | 畸形数据、注入、RCE |
| 3 | **业务层** | 每个指令声明权限等级 + 状态门禁；GM 操作全审计；密码 argon2 | 越权、状态竞态、提权 |
| 4 | **内容层** | 内容脚本跑 **vm 沙箱**，只暴露白名单全局 | 内容文件的任意代码执行 |

### 4.2 红线清单（AI 生成代码时禁止出现）

| ❌ 禁止 | 原因 | ✅ 替代 |
|---|---|---|
| `new Function(...)` / `eval` | 远程代码执行 | `JSON.parse` + zod |
| 手工拼 JSON 字符串（`"{type:\"sc\",id:\"" + id`） | 注入 + 字段错配静默 | `JSON.stringify` + 类型 |
| 内容脚本可直接访问 `require` / `fs` / `process` | 内容文件 = 任意代码执行 | vm 沙箱白名单 |
| GM 命令支持执行任意表达式（wushen 的 `call`） | 提权后 RCE | 白名单命令集 + 审计 |
| 会话票据内含凭据（密码/用户名） | 泄露即永久泄露 | 随机 token + 服务端 session + 有效期 |
| 前端直接 `append()` 服务端文本 | XSS | 自定义标签白名单 + 转义 |
| SQL 字符串拼接 | SQL 注入 | 参数化查询（better-sqlite3 绑定参数） |
| Cookie 无 `httpOnly` / `secure` / `sameSite` | XSS 窃取、CSRF | 显式设置三属性 |
| CORS `*` + `Allow-Credentials: true` | 浏览器拒绝且不安全 | 显式 origin 白名单 |

### 4.3 wushen P0/P1 缺陷的对应修复（必须逐条落实）

| wushen 缺陷（第 21 册编号） | 修复 |
|---|---|
| #1 前端 `new Function` 解析 | `JSON.parse` + zod |
| #2 `hotload.js` 空对象覆盖指令 | 不实现；统一走 `BASE.UPDATE` 三段式 |
| #3 GM `call` 远程 eval | 删除，改白名单 |
| #4 票据含明文 MD5 密码 | 随机 token + 有效期 |
| #5 `getData` 丢弃角色 id | SQL 加 `and a.id=?`，类型签名强制两参 |
| #8 `ws://` 硬编码 | 按 `location.protocol` 选 ws/wss |
| #9 不回 Pong | 实现 Ping/Pong |
| #10 无心跳无重连 | 前端 30s ping + 指数退避重连 |
| #13 `.id` vs `.ID` 不一致 | 统一命名 + 类型约束 |
| #15 `OBJ_STROE` 拼写 | `OBJ_STORE`，且索引封装在 `registry.ts` |

## 5. 内容层的安全设计（★ 本项目特有的风险点）

wushen 的 `world/` 脚本体用 `vm.compileFunction(script, [], ...)` 编译后 `func.apply(obj)` —— **`this` 是 obj，但脚本体能访问全局作用域**。一个出错（或恶意）的内容文件可以直接 `require('fs')` 删库、`process.exit()`。

因为内容是你自己写的，wushen 时代风险可控；但**你要用 AI 批量生成 926 个内容文件**，出错概率显著上升。

**方案：内容脚本跑 `vm.runInNewContext`，只暴露白名单全局。**

```ts
// server/world/sandbox.ts
const ALLOWED_GLOBALS = {
  ROOM, NPC, OBJ, EQUIPMENT, SKILL, FAMILY, COMMAND, AREA,
  EQUIP_TYPE, WEAPON_TYPE, PROPERTIES, SKILL_TYPES,
  Math, JSON, parseInt, parseFloat, Date, Array, Object, String, Number,
  console,
  // ❌ 不暴露：require, fs, process, globalThis, Buffer, __dirname
};

export function loadContentScript(code: string, filename: string) {
  const ctx = vm.createContext({ ...ALLOWED_GLOBALS, __result: {} });
  vm.runInContext(`(function(){ ${code} }).call(__result)`, ctx, { filename, timeout: 1000 });
  return ctx.__result;
}
```

配套三条：

1. **加载超时**（`timeout: 1000`）：内容文件里的死循环不会挂起服务器
2. **加载失败隔离**：单个内容文件报错只跳过该文件 + 记日志，不中断启动（wushen 是 `console.error` 后继续，这点可以保留）
3. **启动期静态校验**：`validate_world.ts` 检查出口指向的房间存在、NPC/物品 path 有效

> 权衡：沙箱会让内容脚本**无法 `require` 自己的工具函数**。解决：把常用工具预先注入沙箱（如 `create_by_odds`、颜色标签工具），或提供 `helpers` 命名空间。

## 6. AI 协作约定（★ 给后续所有 AI 会话的约束）

因为项目由 AI 生成代码，必须建立可机检的闭环：

| 约定 | 说明 |
|---|---|
| **类型先行** | 新增任何协议包，先改 `shared/protocol.ts` 的类型 + zod schema，再写实现 |
| **契约先行** | 新增模块先写接口 + 测试用例，再写实现 |
| **校验闭环** | 每完成一个模块必跑：`tsc --noEmit` → `vitest` → 冒烟脚本 |
| **红线自检** | AI 每次提交前对照第 4.2 节红线清单自查，逐条报告 |
| **内容样例驱动** | 批量生成内容前，先手工打磨 3 个样例文件（1 房间 / 1 NPC / 1 物品），让 AI 照抄范式 |
| **不变式断言** | 关键不变式写成运行时断言（如"玩家 hp 不超过 max_hp"、"背包容量不超限"） |
| **不信任生成结果** | AI 自报"完成"不等于通过；必须有可执行的验证证据 |

### 每个模块的最小交付单元

```
① shared/protocol.ts 的类型 + schema
② 服务端实现
③ 前端 handler + 渲染
④ vitest 测试（含一个"畸形输入"用例）
⑤ 冒烟脚本输出
```

## 7. 200 人规模下的架构要点

| 项 | 决策 |
|---|---|
| 进程模型 | 单进程，对象常驻内存 |
| 战斗调度 | 全局 tick（200ms）驱动战斗注册表，不用 per-role setTimeout |
| 心跳 | 全局 5s 业务心跳；WS 层独立 30s ping/pong |
| 存档 | 定期全量（60 分钟）+ 玩家退出时单角色 + 写前备份 |
| 索引 | 全部 `Map`（玩家、房间、物品模板、NPC 模板） |
| 日志 | pino 结构化；安全事件（登录失败、GM 操作、异常协议）单独落审计流 |
| 限流 | 每连接每 5s ≤ 20 条指令；登录失败按 IP + 账号双维度限流 |

> 200 人意味着**不需要** Redis、消息队列、多进程分片、读写分离。架构复杂度应压到最低——复杂度本身就是安全风险。
