## 0. 结论摘要

| 子系统 | 一句话契约 |
|---|---|
| **GM** | 独立进程 + 独立鉴权 + 命令白名单 + 危险操作二次确认 + append-only 审计链；**永不复用玩家鉴权、永不执行任意表达式** |
| **支付** | 金额只用**整数分**；回调**必须验签**、**必须幂等**、**必须可对账**；订单与发货分离，发货失败可补偿 |

## 1. 威胁模型与信任边界

wushen 的四层防御全破（23 册 §2.2），其中与 GM/资金直接相关的两条：

| wushen 缺陷 | 位置 | 后果 |
|---|---|---|
| GM `call` 指令 = 服务端 eval | `world/cmd/admin/*` 的 `call` | 任意 GM 可执行任意代码（21 册 #3） |
| GM 后台与游戏世界同进程、同鉴权 | `os/world.js:342-520` | 一个 GM 账号失守 = 全服失守 |

**信任边界（新项目）**：

```
[公网浏览器] ──TLS──> [游戏进程]        仅接受玩家会话；不暴露任何管理接口
[公网浏览器] ──TLS──> [GM 进程]         独立端口 + 独立账号 + IP 白名单
[第三方支付] ──TLS──> [回调入口]        只接受验签通过且幂等的新回调
                          │
                    [SQLite：订单/审计 append-only]
```

**不变式**：三条入口互不共享会话；玩家 token 在 GM 进程**不可用**，反之亦然。

## 2. GM 子系统契约

### 2.1 进程隔离（强制）

- GM 服务是**独立进程**，独立端口，独立启动脚本（`npm run gm`）。
- **禁止**把 GM 接口挂在游戏进程的 Express 上（wushen 的反面教材）。
- 游戏进程崩溃 / 重启不影响 GM；GM 进程崩溃不影响在线玩家。

### 2.2 独立鉴权（强制）

| 项 | 要求 |
|---|---|
| 账号体系 | **独立 GM 账号表**，与玩家表物理分离；不得用玩家账号登录 GM |
| 密码存储 | `argon2id`（或 bcrypt cost ≥ 12），**禁止 MD5**（wushen 是明文 MD5，21 册 #4） |
| 会话 | 随机 token + 服务端 session + 短有效期（≤ 2h 空闲过期） |
| 令牌 | GM token **必须**携带角色标识，玩家 token 一律拒绝 |
| 网络 | IP 白名单 + 强制 TLS；白名单为空时**拒绝启动**（fail-closed） |
| 登录失败 | 按 IP + 账号双维度限流并写审计 |

### 2.3 命令白名单（强制）

- 所有 GM 能力在 `server/gm/commands.ts` 登记，形如 `{ name, level, danger, run(ctx, args) }`。
- **禁止任何形式的表达式求值**：不得实现 `eval` / `new Function` / `vm.runInContext` / `call` 指令（21 册 #3 的直接根治）。
- 每个命令声明**最低 GM 等级** `level` **与危险性** `danger`，由分发器统一校验（不得由命令自己判断）。

### 2.4 二次确认（强制）

| danger | 触发二次确认 | 例 |
|---|---|---|
| `low` | ✗ | 查角色信息、发公告 |
| `medium` | ✓ | 改属性、发物品、踢下线 |
| `high` | ✓ + 需**第二人在场批准**（可选，按运营规模启用） | 发钱、改等级、封号、删档 |

二次确认机制：

1. 第一次调用返回 `confirm_token`（服务端生成，**一次性**，有效期 ≤ 60s，绑定"操作者 + 命令 + 目标"）。
2. 第二次调用必须携带该 token 且三个绑定项完全一致，否则拒绝。
3. token 使用后立即失效；过期不自动续。

### 2.5 审计链（强制）

**append-only**，禁止 UPDATE / DELETE。字段：

| 字段 | 说明 |
|---|---|
| `at` | 时间（服务端时钟） |
| `gm_id` | 操作者 |
| `action` | 命令名 |
| `target_type` / `target_id` | 受影响对象（world id 或 role id） |
| `before` / `after` | 变更前后快照（JSON） |
| `ip` / `ua` | 来源 |
| `confirm_token` | 二次确认凭据（可追溯为哪次确认） |
| `result` | 成功 / 失败 + 原因 |

配套：审计写入失败 → **整个操作回滚**（审计不可用则不允许改数据）。

## 3. 支付子系统契约

### 3.1 金额：整数分（强制）

- 存储、计算、比较一律用**整数分**：`amount_fen: number`。
- **禁止浮点金额**（`19.9` 这类在 JS 里是 `19.899999...`）。
- 展示层再做 `/100` 转换；转换只允许出现在渲染函数里。

### 3.2 订单模型

```sql
CREATE TABLE orders (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id       TEXT    NOT NULL UNIQUE,   -- 商户订单号（幂等键，服务端生成）
  role_id        TEXT    NOT NULL,
  product_id     TEXT    NOT NULL,
  amount_fen     INTEGER NOT NULL CHECK (amount_fen > 0),
  channel        TEXT    NOT NULL,          -- wechat / alipay / ...
  status         TEXT    NOT NULL,          -- created|pending|paid|delivered|failed|refunded
  channel_txn_id TEXT,                      -- 第三方流水号
  created_at     INTEGER NOT NULL,
  paid_at        INTEGER,
  delivered_at   INTEGER
);
CREATE INDEX idx_orders_role ON orders(role_id);
CREATE INDEX idx_orders_status ON orders(status);

-- 原始回调存档（验签与争议取证）
CREATE TABLE pay_callbacks (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id   TEXT NOT NULL,
  channel    TEXT NOT NULL,
  raw_body   TEXT NOT NULL,
  sign_ok    INTEGER NOT NULL,
  received_at INTEGER NOT NULL,
  applied    INTEGER NOT NULL DEFAULT 0
);
```

> 金额、商品、角色的对应关系**以服务端订单为准**；客户端传来的任何金额字段一律忽略（防篡改）。

### 3.3 下单流程

```
客户端 POST /pay/create { product_id }
  → 服务端按 product_id 查**服务端商品表**得到 amount_fen（不信客户端金额）
  → 生成 order_id（雪花/ULID），status=created
  → 向渠道下单，status=pending，返回 PayPacket{ url, order_id }
```

### 3.4 回调验签（强制）

回调入口的处理次序**不可调换**：

```
1. 读原始 body（不做任何解析/改写，验签用原文）
2. 落 pay_callbacks(raw_body)                  ← 先取证，后处理
3. 验签：渠道签名算法；失败 → sign_ok=0 + 审计 + 返回失败 + 状态不变
4. 校验金额与 order_id 与本地订单一致
5. 幂等检查（见 3.5）
6. 事务内：status=paid → 发货 → status=delivered → applied=1
```

- **禁止**先解析成对象再验签（几乎必然验签失败或可被绕过）。
- 验签失败**必须**留下审计记录，且计入告警。

### 3.5 幂等（强制）

- `orders.order_id` 为 `UNIQUE`；同一个 `order_id` 的重复回调**只允许生效一次**。
- 实现方式（二选一，推荐前者）：

```sql
-- 原子流转：影响行数为 0 即代表已被处理过
UPDATE orders SET status='paid', paid_at=?, channel_txn_id=?
 WHERE order_id=? AND status='pending';
```

- 重复回调返回渠道"成功"（避免渠道无限重试），但**不再发货**、写一条 `applied=0` 的回调记录。

### 3.6 发货状态机

```
created ──> pending ──> paid ──> delivered
                 │         │
                 └─failed  └─(补偿任务)──> delivered
delivered ──(客服/风控)──> refunded
```

- 发货失败**不得回滚支付状态**（钱已经收了），改为置 `paid` 并进入补偿队列重试。
- 补偿任务按 `status='paid' AND delivered_at IS NULL` 扫描，指数退避重试，上限后告警。

### 3.7 对账（强制）

- 每日对账任务：拉渠道账单 ↔ `orders`，比对 `order_id` / `amount_fen` / `channel_txn_id`。
- 差异三类：**本地有渠道无**（可能未支付成功）、**渠道有本地无**（漏单，需补发）、**金额不一致**（严重，立即告警并冻结订单）。
- 对账结果落库并保留 ≥ 180 天。

## 4. 会话与传输（与 23 册叠加）

| 项 | 要求 |
|---|---|
| 传输 | `wss://` / `https://`；**按 `location.protocol` 选择**，禁止硬编码 `ws://`（wushen #8） |
| 票据 | **随机 token**，服务端 session 存储，含有效期；**严禁内含密码**（wushen #4） |
| Cookie | 显式 `httpOnly` + `secure` + `sameSite=Lax` |
| CORS | 显式 origin 白名单；**禁止** `*` + `Allow-Credentials` |
| 限流 | 每连接每 5s ≤ 20 条指令；登录失败按 IP + 账号双限流 |
| 心跳 | WS 层 30s ping/pong；前端 30s 主动 ping + 指数退避重连（wushen #9/#10） |

## 5. 红线清单（在 23 册 §4.2 之上追加）

| ❌ 禁止 | 原因 | ✅ 替代 |
|---|---|---|
| GM 命令执行任意表达式 / `eval` | 提权即 RCE | 白名单命令 + 参数化 |
| GM 与玩家共用鉴权 | 单点失守即全失守 | 独立账号表 + 独立 token |
| GM 无审计或审计可改 | 事后无法追责 | append-only 审计 + 写失败即回滚 |
| 用客户端传来的金额 | 篡改 | 服务端商品表定价 |
| 浮点金额 | 精度丢失 | 整数分 |
| 回调先解析后验签 | 验签可绕过 | 用原始 body 验签 |
| 回调不幂等 | 重复发货 | `order_id` UNIQUE + 状态原子流转 |
| 支付成功即"立即发货且无补偿" | 发货失败即玩家损失 | 状态机 + 补偿队列 + 对账 |

| 闸门 | 检查 | **必须包含的反例**（否则算假绿） |

| **G10 支付** | 回调验签 + 幂等 + 金额校验的单元测试 | ① **伪造签名** → 必须拒绝且状态不变；② **重复回调** → 只发货一次；③ **篡改金额** → 必须拒绝 |
