# 34 · 状态与效果系统设计（BUFF / 行动状态）

> **本册回答**：一个「效果」（中毒、忙乱、内功护体…）和一个「行动状态」（打坐、疗伤）在我方**怎么建模** ——
> 存在哪、怎么叠加、怎么到期、怎么存档、怎么告诉前端。
>
> **什么时候读**：动 BUFF / 状态 / 打坐疗伤 / 绝招效果之前。
>
> **现状：未实现。** 本册是**施工图 + 判据**，不是实现记录。实现完成后由 26 册新增节回写「做到什么程度」，
> 本册只保留「为什么这么设计」。★ **别把它当"已完成"引用**（33 册红牌：注释与文档也是断言）。
>
> **素材来源与边界**：内容来自对 wushen 状态系统的一次通读（笔记在 `docs/核心系统-属性技能战斗状态-深度分析.md` 的 §四 / §五）。
> **但结论一律按我方引擎重写**：wushen 是 JS + 闭包 + 每个 buff 一个定时器，我方是 TS + 纯数据 + 单调度器
> ⇒ **抄它的教训，不抄它的实现**。凡与 wushen 不同处都标「差异」并给理由。

## §34.1 三个概念必须先分开（★ 本册最重要的一张表）

wushen 把它们混在一起，所以「2 秒不能动」和「很久不能动」共用同一个字段，一条写错的 buff 能把角色锁死。
我方**用三个不同的落点**，判据是三个问题：

| 概念 | 我方落点 | 时间量级 | 改属性？ | 锁指令？ | 进存档？ |
|---|---|---|---|---|---|
| **`busy`** 短时动作锁 | `Character`（**已实现**：TTL + `BUSY_MAX_MS` 硬上界，26 册 §49 拍板） | 秒 | ❌ | ✅ | ❌ 重登清零 |
| **`effect`** 效果（BUFF / debuff） | 本册 §34.2–§34.6（**待做**） | 秒 ~ 分 | ✅ 走 `props.ts` | 视 `control` | ✅ |
| **`state`** 行动状态机（打坐 / 疗伤） | 本册 §34.7（**待做**，门禁桩已在 `command.ts`） | 持续 | ❌（它自己去调 `setHp` / 内力） | ✅ 白名单 `allow_state` | ❌ 下线即停 |

**判据（三选一，别混）**：问「它要不要**改属性**」——
要 ⇒ `effect`；不要但**要持续** ⇒ `state`；都不要、**只锁一下** ⇒ `busy`。

★ **凡"要锁得比 15 秒更久"的需求，一律不许走 `busy`**（硬上界是刻意留的护栏，不是可调参数）。
★ 别与**属性键** `busy` 混淆：`props.ts` 里的 `'busy'` 是 wushen 的「忙乱时间」，它属于 `effect` 的 `prop`，不是动作锁。

## §34.2 `effect` 契约：**Def 与 Instance 必须分开**（与 wushen 最根本的分歧）

wushen 把 `on_interval` / `on_attach` / `on_expire` **当成函数存在 buff 实例里**。
后果是实测过的：buff 实例不可序列化 ⇒ **玩家下线重登后属性还在、毒不发作**（回调丢了）。

**我方判据一句话：实例必须是 JSON。**

```ts
/** 内容层：纯数据 + id，**不含任何函数** */
export interface EffectDef {
  readonly id: string;                       // 全局唯一（G18 词表会收它）
  readonly name: string;
  readonly durationMs: number;               // 0 = 永不过期（要显式写，不许省略语义）
  readonly maxCount: number;                 // 层数上限；1 = 不叠层
  readonly stacking: Stacking;               // §34.3
  readonly prop?: Readonly<Partial<Record<PropKey, number>>>;  // ★ 每层叠加的属性
  readonly control?: ControlKind;            // 判别联合，不是任意标志位
  readonly tick?: TickSpec;                  // 周期效果，**数据**不是回调
  readonly flags?: readonly EffectFlag[];    // 'downside' | 'onlyCombat' | 'noResist' …
}

/** 运行时：只有数据，`JSON.stringify` 能原样回来 */
export interface EffectInstance {
  readonly id: string;
  count: number;
  expiresAt: number;                         // ★ 绝对时刻，不是"剩余毫秒"
  sourceId?: string;                         // 谁施加的（统计/仇恨/文案用）
}
```

**分派方式**：引擎按 `def.stacking` / `def.control` / `def.tick` 做**判别联合分派**，
`switch` 不留 `default`，末尾 `const _never: never = x`（33 册铁律 10：漏一支就编译报错）。

```
TickSpec = { readonly everyMs: number; readonly damage?: number; readonly damagePerLevel?: number }
ControlKind = 'busy' | 'stun' | 'cannotDodge' | 'cannotParry' | 'broken' | 'unseen'
```

★ `expiresAt` 存**绝对时刻**而不是剩余毫秒：剩余量每次读都要减，多读一次就多错一次；
绝对时刻是**幂等**的，重登/重算都不改变它。这也顺手绕开了 wushen 那个
「`duration` 存 0 表示无限、结果标志位反而为假」的坑。

## §34.3 叠加语义：三档，用字符串不用 0/1/2

| `stacking` | 重复施加同一 `id` 时 | 到期一次扣几层 |
|---|---|---|
| `refresh` | 层数不变，**重置 `expiresAt`** | 1（最后一层到期才清标志） |
| `stack` | `count = min(count + n, maxCount)`，重置 `expiresAt` | 1 |
| `replace` | **换新实例**（旧实例先按"减一层"结算） | 1 |

不抄 wushen 的 `override: 0/1/2`，因为数字在调用点看不出含义（`override: 1` 是"可叠"还是"覆盖"？
每次都要回去查表）。**字符串即文档。**

**必须修掉的三个 wushen 坑**：

1. **`replace` 且 `count > 1` 时被一次性删光** —— wushen 的 `remove_status` 对 `override !== 1` 直接移除、忽略 `count`。
   我方：**移除永远走「减一层」**，只有 `count` 归零才真正删实例、撤属性、清标志。
2. **`replace` 的 refresh 路径不减 `count`** —— 同一个函数两条路径对层数的处理不一致，减属性的份数就对不上。
   我方：**加减各只有一个入口**（`applyEffect` / `removeEffect(n)`），层数变化只在这两处发生。
3. **同一 `id` 被多个技能抢用** —— wushen 里 `force` / `weapon` 之类被多处当"唯一 buff 槽"，
   谁后挂谁覆盖，先挂的属性永远回不来。我方：**`id` 全局唯一（内容层定义处派生）**；
   需要"同类互斥"的场景用 `group` 字段表达，**不用共用 id**。

## §34.4 标志位与引用计数：谁都不许顺手清 0

`busy` 已实现，读路径只有 `busyRemainingMs()` / `isBusy()`（26 册 §49：同一个概念只许有一个答案）。
`effect` 要接进来，**只许调 `applyBusy(ms)` / `clearBusy()`，不许直接写字段**。

**为什么**：wushen 的 `change_buff(false)` 是无条件 `this.is_busy = 0`，不区分"还有没有别的同类 buff 在场"。
于是两个都带 `is_busy` 的 buff 同时存在时，**先到期的那个会把还该有效的控制清掉**。

我方两条规则：

1. **同一控制只有一个"占位者"**：记录 `controlOwner: { kind, effectId, expiresAt }`；
   新 effect 要占位时，与现占位者比 `expiresAt`，**晚者胜**（不是"后施加者胜"）。
2. **释放时必须核对身份**：`releaseControl(kind, effectId)` 只在 `controlOwner.effectId === effectId` 时生效。
   ⇒ "被别人顶掉的那方到期时"不会误清。

★ 这条要靠单测钉住：「两个效果同带 `busy`，先施加的先到期，另一个仍然 busy」。**不写这条测试就等于没做**。

## §34.5 到期：**单时钟扫描**，不是每个 buff 一个定时器

wushen 每个 buff 一个 `call_out`。21 册把它记成架构债（"千场战斗 = 千个定时器，无法统一暂停/回放"）。
我方只有一个时钟：`World.scheduler`（`server/engine/scheduler.ts`，缺它抛错，26 册 §54）。

**到期由 tick 扫出来，不是"定时器自己回调"**：

- 扫描判据只有一句：`instance.expiresAt <= now` ⇒ 结算到期
- `scheduler.schedule()` 只用来排**下一次扫描时刻**（取所有实例里最小的 `expiresAt`），
  **不为每个实例各排一个任务**
- 好处：离线/暂停/单测都能用 `scheduler.step(nowMs)` 精确推进，不依赖真实时间

**`TempStore` 只做数据、不做行为（★ 容易做错的一点）**：

- `TempStore`（`server/engine/temp.ts`，已实现）回答的是「**还有多久**」；
- 它**不回答**「**到期时要做什么**」（撤属性、清标志、播文案）。
- ⇒ 属性叠加可以借它的 TTL，但**到期动作必须由扫描驱动**。
- 反例：只挂 TTL、不注册到期动作 ⇒ 重登后那条"早就过期"的记录**永远不会被结算**，
  属性一直挂着 —— 这正是 wushen「毒不发作但属性还在」的另一种形状。

**装载时先扫一遍**：`loadProps()` 同族的准入（26 册 §40 的分级：条目级坏 ⇒ 丢+记账；
正常过期 ⇒ 丢但**不**记账）。**过期的效果算"正常过期"，不记账。**

## §34.6 存档契约

- 存 `{ id, count, expiresAt, sourceId? }`，就这四个字段，多一个都不存（存了就会与 def 双份真相）
- 重登：按 def 重建 → 重算属性（`recount()`）→ 重排下一次扫描
- `def` 找不到（内容改名/删了）⇒ 按条目级坏处理：**丢掉 + 记账**（`LoadReport`），不许静默留一条空壳
- **不存**：`state`（打坐/疗伤）、`busy`。二者都是"人在这一次会话里正在做什么"，跨会话没有意义

## §34.7 `state` 行动状态机（打坐 / 疗伤）

我方已有**门禁桩**：`command.ts` 的 `state: { readonly title: string } | null` + `checkCommandGates()`。
本册把它补成真状态机。

```ts
export interface ActivityDef {
  readonly id: string;
  readonly title: string;          // 面板/提示文案，例："打坐"
  readonly tickMs: number;         // 每拍间隔（wushen 的 `rate`，单位是秒；我方统一毫秒）
  readonly tick: (actor, ctx) => ActivityResult;   // ★ 这是**引擎侧**函数，不进存档
  readonly allowCommands: readonly string[];        // 白名单：状态中仍可用的指令
}

export type ActivityResult =
  | { readonly kind: 'continue' }
  | { readonly kind: 'stop'; readonly reason: InterruptReason }
  | { readonly kind: 'done'; readonly message?: string };

export type InterruptReason = 'damaged' | 'moved' | 'player-stop' | 'busy' | 'died' | 'resource-full';
```

- **驱动**：`scheduler.every(def.tickMs, …)`。**差异**：wushen 用 `heart_beat` 每 `rate` 拍，
  我方用调度器 ⇒ 可暂停（战斗时停表）、单测可 `step()` 推进，不睡真实时间。
- **互斥**：进入前查 `isBusy()`；进入后 `state !== null` ⇒ 只放行 `allowCommands`
  （这就是 `checkCommandGates` 已经在判的那条，**别另写一份**）。
- **三件必须有的中断**：受击、切房间、`busy`。三者用**判别联合**`InterruptReason`，
  而不是各自 `notify` 一句不同的话 —— 文案由 `reason` 在一个地方映射，否则同一句提示会写三遍还写不一致。
- **`tick` 不进存档**：它是引擎函数；`state` 本来也不存档（§34.6），所以这不矛盾。
  ⇒ 与 `effect` 的 `TickSpec`（数据）是**两种不同的东西**，别为了"统一"把 `state.tick` 也变成数据。

## §34.8 前后端同步：一份帧，一个 `action` 字段

wushen 有 `notify_status`（全量）/ `appdend_status`（追加）/ `status_changed`（增量）**三段手拼 JSON**，
`duration` / `overtime` / `count` 各写一遍 ⇒ 三处逻辑几乎重复。

我方：

- **只有一种帧**，用 `action` 区分：`'list'`（全量，进房间/重登用）/ `'add'` / `'refresh'` / `'remove'`
- 必须走 `packet()` 发送点 + 进 G2 台账（`SERVER_PACKET_UNWIRED`），**禁手拼 JSON 字符串**
  —— 这是 §55 已经定过的红线（JSON 通道绕过控制字符过滤）
- 帧里给**绝对到期时刻**（`expiresAt`），不给"剩余秒数"：前端自己算进度条，
  否则每个客户端都要减一次，网络延迟还会让它们各减各的

## §34.10 明确不抄的六条

| wushen 做法 | 抄了会怎样 | 我方做法 |
|---|---|---|
| buff 实例里存 `on_interval` 等**闭包** | 实例不可序列化 ⇒ 下线丢回调（**属性在、毒不发作**） | `EffectDef`（数据，内容层）+ `TickSpec`（数据）；引擎按 kind 分派（§34.2） |
| `is_busy = buff.duration`（**存毫秒当布尔**） | `duration = 0` 的常驻控制反而失效；语义二义 | 控制只有 `controlOwner` 一个占位 + 绝对 `expiresAt`（§34.4） |
| `override: 0/1/2` 数字 | 调用点看不出含义，每次回去查表 | `stacking` 字符串三档（§34.3） |
| 每个 buff 一个 `call_out` | 千场战斗千个定时器，无法暂停/回放 | 单时钟 + tick 扫描（§34.5） |
| `notify_status` / `appdend_status` / `status_changed` 三段手拼 JSON | 三份渲染逻辑必然分家 | 一份帧 + `action` 字段（§34.8） |
| `remvoe_statuses(func)`（谓词清理，且拼错了） | 谓词参数没有类型约束，调用点靠猜 | 清理入口收成**枚举**（`'all-downside' \| 'only-combat' \| 'by-group'`），不用谓词 |
