## 一分钟总览：一个角色的数字是怎么来的

> **只读这一节就能上手**，后面各节都是它的展开。
> ★ 下面的数值只是**演示**（取自游戏里真实存在的「扬州城 · 小二」），
> 真实取值一律以 `formula.ts` 为准 —— 本册不复制数值（见本册顶部纪律）。

**整条链路只有四步**：

```
  ① 先天属性（人物自带，写在 def 里）
     str 臂力 / con 根骨 / dex 身法 / int 悟性 / maxMp 内力上限
              │
              │     ② 后天 prop（装备 / 技能 / BUFF 给的"加成"）
              │        例：基本内功 30 级 ⇒ prop(con) += 3
              ↓
  ③ 公式（**只有一份**：`formula.ts` → `computeDerived()`，纯函数）

       先天   ＋   加成   ──→   × 百分比修正（`*_per` 族）  ──→   ④ 派生战斗属性（只读）
              ↑
        这两者是**两个不同的量**，别混（见术语表 C 组）

  ④ 派生结果（代码里读 `character.derived.X`，改不了 —— 只有 `character.ts` 能写）
     attack 攻击 · defense 防御 · hit 命中 · evasion 躲闪 · deflect 招架
     crit 暴击 · attackSpeed 攻击速度 · maxHp 气血上限
     damageReductionPer 伤害减免 · ignoreDefensePer 忽视防御（这两项是透传）
```

**拿小二走一遍**（`con=27`、`maxMp=150`、没练内功 ⇒ `forceRad=0.1`、基本内功 30 级 ⇒ `prop(con)=3`）：

| 步骤 | 算什么 | 算式 | 结果 |
|---|---|---|---|
| 1 | 气血的**先天部分** | `con × 5` = 27 × 5 | 135 |
| 2 | 气血的**内力部分** | `maxMp × forceRad` = 150 × 0.1 | 15 |
| 3 | 气血的**根骨加成部分** | `prop(con) × con` = 3 × 27 | 81 |
| 4 | 三部分相加，再乘气血百分比（此处为 0） | `int(135 + 15 + 81)` | **maxHp = 231** |

⇒ `小二.maxHp === 231`；而 def 里写的初始 `hp: 150` 小于上限，不会被 `setHp()` 截断。

★ **这张表里藏着三个"本项目已经踩过"的坑**：

1. **第 3 步不除 10**，但同一份代码里算「**防御**」时 `prop(con)` **要除 10** ——
   同一个量两种算法，是**原作如此**（§29.2「三处原作不一致」②，别顺手统一）；
2. **第 2 步只有「气血」有**，其余七项都没有（§29.2「三处原作不一致」③）；
3. 早期这里写着「内容层没有 `con` 生产者 ⇒ 影响为零」—— **这句是错的**：
   `world/skill/base/force.ts` 一直在给 `prop.con`。2026-10-14 复查订正（见 §29.4 偏离①）。

**想改？三条路，别走错**：

| 你想做什么 | 去哪一节 |
|---|---|
| 改一个**数字**（比如根骨系数 5 → 8） | **§29.3** 参数表 → `COMBAT_FORMULA` 里那一个键 |
| 改**公式形状**（加一项、改括号、把百分比提到括号外） | **§29.2** 逐式对照，**且**必须按 §29.4 登记偏离 |
| 改**容器容量**（背包 / 房间 / NPC 携带） | **§29.5** |
| 以后统一调数值 | **§29.12 调参清单**（旋钮总表 + 流程 + 待办） |

### C. ★ 最容易看错的两组

1. **同名不同物（`str` 有两个身份）**：`str` 既是**先天臂力**，又有一个 **prop 键 `str` = 臂力加成**。

## 29.1 三层结构（照抄 wushen 里"对的那部分"）

wushen 的属性其实分三层（08 册 §8.7 第 1 条），本项目**保留这个分层**：

```
先天属性（人物自带，不是 prop）
    str 臂力 / con 根骨 / dex 身法 / int 悟性   （另有 maxMp 内力上限 → 喂气血）
  + 后天 prop（装备 / 技能 / BUFF 给的加成，全部走 props.ts 的访问器）
    例：prop(gj)=攻击加成、prop(str)=臂力加成、prop(con)=根骨加成、prop(hp_per)=气血百分比
  × 百分比修正（`*_per` 族：gj_per / fy_per / mz_per / ds_per / zj_per / hp_per / gjsd_per）
    写 50 = +50%
  → 派生战斗属性（只读）
    gj 攻击 / fy 防御 / mz 命中 / ds 躲闪 / zj 招架 / bj 暴击 / gjsd 攻击速度 / maxHp 气血上限
```

**为什么值得照抄**：调平衡时"改先天"和"改装备加成"是两件独立的事 —— 前者动人物模板，
后者动装备/技能表；两者都通过**同一条百分比修正**收口。混成一层就没法单独调。

**本项目相对 wushen 加的结构保证**：

- **公式只有一份**：`computeDerived()` 是纯函数，`Character.recount()` 只是调用它并装回结果。
  wushen 把同一套 `recount` **写了两遍而且两遍不一样**（见 §29.2 末的「wushen 自己的缺陷」）——
  本项目在结构上让这类"同名不同算法"**不可能发生**。
- **派生值只读**：派生结果存在 `Character` 的 TS 私有字段里，**只有 `character.ts` 自己能写**，
  连子类都碰不到。于是"改了 `str` 却忘了重算攻击"这个 wushen 里反复出现的错**在结构上不存在**
  （`setInnate()` / `loadProps()` 内部自动 `recount()`）。
- **参数进表**：所有数值进 `COMBAT_FORMULA`，公式体只做算术 —— 调参不必读公式，读公式不必猜参数。

## 29.2 逐式对照（本项目 ↔ wushen 原作）

> **对照口径**：以 wushen `world/extends/char/user.js`（玩家走的版本，`:2-32`）为准；
> `world/extends/char/combat.js`（`:2-19`）只在末尾单独说。
> **本项目出处**统一在 `formula.ts:computeDerived()`；`int(x)` = 向零截断（同 wushen `parseInt`）；
> `scaled(x, per)` = `x * (100 + per) / 100`。**逐式都逐字核过源码，不是读文档转抄。**
> ★ **本项目派生字段用英文常见名**（`attack`/`defense`/…），**wushen 的键名是拼音缩写**
>   （`gj`/`fy`/…）—— 两者靠 `PROP` 别名表对接（`PROP.attack === 'gj'`，见 §29.10）。
>   公式里的 **`prop(x)` = 后天加成**、**裸 `x` = 先天值**。

| 派生字段 | 中文 | wushen 键 | 本项目公式（`formula.ts`） | wushen 公式（`world/extends/char/user.js`） | 一致？ |
|---|---|---|---|---|---|
| `maxHp` | **气血上限** | `max_hp` | `int(con*5 + scaled(maxMp*forceRad + prop(max_hp) + prop(con)*con, hp_per))` | `:3-4` `parseInt(con*5 + (max_mp*force_rad + prop(max_hp) + prop(con)*con) * (100+hp_per)/100)` | ✅ 一致（★ 2026-10-14 起 —— 见**偏离①**；⚠️ 同一个 `prop(con)` 在本表 `defense` 里是 `/10`、这里**不除** —— 原作如此，见下方「三处原作不一致」） |
| `attackSpeed` | **攻击速度**（毫秒/次，越小越快） | `gjsd` | `g = 4000 - prop(gjsd)`；`g>500` 时 `int(scaled(g, -prop(gjsd_per)))` 再取下限；否则 500 | `:8-14` 同式（`parseInt(g - g*gjsd_per/100)`，下限 500） | ✅ 一致 |
| `attack` | **攻击** | `gj` | `int(str + scaled(prop(gj) + prop(str)*(str/10), gj_per))` | `:16` `parseInt(str + (prop(gj) + prop(str)*str/10) * (100+gj_per)/100)` | ✅ 一致（★ 2026-10-14 起 —— 见**偏离③**） |
| `defense` | **防御** | `fy` | `int(scaled((str+con)/10 + prop(fy) + prop(con)*(con/10), fy_per))` | `:17` `parseInt(((str+con)/10 + prop(fy) + prop(con)*con/10) * (100+fy_per)/100)` | ✅ 一致 |
| `hit` | **命中** | `mz` | `int(scaled(dex*0.5 + prop(mz), mz_per))` | `:18` `parseInt((dex/2 + prop(mz)) * (100+mz_per)/100)` | ✅ 一致 |
| `evasion` | **躲闪** | `ds` | `int(scaled(dex*0.5 + prop(ds) + prop(dex)*(dex/10), ds_per))` | `:19` `parseInt((dex/2 + prop(ds) + prop(dex)*dex/10) * (100+ds_per)/100)` | ✅ 一致（**但缺钩子**，见下） |
| `deflect` | **招架** | `zj` | `int(scaled(str*0.5 + prop(zj) + prop(str)*(str/10), zj_per))` | `:23` `parseInt((str/2 + prop(zj) + prop(str)*str/10) * (100+zj_per)/100)` | ✅ 一致（**但缺钩子**，见下） |
| `crit` | **暴击** | `bj` | `int(dex*0.1 + prop(bj_per))` | `:27` `parseInt(dex/10 + prop(bj_per))` | ✅ 一致（`bj_per` 是**平加**、不乘百分比，照抄） |
| `damageReductionPer` / `ignoreDefensePer` | **伤害减免** / **忽视对方防御** | `diff_sh_per` / `diff_fy_per` | 原样透传 | `:28` / `:31` 原样透传 | ✅ 一致 |
| （`hp` 上钳） | **气血钳到上限** | — | `recount()` 里 `if (hp > maxHp) hp = maxHp` | `:6` `if (this.hp > this.max_hp) this.hp = this.max_hp;` | ✅ 一致（**只钳 hp、不钳 mp** —— 见 §29.6 E9） |

### ★ 三处"原作自己的不一致"（**逐式照抄，不许代为统一**）

wushen 的 `recount` 里有三处"**同一个量在不同式里算法不同**"。它们看着都像笔误，
但原作的两处分身（`user.js` 与 `combat.js`）**都这么写** ⇒ 是原作如此，不是抄漏。
本项目**一律照抄**，并且每一处都配了**正反两个测试锚点** —— 谁顺手"修正"成一致，谁红。

| # | 哪里不一致 | wushen 原式 | 本项目 | 钉住它的测试 |
|---|---|---|---|---|
| **①** | **`gj` 的先天 `str` 在百分比「外」** —— 其余四式的先天项都在百分比「内」 | `:16` `str + (prop(gj)+prop(str)*str/10) × (100+gj_per)/100` | 同（见**偏离③**） | `describe('…gj 的口径…')` 4 条，**含 `fy` 对照组**证明"只有 gj 在外" |
| **②** | **同一个 `prop(con)`：`max_hp` 不除 10、`fy` 除 10** | `:3` `prop("con")*con`（不除）／`:17` `prop("con")*con/10`（除） | 同（见**偏离①**） | 「根骨加成项不除 propScaleDivisor」+「同一个 prop(con) 在 maxHp 与 defense 里算法不同」 |
| **③** | **`max_hp` 独有「内力上限 × 内功系数」项**，其余式都没有 | `:3` `max_mp * query_force_rad()` | 同 | 基线逐项对账的 `maxHp: 200` |

> **为什么值得单列一张表**：这三处是"以后调数值时最容易被人顺手改掉"的地方 ——
> 它们都**长得像 bug**，而且在没有锚点的情况下改掉它们**不会让任何测试变红**。
> 一旦被"统一"掉，本项目就会**静默偏离原作**，而这种偏离要等到"复刻 wushen 内容时
> 发现数值对不上"才暴露 —— 那时已经很难定位到是哪一式。
>
> **判断口诀**：看到公式里有个地方"跟别处不一样"，**先去 wushen 源码核**，

> **换成人话读一遍**（以全 20 的裸角色为例，无任何加成）：
> **攻击 20 = 臂力 20**；**防御 4 = (臂力 20 + 根骨 20) ÷ 10**；
> **命中 10 = 身法 20 ÷ 2**；**躲闪 10 = 身法 20 ÷ 2**；**招架 10 = 臂力 20 ÷ 2**；
> **暴击 2 = 身法 20 ÷ 10**；**气血上限 200 = 根骨 20 × 5 + 内力 100 × 内功系数 1**（无内功时系数是 0.1 ⇒ 110）；
> **攻击速度 4000 毫秒 = 4 秒一击**。
>
> ★ **字段名与实际值**：代码里读 `character.derived.attack` / `.defense` / `.hit` / `.evasion` /
>   `.deflect` / `.crit` / `.attackSpeed` / `.maxHp` / `.damageReductionPer` / `.ignoreDefensePer`。


**两处"缺钩子"（属未做的技能批次，不是笔误）**：wushen `:20-22` 在 `ds` 之后额外加

本项目没有这两个钩子的消费者（技能第三档 / 养成批次未做）⇒ **现在不实现**。补的时候要在
`computeDerived()` 里加**显式入参**（不能去读 `Character`，否则纯函数性质就没了）。

### 29.2.1 wushen 自己的缺陷：`recount` 写了两遍、四个归属、两套算法

这是本项目**不抄**的部分，也是 E1 之所以"看起来像笔误其实是原作如此"的根源：

| wushen 归属 | 出处 | 特点 |
|---|---|---|
| `USER.prototype.recount`（玩家） | `world/extends/char/user.js:2` | `/10` + `max_hp` + dodge/parry 钩子 |
| `FOLLOWER.prototype.recount` | `world/extends/char/user.js:193`（**= `USER.prototype.recount` 别名**） | 同玩家 |
| `CHARACTER.prototype.recount`（NPC 等） | `world/extends/char/combat.js:2` | **`ds`/`zj` 用 `/5`（不是 `/10`）**、**完全不算 `max_hp`**、无钩子 |
| （继承关系） | `NPC.inherits(CHARACTER)`（`os/char/npc.js:9`）→ 走 combat.js 那版 | — |

⇒ **同一个"人物"，玩家与 NPC 走的是两套系数**（`ds`/`zj` 的换算项一个 `/10` 一个 `/5`），
而且 NPC **根本没有 max_hp 重算**（`os/char/npc.js:3` 直接写死 `hp = max_hp = 100`）。
这不是设计，是两份实现各自演化的结果（22 册 / 21 册据此立的缺陷条目）。

**本项目的处置**：**只有一份 `computeDerived()`，玩家与 NPC 走同一套**（`/10` 口径）。
后果是**已知偏离④**（见 §29.4）：NPC 的 `ds` 躲闪 / `zj` 招架 / `max_hp` 气血上限 与 wushen NPC 算出来的**不一样**。
这是"单源化"的**有意代价** —— 我们选的是玩家那套（更完整、带 `max_hp`），并接受与 wushen NPC 分家。

> ★ **订正（2026-10-14 复查）**：这一段原先指向「偏离③」，而 §29.4 的偏离③ 是 `gj` 口径 ——
> 指针错了一年多的账。NPC 分家这一条此前**根本没有登记条目**，现补为**偏离④**。

## 29.3 参数表（`COMBAT_FORMULA`，**单源在 `formula.ts`**）

本册**不抄数值**，只列"有哪些旋钮"及其含义；**取值以 `formula.ts` 为准**，启动日志会打印全量。

| 键 | 含义 | 用在哪（派生量） |
|---|---|---|
| `hpPerCon` | 气血基础系数（**根骨 × 系数**） | `maxHp` 气血上限 |
| `attackIntervalMs` | 攻击间隔基准（ms） | `gjsd` 攻击速度 |
| `attackIntervalFloorMs` | 攻击间隔下限（防"攻速堆到 0 死循环"） | `gjsd` 攻击速度 |
| `innateDexPer` | 先天**身法**系数（**命名刻意中性**：同时喂 `mz` 命中与 `ds` 躲闪） | `mz` / `ds` |
| `deflectPerStr` | **招架**的先天部分（**臂力 × 系数**） | `zj` 招架 |
| `defenseBaseDivisor` | **防御**先天部分除数（**（臂力+根骨）÷ 除数**） | `fy` 防御 |
| `propScaleDivisor` | "属性换算加成"除数（`prop(x) * x / 除数`） | `maxHp`/`fy`/`ds`/`zj`/`gj` |
| `critPerDex` | **暴击**先天部分（**身法 × 系数**） | `bj` 暴击 |
| `forceRadDefault` | 无内功时的**内功系数**（**必须照抄 wushen 的 0.1**，不是 1） | `maxHp` 气血上限 |

★ **`innateDexPer` 为什么叫这个名字**（**别**按某一个消费者命名；旧名 `dodgePerDex` 就是反例）：
wushen 的 `mz`（`:18`）与 `ds`（`:19`）都写死 `this.dex / 2` —— 是**一个**系数喂两条公式。
若命名成 `evasion*`，调躲闪时会顺手改到命中，而且改完两边都"看起来对"（26 册 §25）。
这条由 `engine-formula.test.ts` 的「`mz` 与 `ds` 共用同一个先天 dex 系数」钉住。

★ **`forceRadDefault = 0.1` 的理由**：`query_force_rad()`（`os/char/chara_prop.js:20-22`）由**生效内功
技能模板**上的常量 `force_rad` 决定、与等级无关；实测 wushen 全部内功心法都落在 0.5–0.9
（`taijishengong 0.8` / `baiyunxinfa 0.75` / `gaibangxinfa 0.5`），而连 `base/force` 都没有 `force_rad`
⇒ 走 0.1 兜底。所以 **0.1 = "没练内功"这个真实状态**；写成 1 会让所有裸角色的气血凭空多 10 倍内力项。

## 29.5 容器容量（第二组"设计数字"）

数值/公式之外，"装得下几个"也是一族要反复调的设计数字。它与战斗派生**不同源**，
但同样**单源在代码**，一并收在本册。

| 容器种类 | 缺省容量 | 常量（单源） | 与 wushen |
|---|---|---|---|
| 房间 | **50** | `room.ts` → `DEFAULT_ROOM_CAPACITY` | ✅ 照抄，`os/room/room.js:9` `max_item_count = 50` |
| 玩家 | **50** | `character.ts` → `DEFAULT_CHARACTER_CAPACITY` | ⚠️ **有意偏离**，wushen `os/char/user.js:5` 是 **20** |
| NPC | **10** | `npc.ts` → `DEFAULT_NPC_CAPACITY` | ✅ 照抄，来自**基类** `os/item.js:67` `ITEM.prototype.max_item_count = 10`（继承链：`os/char/npc.js:9` `NPC.inherits(CHARACTER)` → `os/char/character.js:10` `CHARACTER.inherits(ITEM)`）。⚠️ 早期误引 `os/char/follower.js:12`（那是**随从**、不是 NPC），2026-10-14 订正 |
| 泛型 `Container`（基类） | **不限**（`+∞`） | `base.ts` 构造缺省 | — 基类**不给**缺省，缺省由子类给 |

- ★ **基类缺省是"不限"是刻意的**：`Container` 是通用抽象（"能装东西的东西"），把 50 写进基类
  会让"房间 50 / 玩家 50 / NPC 10"三档**看起来像巧合**、且新种类会**静默继承一个不合适的数**。
  "缺省由子类给"这条由 `tests/engine-base.test.ts` 的「默认容量不限」钉住（**成对**用例）。
- ★ **"不限"曾是 E8 的症状**：角色/NPC 原先走基类缺省 ⇒ **背包/携带无上限**。B 批 `get` 接上后
  即成真问题。现已由三个常量收口。
- **回归**：`tests/engine-capacity.test.ts`（6 条）—— 三档缺省 + 显式覆盖 + 三档都有限 +
  **缺省真的被 `addItem` 用上**（装满后抛 `ContainerError`，防"只写在字段里没人读"）。
- ⚠️ **`maxItems` 与 `isFull()`/`addItem` 是同一个阈值**：容量判据**只此一处**（`base.ts:isFull()`），
  `addItem` 的抛错也调它 —— 两处一旦漂移，就会出现"`isFull()` 说没满、`addItem` 却抛"的鬼故事。

## 29.10 命名对照表（★ 复刻 wushen 时查这一张）

**三层名字，各管各的**：

| 层 | 长什么样 | 权威来源 | 能不能改 |
|---|---|---|---|
| **代码名**（本项目） | `derived.attack` / `PROP.attack` | `server/engine/formula.ts`（派生字段）、`shared/constants.ts` 的 `PROP`（prop 键别名） | ✅ 可以改（改的是**可读性**） |
| **数据键**（= wushen 键） | `'gj'` / `'max_hp'` | `shared/constants.ts` 的 `PROPERTIES` | ❌ **不能改** —— 内容层 / 协议帧 / 存档都在用 |
| **中文名** | 攻击 / 气血上限 | `shared/constants.ts` 的 `PROPERTIES` | ✅ 改（只影响显示） |

> **为什么数据键不改名**（2026-10-14 的裁定，理由有三）：
> ① 内容层脚本直接写 `prop: { gj: 20 }`（`world/**`）—— 改名等于**全部内容脚本都要改**，
>    而且从此**不能照抄 wushen 的内容**；
> ② **协议帧**用这些键（`shared/protocol.ts` 的 `sc` 帧有 `max_hp` / `max_mp`，
>    前端与端到端测试都按这个读）；
> ③ **存档**是持久化格式，改键 = 老档读不回来。
> ⇒ 于是折中：**数据层照抄 wushen，代码层用英文常见名**，中间由 `PROP` 别名表对接。

> ★★ **还有第 4 个命名空间：技能 id**（`force` / `dodge` / `parry` / `bite` / `sword` / `blade` / …，
>   见 `shared/constants.ts` 的 `BASE_SKILLS` / `WEAPON_TYPE` / `ENABLE_SLOTS`）。
>   wushen 原作靠 **"属性用拼音、技能用英文"** 把这两层岔开（`os/const.js`：属性 `ds`/`zj`，
>   技能 `dodge`/`parry`）；本项目把属性改成英文可读名之后**一度撞了回去** ——
>   躲闪/招架曾叫 `dodge` / `parry`，而那正是 `BASE_SKILLS` 的技能 id
>   （内容挂在 `wushen/world/skill/dodge|parry/` 下），grep 一下分不清命中的是哪一层。
>   ⇒ 2026-10-14 定为 **`evasion` / `deflect`**，并由闸门 **G3.G** 机械守住
>   "**数值侧名字（`PROP` 别名键 ∪ `DerivedCombat` 字段）⊥ 技能槽词表**"（26 册 §34）。

## 29.11 属性键英文化 · 词干对照表（★ 草案 v2 待批 · 2026-10-14）

> **起因**：用户拍板「**连内容层一起全改英文**」—— 即 `PROPERTIES` 的数据键不再保留 wushen 拼音缩写。
> 本节是**动手前的对照表**；批准后表格转正、本节成为本次改造的规格。**未批准前不动代码。**
>
> ★ **v2 修正（2026-10-14 晚）**：v1 的约定①「加成键加 `*Bonus` 后缀」**是错的** ——
> 它会**打穿 `ModProp` 派生族**（核心键若叫 `attackBonus`，就派生出 `diff_attackBonus`、`attackBonus_per`）。
> v2 改为「**核心键 = 英文 snake_case 裸名词；派生键跟着核心键自动生成**」。依据是 `shared/constants.ts#ModProp`。
>
> ★ **定位变更**：用户已明确「**只学 wushen 的架构；数值与派生值后续都会替换、不照抄 wushen 数据**」。
> ⇒ 本节从"**逐字照抄的翻译表**"降级为"**读懂 wushen 来源的索引**"，只要求**词干级对应**
> （`ds` 是躲闪、`dodge` 是技能 id 这类粒度），**不要求** wushen 键与本项目键逐条双射。
>
> ⚠️ **先读 §29.11.1**：**全长键不必逐条背** —— 由 §29.11.2 的**词干表展开**即可。

### 29.11.1 命名约定（三条）

| # | 约定 | 例 |
|---|---|---|
| ① | **核心键 = 英文 snake_case 裸名词**（不加 `Bonus`/`Per` 之类后缀） | `attack` · `defense` · `hit` · `evasion` · `deflect` · `damage` · `attack_speed` · `max_hp` |
| ② | **派生键跟着核心键自动生成，不单独起名** | 规则 = `shared/constants.ts#ModProp`：`<c>_per` / `diff_<c>` / `diff_<c>_per` / `add_<c>` / `add_<c>_per` |
| ③ | **数据键 / 协议 wire / 内容层 `prop:{}` 同一套**（都是 snake_case） | 内容层 `prop: { gj: 20 }` → `prop: { attack: 20 }` |

★ **②是 v2 的核心修正**：**只有"核心键"的名字是自由的** —— `_per` / `diff_` / `add_` 那些名字由核心键**机械生成**。
这正是条①**不能**写成"加成键加 `*Bonus` 后缀"的原因：后缀会被卷进派生规则，生成 `diff_attackBonus` 这类怪键。

★ **③的副作用（须有意识接受）**：改名后，**"数据键 ⊥ 派生字段"这条不再成立，也不该成立**。
wushen 本身就是 `prop.gj`（**加成**）与 `this.gj`（**算出的值**）**同名不同物**，靠 receiver 区分；
本项目变成 `props.attack`（加成）vs `derived.attack`（值），**同样靠 receiver 区分**。
⇒ 这是"学 wushen 架构"的一部分，**接受它**，不要再试图用后缀把两者岔开。

★ 反面：**不要**出现"英文词干 + 拼音尾巴"的混血键（`attack_per` 改对了、`gj_per` 却留一半）。
§29.11.2 的词干表就是为消除这种半改状态而设。

## 29.13 ★ 有效属性归一（**门槛口径**，2026-10-15 用户裁定）

> 裁定原话：「先天属性和后天属性统一一下吧，实际有效属性=先天+后天，然后各种限制改为实际有效属性，
> 顺便统一一下省得到时候什么 str 和 str1 啥的」。
> 落地记档见 **26 册 §37**；本条是**数值册侧**的权威定义。

### 29.13.1 一句话定义

**有效属性 = 先天值 + 后天加成**。定义为**单一函数**：

```
server/engine/formula.ts
  export function effectiveAttr(innate, props, key): number   // = innate[key] + getProp(props, ATTR_BONUS[key])
  export function isAttrKey(key): key is AttrKey             // 'str' | 'con' | 'dex' | 'int'
```

- **适用**：**一切门槛 / 限制** —— 学条件 `SkillLearnCondition.minAttr`（今天的唯一消费者）、
  将来的装备穿戴要求、转职条件……
- **不适用**：**派生公式**（`computeDerived()`）。⚠️ **这一条是本节最要紧的话**，见 29.13.2。

### 29.13.2 ⚠️ 为什么**门槛**能合并、**公式**不能合并

`computeDerived()` 里先天与后天加成**出现的位置不同**，是**逐式照抄 wushen** 的结果：

| 派生值 | 表达式（`formula.ts`） | 先天项位置 |
|---|---|---|
| `attack` | `str + (prop_gj + prop_str * str/10) * (1+gj_per/100)` | 百分比**外** |
| `defense` | `((str+con)/10 + prop_fy + prop_con * con/10) * (1+fy_per/100)` | 百分比**内** |
| `maxHp` | `con*5 + (maxMp*forceRad + prop_max_hp + prop_con*con) * (1+hp_per/100)` | 百分比**内**，且 `prop_con*con` **不除 10** |

而 `defense` 里同一个 `prop_con*con` 却**除 10**（wushen 自身的不一致，见 §29.4 偏离①）。

⇒ 若先把 `str`/`con` 合并成"有效值"再代入，**五式全部改变数值**，且**偏离 wushen**。
所以：**门槛读合成值、公式读分开值** —— 这不是妥协，是两件事。

★ 与之配套的一条纪律：`Character.str/con/dex/int` 四个 getter **返回有效值**（内容层口径统一），
裸先天值只在 `Character.innateSnapshot()`（`protected`）里可见 —— 派生公式要的是**分开的**先天。
**谁要把 `innateSnapshot()` 换成四个 getter，先看 26 册 §37 的锚点**（会红）。

### 29.13.3 为什么可以合并：wushen 内容的实证

担心"合并会丢能力"（wushen 有三档：`str1` 纯先天 / `str` 先天+加成 / 其它 纯加成）——
**实测扫了 wushen 全仓 `learn_condition` 块（94 个，含 `os/` 与 `world/`），顶层键只有四个**：

| 键 | 次数 | 合并后由谁承载 |
|---|---|---|
| `skill` | 94 | `minSlot` |
| `max_mp` | 80 | `minMaxMp` |
| `dex1` | 2 | `minAttr`（有效值，见下注） |
| `int1` | 1 | `minAttr` |

- **`str`/`con`/`dex`/`int`（先天+加成的合计档）：0 处**
- **`gender`：0 处**（wushen 有读它的代码 —— `os/cmd/comm/zigong.js:10`、`world/obj/cash/bian.js:17` —— 但内容从未填；属防御性死代码）
- **裸 prop 键：0 处**

出现 `*1` 的 3 处：`world/skill/dodge/shenxingbaibian.js`（`dex1:20, int1:20`）、`world/skill/dodge/sixiangbu.js`（`dex1:20`）。

> ⚠️ **唯一的语义漂移**：wushen 的 `*1` 是**纯先天**，合并后读**有效值**（更宽）。
> 上面那 3 处阈值都是 20、先天四维建号即 15–30（见 05 册 5.1.4）⇒ 影响极微。
> ★ 若将来真的需要"只看先天"的门槛，**那时再加**一个显式字段（按项目纪律：
> 不留没有消费者的空接口，见 `defs.ts` 的 `SkillLearnCondition` 注释）。

### 29.13.7 三档怎么**读出来**（2026-10-15 补，26 册 §39）

归一只解决"判定读哪个数"，**不解决"怎么把三档分别取到手"**。原先的现状：

| 档 | 读取口 | 顺手？ |
|---|---|---|
| ③ **合计**（有效值） | `Character.str/con/dex/int`（getter） | ✅ |
| ② **后天加成** | `getProp(char, PROP.strengthBonus)` —— 要知道底层键、要 import `getProp` | ⚠️ |
| ① **先天** | —— | ❌ **取不到**（`innateSnapshot()` 是 `protected`，只喂公式） |

⇒ 补一条**只读**通道（数据一个字节没变，只是把既有三档"摊开"）：

- `formula.ts#computeAttrBreakdowns(innate, props): readonly AttrBreakdown[]`
  —— 行序恒为 `ATTR_KEYS`；`total` **交给 `effectiveAttr()`** 算 ⇒ **仍是一处口径**；
  额外给出的只是 `innate` 与 `bonus` 两档分开值。
- `Character.attrBreakdowns()`（= `CommandActor` 契约）→ 内容层（`world/command/**`）可直接调。
- 消费点：`world/command/info/score.ts`（`score` / `attr`），输出
  `臂力 25（先天 20 + 后天 5）`。这正是 wushen `score` 面板的摆法
  （`world/cmd/dialog/score.js:90-97` 的 `str_add`… 就是 `query_prop` = 后天加成）。

★ **`AttrKey` 现在由值表派生**（`export const ATTR_KEYS = ['str','con','dex','int'] as const`），
不再手写一份联合类型 —— 想加第五维只改一处（铁律 4）。
★ 为什么"先天"不放宽成公开字段：那正是 wushen `str`/`str1` 翻车的入口；
现在它**只在这条只读通道里以"被展示的一档"出现**，无法被顺手拿去当游戏逻辑的输入。
★ 口径守卫：`tests/engine-formula.test.ts` 的「`computeAttrBreakdowns`」三例
（合计 = 先天+后天 = `effectiveAttr`；后天档只读 `prop`；行序 = `ATTR_KEYS`）。
