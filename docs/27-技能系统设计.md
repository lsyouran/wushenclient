## 0. 一句话结论

wushen 的技能系统里，「**三档属性 + 装配槽 + 绝招子对象**」这套骨架是对的、值得抄；
但它的**属性挂载方式（release→改→attach 三角）会漂移**、**基本技能槽的词汇表是隐式的**、
**绝招和 BUFF 全靠"持续时间数值挂在角色字段上"**——这三处是必须改的。

本提案的核心是**先定词汇表、再定挂载模型**，其余（等级/经验/学习条件）都可以照抄 wushen 的数值。

## 2. wushen 现状解剖

### 2.1 两张表：技能是"全局模板"，等级是"角色记录"

```
WORLD.SKILLS[id] = SKILL 实例          ← 全局唯一（模板）
CHARACTER.skills[id] = { level, exp, enable_skill, [槽]=true, addin[], ref }   ← 每个角色一份
```

| 侧 | 关键点 | 证据 |
|---|---|---|
| 模板 `SKILL` | `id/name/type/grade/score` + `can_enables[]` + `pfm{}` + `query_prop/query_enable_prop/query_addin_prop` 三个**函数** | `os/skill/skill.js:4-10` |
| 角色记录 | 只是一个**裸对象**，没有类、没有方法 | `chara_skill.js:66-86` |
| 等级读取 | `query_skill(name, def) = skills[name].level + query_prop(name)` | `chara_skill.js:3-6` |

> ★ 第 3 行值得单独注意：**`query_prop(name)` 里的 `name` 是技能 id**
> —— 也就是「装备/饰品挂了一个叫 `taijijian` 的 prop，就等于给太极剑法加等级」。
> 这是把"装备加技能等级"实现成"prop 键 = 技能 id"。**本提案不抄这条**（见决策 D2 / §3）。

### 2.2 三档属性（12 册 §12.1.2 抄，但要改挂载方式）

| 档 | 函数 | 何时生效 | 参数 |
|---|---|---|---|
| ① 学会即生效 | `query_prop(lv, me)` | 只要会这个技能 | 等级 |
| ② 启用后生效 | `query_enable_prop(lv, me)` | 当它被 enable 到某个**基本技能槽**时 | 返回 `{ 槽名: propObj }` |
| ③ 进阶附加 | `query_addin_prop(me, lv)` | `addin[]` 槽位里的词条 | 槽位表 |

### 2.3 装配模型（12 册 §12.1.2，**这套要抄**）

```
基本技能槽（force / dodge / parry / bite / sword / blade / ...）  ← 谁都可以有几个
     │  每个槽同一时刻只挂一个武功
     ▼
skills['sword'].enable_skill = 'taijijian'        槽指向武功
skills['taijijian']['sword'] = true               武功记录"我挂在 sword 上"
```

- `enable_skill(base, skill)`：**先卸旧**（`old_skill.disenable()`）→ `sp_skill_base.enable(me, base) === true` → 记账。
- `init_skill()` 解析出五类**当前生效技能对象**：`attack_skill`(按武器类型) / `noweapon_skill` / `dodge_skill` / `parry_skill` / `force_skill`。
- `query_used_skill(槽)`：槽有记录 → 取 `enable_skill` 指的那个模板；否则回退 `WORLD.DEFAULT_SKILLS[槽]`。

> ★ **槽的词汇表 wushen 是"隐式"的**：`SKILL_TYPES.BASE` 类型的技能 id 就是槽名。
> 代码里没有任何地方显式列出 `{force, dodge, parry, bite, sword, blade, staff, club, whip, ...}`。
> 而 `BASE_SKILLS` 常量**只有 4 个**（force/dodge/parry/bite）——武器类槽是以 `WEAPON_TYPE`
> 的形式**另立一处**存在。这是本提案要收敛的第一个点（决策 D1）。

### 2.4 绝招（pfm）：技能的**子对象**

- `pfm{ pid: { name, use, check, query_mp, query_releasetime, query_distime, enable_skill, allow_busy, no_auto, is_weapon } }`（12 册 §12.1.3）。
- 建模板时 `pfm.__proto__ = PERFORM.prototype` 并补 `id = skillId+'/'+pid`、`pid`（`skill.js:467-478`）。
- 冷却存 `temp["pfm/"+id] = {v, e}`（`skill.js:624` `change_distime`）。

### 2.5 学习 / 升级 / 进阶

| 环节 | 公式 / 条件 | 位置 |
|---|---|---|
| 每级所需经验 | `(lv+1) * (grd+1) * 5` | `skill.js:46` |
| 升级循环 | `exp` 够就 `lv++`，**>100 级才计评分** | `skill.js:324-365` |
| 等级上限 | `round(pow(exp * {20,30,40,50,60,60}[境界], 1/3))`；`exp<100` 固定 **10** | `chara_skill.js:87-99` |
| 进阶（突破） | 需 `level>=1000`；`newLevel = int(sqrt(pot*2/5/(targetGrade+1)))`；**移除原技能、写进目标技能** | `skill.js:380-401` |
| 学习条件 | `learn_condition` 一个 key→value 字典，`switch` 按 key 分派（skill / str1 / gender / 其它当 prop） | `skill.js:207-264` |

### 2.6 门派（12 册 §12.2）

`FAMILIES[id] = FAMILY`；技能通过 `SKILL.update()` **反填**到门派的分档技能表
（`skills/skills2/skills3/skills4/skills0`）；门派持 `titles[]`（称号阶梯）、`npc_skills`（本门 NPC 技能）、`def_npcs`（NPC 布置）。

### 2.7 BUFF / 状态（12 册 + 11 册 §11.4）——**本批不碰，但要提前知道为什么**

`chara_skill.js:173-566` 有 400 行状态机：`add_status` / `change_buff` / `remove_status`，
`is_busy` / `is_faint` / `is_miss` / `is_rash` / `is_shadow` 都是**"持续时间数值"**直接挂在角色字段上。
六道闸门读的正是这几个字段（本项目已把它们收进了 `CommandActor.fightType/state/isFaint`，见 26 册 §9）。

> 技能绝招会在 `on_attack_over` 里 `target.add_status({is_busy:true,...})`。
> 也就是说**绝招的"控制效果"依赖状态系统**——这套属于战斗批次。
> 本批只把**冷却**和**数据**立起来，控制效果留空接口。

## 4. ★★ 需要你确认的决策

> 下面每一条都会**改变代码形态或内容写法**，所以我停在门口。默认建议已给出（标「建议」），
> 你只需要说"按建议"或点名改哪条。

### D1 · 装配槽（enable slot）的词汇表怎么定？

**问题**：武功要挂到"基本技能"上。这个"基本技能"是**闭集词汇**（force/dodge/parry/bite/sword/blade/staff/club/whip/throwing/unarmed），
但 wushen 把它拆成了两处（`BASE_SKILLS` 4 个 + `WEAPON_TYPE` 7 个），且**代码里从不显式列出全集**。
本项目现状更乱：`NpcDef.skills[].enableAs` 被校验器限制成 `BASE_SKILLS` 的 4 个名字，
而 `SkillDef.can_enables` 校验的是**内容技能 id**（`'base/force'`）——**两个字段用了两套 id 空间**。

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（建议）** | `ENABLE_SLOTS = BASE_SKILLS ∪ WEAPON_TYPE`= 一个**闭集联合类型**；`can_enables` 与 `enableAs` **都**只接受槽名 | 需改 `defs.ts` 两个字段的语义 + G4 校验 + 修现有内容（见 §9 P1/P2）|
| B | 槽名 = 内容注册的 `BASE` 技能 id 的末段（`base/force` → `force`） | 保留两套空间，靠"末段相等"桥接；仍然隐式 |
| C | 槽名 = 任意内容 skill id（完全放开） | G4 无法校验，回归 wushen 的隐式 |

**建议 A**：槽是**引擎概念**（决定 `attack_skill/dodge_skill/...` 五类解析），本就该是闭集。
好处是 `can_enables: ['sword']` 一眼可读、写错即编译失败。需要同步修内容（剑法应挂 `sword` 而非 `force`）。

### D2 · 技能属性怎么"挂上去"？（最重要的一条）

**问题**：技能给的属性加成，怎么进角色的 `props`（公式读的那个 Map）？wushen 用增量三角，
**换技能 / 升级 / 热更任一环节漏一步，`prop` 就永久重复累加**——而且不会报错，只表现为"数值偏高"。

| 选项 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| A | 增量 `attach/release`（wushen 原样） | 照抄快 | **会漂移**，无自检 |
| **B（建议）** | `SkillBook` **记账式重算**：记住"上次加了哪些键/多少"，重算时**先减掉旧账、再加新账** | 幂等、可重复调用、能自检"账 vs 实际" | 需在 `SkillBook` 里存一份 delta 台账 |
| C | **分层属性**：`props = 先天层 + 技能层 + 装备层 + BUFF 层`，只重算技能层 | 架构最干净，一劳永逸 | 要动 `PropHolder` 与所有写 prop 的地方（大改）|

**建议 B**：先落记账式重算。它**幂等**（调 10 次结果一样），并且能加一条自检
「重算前后 `props` 完全一致」——把 wushen 那类"多算了一遍"变成**当场会红**的事。
C 留到装备批次（那时会有第二个加成源，分层才有真实收益）。

### D3 · 绝招做到哪一步？

**问题**：绝招的 `use()` 里是 `me.do_attack(...)`，而战斗系统未建。

| 选项 | 范围 |
|---|---|
| **A（建议）** | 本批：`Perform` **数据面**（name / mp / releasetime / distime / enable_skill / allow_busy）+ **冷却**（`temp` TTL）+ `check()` 准入。`use()` 声明为接口但**不执行战斗** |
| B | 连 `use()` 也留空不声明，等战斗批次一起做 |

**建议 A**：冷却与准入可脱离战斗完整单测；把"能不能放"和"放了打谁"分开，边界清楚。

### D4 · 等级 / 经验 / 上限公式照抄吗？

| 项 | wushen | 备注 |
|---|---|---|
| 每级经验 | `(lv+1)*(grd+1)*5` | 简单，建议照抄 |
| 等级上限 | `round(pow(exp*{20..60}[境界], 1/3))`；`exp<100→10` | **曲线很怪**（经验翻 8 倍上限才翻倍），是"卡等级"的设计 |
| 进阶 | `level>=1000` 且 `newLevel=sqrt(pot*2/5/(grade+1))` | 门槛极高 |

**建议**：三档数值**全部进 `COMBAT_FORMULA` 式的参数表**（如 `SKILL_FORMULA`），**先照抄 wushen 的取值**，
但**不写死在表达式里**——于是"调参"和"改设计"是同一处的一行数字，不产生第二份事实源。

### D5 · 学习条件的数据模型

| 选项 | 形态 |
|---|---|
| **A（建议）** | 声明式 typed 条件：`{ minSkill?: {[槽 or 技能]: level}, minProp?: Partial<Record<PropKey,number>>, gender?: 0\|1, maxMp?: number, desc?: string }` ★ **2026-10-15 订正**：属性条件已**归一为 `minAttr`**（读"有效属性 = 先天+后天"，取代 `minProp`+`minInnate`）—— 见 **29 册 §29.13** 与 **26 册 §37** |
| B | 照抄 wushen 的 `learn_condition` 字典 + `switch`（`skill/str1/gender/其它当 prop`） |

**建议 A**：wushen 的 `switch` 把"条件键"和"属性键"混在一个命名空间（`str1` 是先天、`str` 是含 prop），
极难校验。声明式之后，G4/G3 能对账"条件里引用的技能/属性键是否存在"。

### D6 · 知识类技能 / 隐藏技能 / `addin` 进阶槽

| 选项 | 范围 |
|---|---|
| **A（建议）** | 本批支持 `type=KNOWLEDGE`（不参与装配、只给被动）与 `is_hidden`；`addin[]` 槽**留类型与接口，不做内容** |
| B | 全部后置 |

**建议 A**：类型现在加进去成本低；`addin` 的内容依赖"进阶词条表"（wushen 的 `slots{}`），那是一个独立子系统，后置。

### D7 · 门派（FAMILY）本批做不做？

| 选项 | 范围 |
|---|---|
| A | 本批只做技能，门派完全后置 |
| **B（建议）** | 本批顺带做门派**薄壳**：`FAMILY` 注册表 + `titles[]` 称号 + `skills[]` 反填（技能按门派归类）。**不做**门派战/贡献榜/NPC 布置 |

**建议 B**：门派与技能是双向引用（技能属门派、门派列技能），分开做会有一次"补引用"的返工；薄壳成本很低。

### D8 · 技能是"每角色一个实例对象"还是"轻量记录 + 模板引用"？

| 选项 | 形态 |
|---|---|
| **A（建议）** | 模板（`SkillTemplate`，全局唯一、不可变）+ 角色记录（`SkillState{id,level,exp,enabled,addin}` 纯数据）。行为在 `SkillBook` 上，不散落到记录里 |
| B | 每角色 `new SkillRuntime(template)`（对象持行为） |

**建议 A**：wushen 的记录就是裸对象，行为在模板上——它是**对的**（行为无状态）。
保持"行为在模板/簿、状态在记录"的划分，存档只需序列化纯数据。

### D9 · NPC 的技能要不要保留"完整技能 id"？

**现状**：`Npc.#skills` 建成 `槽名 → 等级`（`enableAs ?? skill` 作键），**把技能 id 丢了**——
于是 NPC 只有"某个槽多少级"，说不出"它练的是太极剑法"。（现有 `xiaoer` 就靠 `enableAs:'force'` 把
剑法写成了内功，见 §9 P2。）

| 选项 | 形态 |
|---|---|
| **A（建议）** | `NpcDef.skills` 完整保留（技能 id + 等级 + 槽），`Npc` 内部改用 `SkillBook`，`forceRad` 从簿上取 |
| B | 维持现状（只有槽→等级） |

**建议 A**：与 D1/D8 一起做，顺手把 `Npc` 的技能面从"简化 map"升级成真正的 `SkillBook`，
`forceRad` 也自然从"启用为 force 槽的技能等级"派生，逻辑与玩家归一。

## 5. 建议的对象模型与接口（按建议选项）

```
SkillRegistry（全局，从 registry 的 'skill' 条目构建一次）
  template(id) → SkillTemplate | undefined
  byFamily(familyId) → SkillTemplate[]
  byGrade(slot, grade) → SkillTemplate[]        ← 取代 SKILL[slot][grade] 挂类上

SkillTemplate（不可变；包装 SkillDef）
  id · name · type · grade · family · can_enables(槽闭集)
  queryProp?(lv, me) → PropMap                  ① 学会即生效
  queryEnableProp?(lv) → Partial<Record<Slot, PropMap>>   ② 启用后
  learnCondition?（typed，见 D5）
  actions?（attack/dodge/parry 文案）
  pfm: Record<pid, Perform>（见下）
  hooks: on_learn / on_remove / on_enable / on_disable / on_recount_dodge / on_recount_parry / on_attack_over / ...

Perform（技能子对象）
  pid · name · mp(lv) · releaseMs(lv) · cdMs(lv) · enableSlot? · allowBusy?
  check?(me, lv) → boolean                       准入（可脱离战斗）
  use?（**声明但本批不接战斗**）

SkillState（角色侧纯数据）      { id, level, exp, enabled: Slot | null, addin: string[] }

SkillBook（角色侧行为；Character 持有，与 TempStore / PropHolder 并列）
  learn(id) / forget(id) / setLevel(id, lv) / addExp(id, exp)
  enable(slot, id) / disable(slot) / levelOf(id) / enabledSkill(slot) → SkillTemplate
  activeCombat(): { attack, noWeapon, dodge, parry, force }   ← init_skill 的对应物
  contributedProps(): PropMap                    全量算出"技能一共给了什么"
  recompute(): void                              记账式重算（D2-B）：先减旧账、再加新账、最后 recount
  pfmCooldown(pid, nowMs) / setPfmCooldown(pid, ms)（底层走 TempStore）
  snapshot() / load(raw)                         存档边界
```

**挂载链（本提案的核心闭环）**

```
内容改技能（学/升/装/卸）
      ▼
SkillBook.recompute()          ← 唯一入口；先减旧账、再加新账
      ▼
角色 props 更新 → Character.recount() → computeDerived()（已有的公式，不改）
      ▼
formula.ts 的 COMBAT_FORMULA 参数表（不改）
```

> 与现状的关系：`computeDerived` / `recount` / `props.ts` **一行都不改**——
> 技能只是"另一个往 `props` 写账的人"，而记账与重算被收进 `SkillBook` 一处。

**抄**：① 三档属性（拆成 `passiveProp` / `enableProp` 两个类型化回调）；
② `can_enables` + `enable_skill` 装配模型（一个槽同时只挂一个武功）；③ 绝招作为技能子对象（独立 MP / 出招 / 冷却）；

**不抄 / 改**（每条都有对应断言，见 §12.4）：

| # | wushen 做法 | 本项目的做法 | 钉住它的断言 |

| 6 | `release_prop → 改 → attach_prop` 增量三角 | `SkillBook.recompute()` **记账式重算**（先减旧账再加新账）| ★「连调 `recompute()` 10 次，`props` 完全一致」（SKL.1）|

### 12.3 实现与本提案的差异（逐条）

| # | 提案写法 | 实际落地 | 为什么 |
|---|---|---|---|
| 1 | `SKILL_FORMULA` 放 `shared/constants.ts` | 放 `server/engine/skill.ts` | 与既有 `COMBAT_FORMULA` 放 `formula.ts` 同例：**参数表贴着唯一的消费者**，`shared/` 只放"多端共享的枚举/协议"。汇总入口仍是 `tuning.ts` |

| 3 | `learnCondition.minSkill`（按技能）| `learnCondition.minSlot`（按**槽**）+ `minInnate` + `minProp` + `minMaxMp` + `gender` | wushen 的 `str1`（先天）/`str`（含 prop）二义性在"按技能"下会更严重；按**槽**问"你基本剑法几级了"才是玩家的心智模型。★ **2026-10-15 收尾**：那对二义性最终被**彻底消除** —— `minInnate`+`minProp` 并为 `minAttr`（读有效属性），见 **29 册 §29.13** |
| 4 | `SkillTemplate.actions?`（攻击文案）| **未做** | 消费者是战斗系统（在下一批）。带一个没人读的字段 = 假接口 |
| 5 | `addin` 进阶槽"留类型与接口" | **完全未做**（连字段都没有） | 同上：`addin` 的内容依赖"进阶词条表"这个独立子系统，留一个空 `addin: string[]` 只会让人以为它能用 |

## 13. 成长闭环：经验 → 技能等级上限 · 潜能 → 技能等级（2026-10-17）

> 触发：用户给出三句话的需求 ——
> 「打怪给潜能和经验，都直接给角色，经验决定技能等级上限，消耗潜能可以提升技能等级」。
> 本批（26 册 §56）把这三句落成一条**可反复跑**的闭环：
>
> ```
> 击杀 NPC ──NpcDef.exp/pot──▶ Character.addExp()  （经验 + 潜能，播报一次）
>                                     │
>              经验 ──▶ skillLimit() = levelLimit(exp, level)   ← 技能等级上限的唯一算式
>                                     │
>                                     ▼
>              潜能 ──practice 1:1──▶ SkillBook.addExp() ──▶ 技能等级（受上限封顶）
> ```

### 13.1 先核实 wushen：哪部分原作**真的接了线**

| 机制 | wushen 实况 | 本批的处理 |
|---|---|---|
| `skill_limit()`（经验 → 上限） | **代码在，但只有 `lianxi` 在调**（`os/char/chara_skill.js:87`；调用点 `lianxi.js:44`、`:131`）。公式照抄：`round(pow(exp*factor, 1/3))`，`exp<100` 固定 10 | 照抄 `SKILL_FORMULA.limitRealmFactor = [10,20,30,40,50,60,60]`，**接上 `SkillBook.addExp` 的封顶**（本批的核心改动） |
| `CHARACTER.EXP_LIMIT`（`character.js:303`） | **零调用点**（死代码）——人物等级不靠经验升 | **不做**。境界提升（`level_up`）走"技能达标 + 内力 + 找 NPC"，属门派批次；在此之前 `level` 恒 0 ⇒ 因子恒 10 |
| 打怪给经验 | **`npc.js` 的 `die()` 里一处 `add_exp` 都没有**；`add_exp` 的调用点全在副本结算（`cr.js`）、采集/钓鱼/挖矿（`caiyao`/`diaoyu`/`wk`）、任务奖励 | **本批补上**：`NpcDef.exp/pot` → `Npc.afterDeath` → 击杀者。字段名沿用 wushen 内容层的写法（`world/area/fb1/fb1.js:12-13` 的 `exp: 500, pot: 500`） |
| 木人桩 | **打不死**：`world/npc/pub/muren.js` 把 `die()` 整个覆写成"回满血 + 播报"，`return false` ⇒ 它的 `exp/pot` **永远发不出去** | 本项目做成**正常会死**、死了给奖励、30 秒重生的练功靶子（见 §13.4） |
| `pot` 的用途 | `lianxi` 是**唯一**消耗点（`me.pot -= exp`）；其余全是 `add_exp` 在加 | 照抄 1:1 兑换（`lianxi.js:172-175`） |

**结论**：用户的三句需求，前两句在 wushen 里是"代码在、但没接线"，第三句（潜能练技能）是原作**真做了**的。
本批把前两句接上，第三句照抄数值、换形态。

### 13.2 三条硬规则（都可被断言钉住）

1. **上限只有一个算式**：`Character.skillLimit() = levelLimit(exp, level)`（`skill.ts`）。
   `SkillBook.#capOf(tpl) = min(tpl.maxLevel, skillLimit())`，**所有**加经验的路径都经过
   `SkillBook.addExp` ⇒ 没有哪条路能绕过上限（26 册铁律"单一封顶点"）。
2. **NPC 不受这条曲线**：`Npc.skillLimit()` 覆写为 `Infinity` ⇒ 它们的天花板就是模板 `max_level`。
   依据见 §13.1（wushen 的 `skill_limit` 只有玩家练习路径在调）。
3. **奖励只发给击杀者**：`Npc.afterDeath(killer)` 里 `killer?.addExp(def.exp, def.pot)`。
   `NpcDef.exp` 是"这只怪值多少"，**不是** NPC 自身经验 —— 两者同名字段不同义，
   别把 `def.exp` 塞进 `this.exp`（那样打死一只怪等于自己练了一级）。

### 13.3 与 wushen 的四处偏离（都是**形态**，不是数值）

| # | wushen | 本项目 | 为什么 |
|---|---|---|---|
| 1 | `lianxi` 是**持续状态**（`set_state` + 每 5 秒心跳 `do_learn`，可排队/中断） | `practice` **一次结算**：一次调用把"到目标等级"的账算清并落账 | `state` 状态机尚未落地（`Actor.state` 目前只读）。账目口径不变（`me.pot -= exp; add_exp(me, exp)`），状态机落地后 `do_learn` 每拍调 `practice()` 一次即可 |
| 2 | 到 `max_level` 后 `skill.exp` 自然留在原地（它没有"上限清零"这回事） | `addExp` **不再清零**剩余经验（旧实现有 `if(level>=maxLevel) exp=0`） | 上限现在是**动态**的（经验涨了上限就抬），清零会把已付代价的进度吞掉 |
| 3 | 玩家按**英文 id** 敲（`lianxi taijijian`） | id 与**中文名**都认（`SkillRegistry.byName`；重名**抛错**，不静默取第一个） | 玩家心智里是"太极剑法"，不是 `wd/taijijian` |

### 13.7 `practice` 的结果形状：**七种原因 + 判别联合**

七种拒绝原因**不可合并**，判据只有一个：**玩家读到提示后该做的事不同**。

| `reason` | 玩家处境 | 该做什么 |
|---|---|---|
| `unknown` | 名字打错 | 换个名字 |
| `not-learned` | 有这个技能，但不会 | 去学（目前**无入口**，见 §13.6）|
| `knowledge` | 知识类不能练 | 去读书 |
| `capped` | 到**上限** | 去涨经验 |
| `reached` | 到了你**指定**的等级 | 把目标写大点 / 不写 |
| `basis` | 基本功火候不够 | 去练基本技能 |
| `no-pot` | 潜能不够 | 去打怪 |

**判定顺序是决策树，不能换**：`unknown` → `not-learned` → `knowledge` → `capped` →
`reached` → `basis` → `no-pot`。其中 **`capped` 必须在 `reached` 之前**：`target` 先被
`min(targetLevel, limit)` 截断，满级时 `target === limit === level`，若先判 `reached`，
玩家会收到"已经练到 40 级了"，**上限这条信息被吞掉**。

**形状**：`PracticeResult = PracticeDone | PracticeRefused`，判据是 `kind`（不是布尔标记）；
每个拒绝分支只带自己文案要用的字段（`basis` 读不到 `level`，`reached` 读不到 `limit`）。
文案表 `switch` **不写 `default`**，末尾 `const uncovered: never = r;` 让漏一支变成编译错误。
理由与取证见 26 册 §56.8。
